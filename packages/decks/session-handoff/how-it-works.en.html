00 · session continuity

Context transplanted, not summarized.

/session-handoff compacts a whole agent session into a file, so a new session picks up exactly where this one stopped, as if the context window had grown instead of reset. The successor is not a reader being told about someone else's work: it is this same session, with a fresh window. Everything it needs to act has to be on disk, addressable, and true when it reads it.

for whoever develops and whoever maintains manual trigger, by design same worktree, same harness

The human asks for it

They notice the window filling up, or that the work goes on past this session.

01 · what it is not

What looks like this skill and is not

A handoff moves the whole session to its own successor. Each neighbor in this table moves something else, and has its own door.

Looks like Actually is Used with
Handing a scoped task to another session and supervising it Orchestration: a task goes out, the work comes back /orca-orchestration
Dispatching a subagent for a piece of work An executor with a briefing, inside THIS session AGENTS.md §3, briefing-template.md
Resuming a story's pipeline after a pause A skill's state, per ticket /sprint-development fase 0, session-management.md
Remembering a decision for next month A durable fact across sessions, about the project Engram (mem_save), an ADR or the tracker
Shrinking the window and carrying on The harness's compaction: lossy, not addressable, outside your control Nothing to do
Moving the whole SESSION to its successor This skill /session-handoff
The difference that matters. Compaction keeps what a summarizer judged relevant. A handoff keeps what the next actor needs, which is a different set, and it is written by the only part that knows the difference.
They compose

With each skill's progress.md

  • A skill's progress.md says where ONE workflow stands. The handoff does not copy it: it points to it, in its reading list and in its live state.
Not a briefing

The 7 components do not apply

  • A briefing scopes a task. A handoff transplants a session. That is why it has its own contract, with ten sections.
02 · when to write one

The trigger is manual, on purpose

The human sees the window filling up, says so, and the skill runs. No polling, no reminders, no tokens spent guessing.

Write one when

Any of this is true

  • ~500k tokens of window used: the owner's threshold, unless they name another. It is their judgment about where this model starts to degrade, not project configuration: it lives in the conversation, not in a yaml key.
  • The session is about to end with work in flight: an open PR, an unverified deploy to staging, a migration written but not applied.
  • What comes next will eat a big slice of the window (a huge diff, a long file, the log of the whole suite) and what is left will not cover the work after that.
  • The owner asks for it.
Do not write one

If what remains fits comfortably

  • Producing a handoff costs a real slice of context. A successor launched too early pays the startup cost for nothing.

What about an automatic trigger?

The answer, with citations, is in references/auto-trigger.md. Verdict: partially feasible, and the manual trigger stays the main one.

No harness passes the size to the agentClaude Code, OpenCode and Pi expose it outside the model's loop; Codex does not. An automatic trigger can be built, but it is new wiring, not a field waiting to be read.
Compaction is the wrong momentEvery harness warns that compaction is imminent, but by then the window is already full: the handoff would be written by a session about to be truncated, with the degraded judgment the handoff exists to escape.
If it is ever turned onIt asks once, in two lines, and accepts a no without asking again in that session. It never writes a handoff unless asked.
The owner's position, on record: "I prefer the human to do it manually". What auto-trigger.md says answers "could it be done?", it is not a plan.
03 · the capture contract

Ten sections, in this order, none omitted

A section with nothing to say is written as a none line with its reason. An omitted one and a forgotten one look identical, and the successor cannot ask which it was. The order is not decorative: it is read top to bottom in a hurry, so it opens with the one thing to do and closes with what is always true.

§ Section What it holds What it prevents
0 Your FIRST task One task, not a menu. The owner's criteria quoted, numbered, without paraphrase. A story's criteria are cited by the synced PBI path. A successor that re-decides what was already decided, and picks differently
1 Identity and authority What the owner delegated and what they kept; harness, worktree, trailers; the strategy of git and the push policy with their resolved values from git_strategy:, not the name of the key Asking again about something delegated, or assuming a permission that does not exist
2 What was built One paragraph per unit of work, with SHAs, PRs, deploys and paths. Pushed or local, merged or open, deployed or only built Redoing work that was already finished
3 Decisions, each with its why Rejected alternatives, the reason, and who decided. Architectural ones cite their ADR Reverting a deliberate choice because it looked like an oversight
4 Gotchas and observations What was learned the hard way, each marked measured or read, with the version it holds for Paying the same cost twice. It is the most valuable section and the one that comes out thinnest
5 Skills, tools and MCPs A table with the Load next session? column answered row by row with a reason Reloading everything and burning the new window, or loading nothing and guessing syntax
6 Files to read, in order Numbered list, absolute paths, what each one is for. Skills' progress.md files come before the code they describe The successor having to hunt for what the predecessor already found
7 Live state you inherit The perishable section. See freshness Acting on a world that no longer exists. This is where handoffs break
8 Pending work, by priority Lettered items, in the owner's order, with the exact next step. It separates what is decided from what waits for a decision Starting with the interesting item instead of the important one
9 Conventions the owner cares about How decisions are presented, what is announced, language, register, memory. It closes with the threshold at which the successor writes its own handoff Relearning preferences by getting them wrong first. And a lineage that dies
The AI does

Walks through capture-contract.md section by section and fills in templates/handoff.md.

Before writing: lists the handoffs directory and re-verifies everything that goes into §7.

You decide

When: the trigger is yours.

A name for the session, if the identity says unknown.

Output

A markdown file in English, gitignored, disposable by design.

Anything durable does not go here: it goes to Engram, the repo or the tracker, and the handoff cites it.

Gate all ten sections present, in order; none empty without its none line.
04 · measured, predicted, perishable

What was true when written has already changed by the time it is read

The predecessor's guesses about what the successor will find are useful, and they are the first thing to go stale. That is why every claim carries its label.

measured

This session ran it and read the output

  • It can be used as a starting point, with the time it was measured.
predicted

Nobody observed it

  • "If CI fails on lint, do X" is predicted. A predicted branch presented as fact sends the successor down a path that no longer exists.

§7, the PERISHABLE section

Everything that is still moving: open PRs and their checks, deploys not yet confirmed READY for the pushed SHA, subagents or commands in the background, Jira transitions in flight, migrations written but not applied, resumable sessions.

Every item marked PERISHABLE, with the wall-clock time it was last measured.
Every item with the exact command that re-verifies it: gh pr checks <N>, bun run jira:sync-issues get <KEY>, the deploy poll of /vercel-cli. The instruction is re-verify, then act, never the other way round.
Ids are copied as they are, in backticks: PR number, tracker key, SHA, deploy id, session id, terminal handle. "The earlier PR" is not an id.
Perishable beats priority. If anything in §7 needs attention before the order of §8, the item says so. The successor cannot infer it. 
# shape of a §7 item (templates/handoff.md)
- **staging deploy**: `PERISHABLE`, measured <HH:MM>. Ids: `<sha>` `<deployment-id>`.
  Re-verify: `<the exact command>`. Then: <what to do with each outcome>.
A receipt is not a result. This is Critical Rule #16 of AGENTS.md applied to the handover: a 201 or a "deploy accepted" noted in the handoff does not say the thing happened. The successor reads the destination before acting.
05 · where it lives and what it is called

Always in the primary checkout, even when the session runs in a worktree

<<PRIMARY_ROOT>> resolves the same from the primary and from every worktree (.agents/README.md, section "Checkout roots"). It is never derived from pwd. 

# the path
<<PRIMARY_ROOT>>/.session/handoffs/<predecessor-session-name>-handoff-NN.md

# how PRIMARY_ROOT is resolved
dirname "$(git rev-parse --path-format=absolute --git-common-dir)"

# the lineage reads off the file list: the successor's name is the basename without extension
<base>
<base>-handoff-01
<base>-handoff-01-handoff-02

Why the primary

A handoff written inside a worktree dies with the worktree. And two worktrees of the same lineage would each count NN from their own empty directory.

If one ended up by mistake in a worktree's .session/, bun run worktree:audit --rescue rescues it before the worktree goes away.

How NN is chosen

By listing <<PRIMARY_ROOT>>/.session/handoffs/. Two digits from 01, counted across the whole lineage. Never assumed. Two handoffs with the same number are a lineage that cannot be read.

Where the name comes from

From the session= value of the AGENT IDENTITY: line the hook injects (the same label the commit trailers carry), with spaces and parentheses replaced by -. If it says unknown, the AI asks you for a name instead of inventing one.

Long names are the point: a lineage that cannot be read is a lineage that cannot be audited.

Why gitignored

.session/ is ignored. A handoff describes the state of a session, it is not a project record: committing it would put a snapshot that rots under version control.

06 · launching the successor

The complete file first, the new session after

The order is never reversed: a successor that starts first reads a file that does not exist yet. It runs in the same worktree as the predecessor (<<REPO_ROOT>>) and in the same harness. Only the file lives in the primary.

With a reachable runtime
1Three preconditionsRuntime responds, file complete at its final path, same worktree and harness. 2Warn you firstWhich terminal will carry it: a second session will show up on your board. 3A plain terminalIn the active worktree, with the launch line as the command. Never a supervised worker.
Without a runtime
1Print the lineAnd say where the handoff ended up. 2You paste itIn a new terminal opened in the same worktree. =Same prompt, byte for byteThe path nobody exercises is the one that breaks silently. 
# the bare binary: its MCPs read .env through the .env loader
claude     # or: opencode · codex · pi, the same harness as the predecessor

# the first prompt, identical on both paths
Read `<absolute path to the handoff>` top to bottom and continue that session exactly where it stopped.
The session name travelsThrough the harness's own flag (read it in its --help, not copied here). In Claude Code the hook also titles an unnamed session from a --name <value> in the first prompt.
The fleet token only travels if it was already thereThe successor is the same session, not a new worker. If the predecessor was a fleet worker, its prompt opens with /<skill> <label> fleet worker and the successor carries on without asking the human; otherwise the prompt does not carry it.
With nobody at the keyboardA routine launches the successor only if the brief that delegates it approves; otherwise it stops at the printed line. The open decisions in §8 are reported, not executed.
If §0 imposes an order, it goes in the promptA pointer to a file is read as reference material; an instruction in the prompt is read as an instruction.
The runtime's grammar is not copiedWhen needed, the binary is asked for its guide. A copy goes out of sync with the next version.
Handoff (this skill) Orchestration (/orca-orchestration)
What moves The whole session A scoped task
The predecessor Finishes Keeps working and supervises
Channel afterwards None, by design Mailbox, questions, answers
Runtime objects One terminal Run, task, dispatch, worker
The predecessor's last acts, in order: confirm on screen that the successor started and has the file; persist what is durable to memory (mem_session_summary), because the handoff is disposable and memory is not; and stop. It does not close its own terminal: ending the predecessor is the owner's call, and a session that closes in the middle of a check cannot report that the handoff failed.
07 · hard rules

The guardrails that are not negotiable

They live in the ## Compact Rules block and in the skill's "Hard rules"; the compact ones are the ones that travel to subagents through .agents/skills/REGISTRY.md.

No secrets in the file. It names the key of .env where a credential lives, never its value. Cookies, tokens and storageState.json paths stay out.
The predecessor's handoff is never deleted. The lineage is the audit trail: writing -handoff-02 does not remove -handoff-01.
Name what is NOT done, and why. A handoff that reads as a flawless success hid something, and what is hidden is always what bites.
Every path is absolute. The successor may start in another directory.
Harness parity. A handoff built for one agent's conventions and handed to another is a translation problem nobody asked for.
It is a repo artifact: in English even if the conversation is not, with no AI attribution (Critical Rules #3 and #12), and never committed.
08 · what you tell the AI

Invoking it in each terminal

It has no modes: one run, three steps. Naming it is enough, or asking in your own words, for example "hagamos el handoff" (let's do the handoff), "pasa el contexto a otra sesión" (pass the context to another session) or "hand this session over".

Claude Code

/session-handoff

The skill's slash command, with no arguments.

OpenCode

load the session-handoff skill

No slash: you name the skill in the sentence.

Codex

load the session-handoff skill

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:session-handoff

Slash with the /skill: prefix. In a new folder, /trust once.

The successor comes from the same host. A Claude Code predecessor launches a Claude Code; OpenCode launches OpenCode; Codex launches Codex; Pi launches Pi. The launch line belongs to the harness, not to the runtime.
09 · around this skill

Who it works with

It is small on purpose: the heavy artifact is the markdown it produces, and the whole contract lives in references/capture-contract.md.

Alongside · another way to move work

/orca-orchestration

For delegating a scoped task and supervising it while you carry on. Its terminal verbs and its traps are the ones the launch with a runtime uses.

Pointed to · per-story state

/sprint-development

Its phase 0 resumes a story from .session/sprint-development/<KEY>/progress.md. El handoff points to that file, it does not copy it.

Cited · what lasts

Engram, ADRs and the tracker

The facts that outlive the session go there. The handoff cites them; the predecessor closes with mem_session_summary.

To read more: .agents/skills/session-handoff/SKILL.md, its three references in references/ and the skeleton in templates/handoff.md. Related doctrine: agentic-dev-core/references/session-management.md.

The idea behind it. A long session knows things that are not in any file: what was decided and why, what is still in flight, what was already tried and failed. The handoff puts them on disk, with their expiry date in plain sight, so the next session uses them without believing them blindly.
