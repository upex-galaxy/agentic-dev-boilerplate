00 · from idea to specification

Define the product before writing the first line.

/project-foundation sets the definition of a new product in order: why it is built (Constitution), what is built (PRD and SRS) and how the system fits into its world (Discovery). It leaves the documents that every skill that comes later takes for granted.

01 · when to use it

The first thing a new product runs

It is invoked at the start, before the infrastructure is set up and before the backlog is seeded. If the scope changes a lot midway, only the phase that needs it is run again. falta.

Use it when

There is an idea and no specification yet

  • A product is defined from scratch and needs a Constitution, PRD, SRS and Discovery.
  • An existing project changes direction (a pivot, a new MVP cut) and the base documents have to be regenerated.
  • One section is missing or has gone stale, for example the user journeys: only that phase is invoked.
Do not use it for

What belongs to another skill

  • Setting up the code (backend, frontend, OpenAPI, auth): that is /project-bootstrap.
  • Seeding the backlog in Jira with epics and stories: that is /product-management.
  • Planning or implementing a story: that is /sprint-development.
  • Unit tests: that is /unit-testing.
  • Formal QA (test plans, exploratory, automation): out of scope here.
What comes out is "ready for /project-bootstrap", not "ready for production". The foundation is documentation: code starts in the next skill.
01·b · existing app: Discovery only

An app whose code already exists has no product to define: its foundation is what the code does, written down. It applies when .template/installer.lock.json says adopted: true (the same value that /project-context reads) or when you ask to document an existing app that has no content in .context/PRD/ or .context/SRS/. A project that already has a PRD and SRS keeps the full chain.

Phase On an existing app
1 Constitution, 2 PRD, 3 SRS They do not run. If the team already has real product documents, they can hand them over; nothing is invented to fill a phase.
2.5 Design Does not run from here. The DESIGN.md comes from the live theme with /design-system extract, optional and on its own.
4 · steps 1 to 3 and 5 The /project-context modes, which read the code and the stack: block. A map that is already generated is not regenerated: it is only refreshed by its own mode if it went stale.
4 · step 4, development guide Rebuilt from the code: folder structure, conventions and commands come from the app, from its package.json and from the stack: block, never from the boilerplate defaults.
4 · step 6, glossary Seeded with the maps, the identifiers in the code, the texts of the live UI, the existing ADRs and the epic names in the tracker. If the file already exists, it is skipped.
The db capability is optional on this path. With schema_source: migrations the data map reads the files without a connection, and a project with no database access leaves a Discovery Gap in the map instead of stopping. The plan carries only Discovery (discovery-only) and the work continues with /product-management for the backlog and /sprint-development per story, never with the base phases of /project-bootstrap.

03 · what it reads

What it reads, in this order

Several inputs may not exist yet at the start. When one is missing, the skill reports it as a missing input instead of inventing the content.

Your brief or first draft

Whatever you bring as a seed: pasted text, a link to a document, the transcript of an audio.

.context/PRD/

If a PRD already exists, re-invoking a phase refines it in place; it does not rewrite it from scratch.

.context/business/

Personas, business model and market from a previous investigation. They are shown, never replaced with invented ones.

Market research you provide

Links, PDFs, analyst notes. Optional, but it is what improves the Constitution the most.

.agents/project.yaml

Project identity: name, key, domain, URLs of each environment. If it is missing, it is created or completed during this same pass.

04 · phase 0 and plan

First it checks for unfinished work, then it writes the plan

Both happen in the main thread before any phase, even the first time: that way "resume or start" is always an explicit decision.

The AI does

Looks for .session/project-foundation/progress.md. If it exists, it reads the plan and the latest entries and shows you the goal, the last closed phase and the next one.

If it does not exist, it drafts plan.md: goal, inputs, approach, the phase breakdown (1, 2, 2.5, 3 and the Discovery steps), risks and a verification checklist.

You decide

With a previous session: resume, restart (the earlier one is archived with the suffix -aborted) or abort (nothing is touched).

With a new plan: which deliverables of Constitution, PRD, SRS and Discovery are produced. Phase 1 does not start without your approval.

Output

.session/project-foundation/plan.md in draft, which becomes approved when you approve it.

Each phase that closes leaves an entry in progress.md: if the session is cut off, it resumes from there.

Gate approved plan, with the scope of each phase chosen.
05 · phase 1

Constitution: why the product exists

The problem worth solving, who it serves, how it makes money and what competition it lives in. Without this, the PRD has no anchor.

The AI does

Builds the Business Model Canvas (segments, value proposition, channels, revenue, costs, metrics), a problem statement and the hypotheses the MVP has to validate.

Then a light market analysis: direct competitors, opportunity and trends.

You decide

You provide the evidence: interviews, analytics data, stakeholder requests, market sources.

Without research, the gap is marked as [PLACEHOLDER] and the AI asks you. It does not fill in with invented data.

If an answer is vague or overloaded (the product, the user, the money, the scope), the AI interviews you in rounds with the grilling skill, each question with its recommended answer. Without the skill installed, it makes the same numbered list.

Output

.context/business/business-model.md and .context/business/market-context.md.

Gate deliverables at their path, with the structure of their reference, and the phase entry in progress.md.
The Constitution names no tools. Database engine, hosting, auth provider or framework are chosen in the SRS: that way the architecture can change without invalidating the strategic anchor.
06 · phase 2

PRD: the product as a buildable specification

Formalizes the problem, names the users, cuts the MVP and traces the end-to-end journeys. It answers what and why; the how belongs to the SRS.

Executive summary first

Problem, solution, success KPIs and MVP metrics. The other pieces start from here.

Personas

Target users, goals, pain points, level of technology adoption.

MVP scope

Epics with high-level stories, what is in (must have) and an explicit section on what is left out.

User journeys

Happy path, alternative paths and edge cases per persona.

personas, scope and journeys run in parallel once the executive summary is written

The AI does

Drafts each piece from its reference and wires the cross-references: the personas appear in the journeys.

You decide

The MVP cut: what goes in and what is left for later. Personas, problem and KPIs carry cited evidence. A vague persona, KPI or scope goes through the same grilling interview as in the Constitution.

Output

.context/PRD/*.md: one file per piece, or a consolidated prd.md.

Gate PRD with its out-of-scope section. Without it, the scope leaks and is the first source of arguments in the middle of a sprint.
07 · phase 2.5

Design: the visual identity is defined before the architecture

Before closing the architecture, the skill hands the baton to /design-system, which produces the DESIGN.md at the project root.

The AI does

Invokes /design-system with the Constitution and the PRD as input. The default path is npx getdesign plus a matcher that picks a brand from the catalog; the other paths are in that skill.

You decide

If a DESIGN.md already exists and you did not ask for a rebrand, the step is skipped.

Output

DESIGN.md at the root, or wherever design_md_path in .agents/project.yaml says.

Gate the session comes back from /design-system and is noted in progress.md. That skill keeps its own session in .session/design-system/.
Why here, between the PRD and the SRS? The visual identity evolves together with the idea of the product, and some architecture decisions come out of it: a stack with a lot of animation or a lot of multimedia content is not the same as a minimal one. With the DESIGN.md ready, phase 3 reads it as input. The full flow of that skill is in the deck From blueprint to product.
08 · phase 3

SRS: the technical contract, with its decisions recorded

Turns the PRD into formal requirements, constraints, architecture and API contract. It is what /project-bootstrap reads to set up the code.

Functional requirements

One per PRD story, with input, processing, output and validations.

Non-functional

Performance, security, scalability, accessibility, reliability. Measurable metrics, not "must be fast".

Architecture

System diagram, data model, stack justification with its trade-offs, data flow and security.

API contracts

The OpenAPI specification of the endpoints, per domain.

the four pieces run in parallel once the PRD is closed

The AI does

With the architecture drafted, it promotes to an ADR each architecture decision that passes the three gates: it is hard to reverse, it is surprising without context and it is a real trade-off between alternatives. Auth model, data access, error contract, tenancy, deploy topology, frameworks with lock-in.

You decide

What you already approved (it is in the PRD or SRS you signed) is written as Accepted, citing where you approved it. Only what is still open goes as Proposed.

Output

.context/SRS/, the records .context/ADR/ADR-NNNN-*.md and the updated index .context/ADR/README.md.

Gate requirements trace to the PRD epics and the API contracts trace to the architecture decisions.
An ADR is append-only. An accepted one is not rewritten: it is replaced with a new one that links to the previous one. Bugfixes, local refactors or names are not ADRs. The procedure lives in agentic-dev-core/references/adr-doctrine.md.
09 · phase 4

Discovery: the mental model every new session reads

This phase does not generate the maps on its own: it requests them from /project-context, mode by mode. That way the same generator serves later, from any session, when the schema or the features change.

Step Who does it What it needs first What it leaves
1 · data map /project-context data nothing the map inside business-data-context
2 · features map /project-context features step 1 (warns if missing, does not block) the map inside business-feature-context
3 · API map /project-context api steps 1 and 2 inform, they do not block the map inside business-api-context
4 · development guide this skill the generated data map (required) .context/business/project-dev-guide.md
5 · master plan optional /project-context master-plan the data map (required) and the features map (recommended) .context/master-implementation-plan.md
6 · domain glossary this skill, once (the domain-modeling method, if installed) PRD, SRS, maps and ADRs as a seed .context/business/domain-glossary.md
The order

One at a time: data, features, API

  • Steps 1 to 3 follow the dependency order of /project-context, one at a time: features and API read the data map, and each mode closes its own approval before the next one starts.
  • The guide (step 4) only needs step 1 and can run alongside steps 2 and 3.
  • The master plan (step 5) is the synthesis: it goes last.
Good to know

Creating is not the same as updating

  • If the map does not exist or is a placeholder, the mode creates it. If it already exists, it updates it: it regenerates only the stale sections, shows you the diff and waits for your approval.
  • The master plan can be skipped if the scope is not defined yet, and re-invoked after seeding the backlog.
  • The glossary is maintained by hand and only grows: re-running the skill never regenerates it.
The maps are read with a command, not by opening the HTML: bun run context:map business-data-context prints its sections (or the placeholder notice if it has not been generated yet). That same command is the one that decides whether steps 4 and 5 can start.
10 · verify and archive

Each phase is verified; the whole session is archived

After any phase the skill confirms the same thing. When the plan checklist passes at the end of Discovery, it archives.

The deliverables exist at their paths under .context/.
Each document follows the structure of its reference: sections, titles, tables.
The cross-references are wired: personas in the journeys, requirements traced to epics, API contracts traced to the architecture.
bun run vars:check shows no new unresolved {{VAR}} variables.
Whatever stayed as [PLACEHOLDER] appears in the report as an open item, never as filler.
Archive. The .session/project-foundation/ folder is moved to .session/.archive/<YYYY-MM-DD>-project-foundation-project/ and the AI saves a session summary in persistent memory with that path, so that a future session can find it again.
11 · safety rails

What the skill never does

The full rules live in the SKILL.md frontmatter (compact_rules) and travel in the compact registry that the subagents receive (.agents/skills/REGISTRY.md).

It does not rewrite from scratch a Constitution, PRD or SRS that already exist: it refines them in place, preserves the decisions and shows the diff.
It does not invent personas, market data or competitors, and does not define personas, problems or KPIs without citing the evidence.
It does not mix PRD with SRS. The PRD says what and why; the SRS says how. Mixing them breaks traceability.
It does not skip Discovery. /product-management and /sprint-development assume those documents exist.
It does not name tools in the Constitution: that belongs to the SRS.
It does not deliver a PRD without an out-of-scope section, or an SRS with hard-to-reverse decisions and no ADR.
It does not fabricate a Constitution, PRD or SRS for an app whose code already exists: its foundation is only Discovery, read from the code. A missing PRD or SRS there is not a gap to fill.
It does not continue without database access when a step needs it: it declares the db capability, and if no tool provides it, it stops and tells you which one is missing, with no silent substitute.
12 · what you tell the AI

Invoking it in each terminal

This skill has no named modes: what you ask for picks the phase and the reference. You name the skill and describe what you need, in Spanish or English.

Claude Code

The slash loads the skill; the rest of the sentence picks the phase.

OpenCode

load the project-foundation skill: user personas

No slash: you name the skill in the sentence.

Codex

load the project-foundation skill: define SRS

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:project-foundation define the PRD

Slash with the /skill: prefix. In a new folder, /trust once.

The core idea. Each skill that comes later reads what this one leaves: why the product exists, what goes into the MVP, which architecture decisions are not argued again. The AI drafts and wires; you bring the evidence, cut the scope and approve the decisions.
