00 · the backlog before the code

Stories ready before anyone codes.

/product-management is the ongoing product work: it turns the PRD into epics and stories inside Jira, refines them until anyone on the team can pick them up, and works out the order in which they can start. The quality of the backlog decides everything that comes after.

01 · when to use it

Backlog work, every time it appears

Unlike /project-foundation, which runs once, this skill is invoked again whenever product work comes up: a new feature, an ambiguous criterion, a story that fails INVEST mid-sprint.

Use it when

There is backlog to create or polish

  • You seed the first backlog from a freshly written PRD.
  • A new feature or epic needs to join the backlog.
  • A story has acceptance criteria that are vague or ambiguous.
  • A story needs to be checked against INVEST or a 3 amigos session.
  • You want to list a feature's edge cases systematically.
  • You want a sprint report or to know what starts first.
Don't use it for

What belongs to another skill

  • Screens or mockups: the story is refined without them; the screen is resolved when /sprint-development picks up the story.
  • Defining the product from scratch: that is /project-foundation.
  • Setting up the infrastructure: that is /project-bootstrap.
  • Implementing a story: that is /sprint-development.
  • Unit tests: that is /unit-testing.
  • Formal QA test cases: out of scope for this repo.
Before starting: the PRD and SRS that /project-foundation leaves in .context/PRD/ and .context/SRS/ (required for the initial seed, useful context for everything else; in an existing app with no PRD or SRS, the business maps and the domain glossary stand in as product docs and flow A does not apply), the project identity in .agents/project.yaml, and Jira access through acli (or the Atlassian MCP as a fallback).

03 · the mechanism

Jira first, the local copy after

Everything the skill writes goes to Jira. What you see in .context/PBI/ is a read-only cache that a script materializes. Nobody writes it by hand: not you, not the AI.

Source of truth

The issue in Jira

[ISSUE_TRACKER_TOOL]
  • It is created with a real key (PROJ-45), never with TBD.
  • Criteria, scope and out of scope live in their own fields, not in the description.
  • Fields are named by slug ({{jira.acceptance_criteria}}), resolved against .agents/jira-required.yaml and .agents/jira-fields.json. Never a numeric ID.
  • Tool layer: acli first, the Atlassian MCP as a fallback, REST as a last resort.
Local copy

The synced cache

.context/PBI/epics/EPIC-…/stories/STORY-…/
  • bun run jira:sync-issues materializes it (get, pull, pull --epic).
  • One file per field with content: acceptance-criteria.md, scope.md, out-of-scope.md…
  • Something wrong in the copy? Fix it in Jira and sync again.
  • A fresh clone rebuilds it with bun run context:hydrate.
Trap: reading fields with acli viewIts default projection omits custom fields: the criteria look empty even when they are filled. To read, use bun run jira:sync-issues get <KEY> and open the field file.
Trap: several rich fields in a single callThe MCP converts Markdown to ADF only in the description. Several rich fields together make the whole update fail: one field per call.
What stays in human hands: the Jira SprintThe skill works out the execution order, but assigning issues to a Sprint object on the board is done by a person, when they decide to start it.
To understand the cache in depth: the deck PBI as a Jira cache explains the three file levels and why the local copy is not committed.
04 · plan before writing

A, B and C start with a plan you approve

The three flows that create issues follow the same session contract: first it checks whether there is half-finished work, then they write a plan, and only with your approval do they touch Jira.

Phase 0 · is there a previous session?

The scope is seed (A) or the epic slug (B, C). If progress.md exists, the AI shows you the goal, the last closed phase and the next one, and waits: resume, restart (archives the old one) or abort. In discovery or in a routine, where nobody is there to answer, it resumes on its own from phase 0.

Phase 1 · the plan

It writes .session/product-management/<scope>/plan.md: goal, inputs, approach, phases, risks and a verification checklist. It starts as draft and becomes approved only when you approve it.

Execution with checkpoints

Each epic created (A), each story added (B) or each part of the decomposed epic (C) leaves an entry in progress.md. If it is cut off, it resumes from there.

Archive

With the plan's checklist green, the folder moves to .session/.archive/ and a summary stays in persistent memory so it can be found later.

05 · flow A

Initial seed: from the PRD to the first backlog

It runs once, when there is a fresh PRD and SRS and zero issues in Jira. It goes epic by epic to keep the context contained.

Confirm the project key

It comes from .agents/project.yaml. If it is missing or malformed, the AI stops: it never guesses a key.

Draft the epic tree, writing nothing

Epics with their foundational stories, priority and provisional order. It is a working draft so that you can spot extra or missing epics before spending ticket numbers.

For each epic: create, transition, sync

It creates the epic and moves it to its default status ({{jira.statuses.epic_default}}, Planning if the slug is not there). It creates the child stories, validated with INVEST, and moves them to {{jira.statuses.story_default}} (Shift-Left QA by default). After that, bun run jira:sync-issues pull --epic.

Scope overlap check

It compares the scope of sibling stories. If two share a literal bullet, it raises an overlap_alert and does not fix it on its own: you choose to move the bullet, extract a shared story or accept the duplicate with its reason.

Dependencies and execution order

With everything created, it runs dependency discovery, publishes the links in Jira and closes with sequencing (see §11).

The AI does

Reads the PRD, personas, journeys and functional specs; builds the draft; creates in Jira.

You decide

You approve the tree, resolve each overlap and confirm the dependency matrix.

Output

Issues in Jira, the cache in .context/PBI/ and .context/dev-roadmap.md §4.

06 · flow B

New feature: measure first, create after

A request from the PO, an opportunity, customer feedback. Before creating anything, the AI classifies the idea into one of three levels. The classification decides the path.

Level 1

One story

It extends something that exists, fits in a current epic, asks for no architecture changes. The story is created under that epic.

Level 2

A whole epic

A new capability that fits in no epic, with a bounded scope and between 3 and 8 stories. The epic is created with its children, links, overlap check and sequencing.

Level 3 · stop

Several epics

Two or more epics, complex dependencies, architecture changes. Nothing is created: a split plan comes out. Once the plan is approved, level 2 runs one epic at a time. With nobody present, the plan goes into the run report and stops there.

Don't force the level. If the analysis says "level 3", insisting on creating everything at once saturates the context and leaves dependencies badly resolved. Work incrementally.

Open questions before creating. When there are questions that decide the scope, the AI calls the grilling skill: it interrogates you in numbered rounds, each question with its recommended answer. If the skill is not installed, it asks the same questions as a numbered list and says so in the report. If you already decided everything in the conversation, the AI writes a spec from that and does not ask again.
07 · flow C

An epic is a module, not a task list

It groups related stories under one parent, tells the "why" of the capability and measures progress at feature scale. If it can't be described in two sentences, it is two epics.

Healthy size

Signs it is well cut

  • Between 3 and 8 stories. Fewer is a story; more, it needs splitting.
  • 2 to 4 sprints long.
  • A single team. Multi-team epics get split.
  • Title as a noun, no pipe or verb: Tenancy & Identity.
Epic or feature flag?

They are not alternatives

  • Flag: turning something that already exists on or off, dark launch, instant rollback.
  • Epic: a new capability with several stories, metrics and a place in the roadmap.
  • A flag is an implementation tactic; an epic, a product container.
An epic's criteria are outcomes: "the person completes the capability end to end without leaving the product", "all its stories are in Done". The Gherkin scenarios live in each story, never in the epic.
An epic too big to plan. A map of decision tickets is drawn (children of the epic, one session each) after interrogating with grilling and domain-modeling. Each ticket is for research (research), for questions to a person, or is a small task. With nobody present this section does not run: the gap is noted in the report.
08 · before every write to Jira

A title that reads on the board, and a pre-check

A story's title is not the "As a… I want… so that…" sentence. That sentence is too long for a card and buries the action. It goes in the description; the title uses another format.

Authentication | Sign up and sign in via OAuth (GitHub / Google)

{Feature} | {Action} · in English · no persona or benefit

As a visitor, I want to sign in via OAuth so that I can access the app

this goes in the description, "User story" section, never in the title

Title rules

Short feature, action as a base verb

  • {Feature}: 1 to 3 words; sibling stories of the same feature share it.
  • {Action}: the "I want to…" as a base verb, with no persona and no "so that".
  • No spec prefixes (FR-…): the spec goes as the first line of the description, **Source spec:** FR-XXX.
  • If the product is itself a management tool, the entity that clashes with agile vocabulary carries the prefix TMS- (TMS-Run Execution).
Pre-check, mandatory

If something fails, it gets fixed before publishing

  • A real persona from the personas file, never "the user" or "the system".
  • Business voice: no endpoints, HTTP codes, tables, libraries or algorithms.
  • Criteria in ```gherkin blocks.
  • Effort and tokens empty: QA sets the AI Effort and the agents measure the tokens.
  • No duplicating criteria or scope in the description, no inventing content, and the domain glossary terms.
The voice test: if a criterion is still true after changing the whole stack, it is in business voice. If it breaks when the stack changes, it is implementation and goes in the plan that /sprint-development builds. The exception: when the persona consumes an API, the endpoints are what they observe.
09 · flow D

From "it exists in Jira" to "anyone can pick it up"

A good story fits in a sprint, is in the persona's voice and leaves no doubt about what "done" is. If two devs read it and imagine different things, it isn't refined.

INVEST The question If it fails
Independent Can it be completed without depending on other stories? Resequence, or extract the shared dependency into its own story.
Negotiable Is there flexibility in how it is implemented? Take implementation detail out of the description.
Valuable Is the "so that…" a clear benefit? Talk to product; with no value, it doesn't get built.
Estimable Could the team size it with what is there? A time-boxed spike, then refine again.
Small Does it fit in a sprint? Split it into vertical slices.
Testable Are the scenarios clear and measurable? Rewrite in Gherkin: at least one happy path, one error and one edge.
Cutting well

Vertical slices, not layers

  • Vertical: each slice delivers a visible result on its own ("pay with a saved card", "add a new card", "clear errors on rejection").
  • Horizontal (antipattern): "database, then API, then UI". Nothing can be shown until the end.
  • Other ways: by workflow step, by data variation, by interface or by role.
3 amigos · optional

Product, dev and QA, before the sprint

  • Worth it if the story is big, touches integrations, is a flow with no precedent, has ambiguity or depends on another team.
  • Thirty to forty-five minutes: read the story, walk the happy path, surface unknowns and edges, decide scope, confirm Ready.
  • If anything is left unchecked, another one is scheduled; it is not marked Ready.
Gate: INVEST and the voice test pass, the criteria are in Gherkin, the dependencies are published as links in Jira, and the story is transitioned to {{jira.statuses.story_default}}. That status change tells the team it passed the Ready check.
10 · flows E and F

Criteria that can be verified, and edges that don't get lost

A criterion without a concrete "given", "when" and "then" is not a criterion: it is a wish. The goal is to remove every "it depends" before the story enters the sprint.

Scenario: User cannot create a note with empty title Given I am on the new-note form When I submit the form with an empty title Then I see the error "Title is required" And no note is created

an error scenario, in its gherkin block, with concrete text

Flow E · when editing existing criteria

The voice check first

  • Reads the field with bun run jira:sync-issues get, never with acli view.
  • Looks for implementation, scenarios without a gherkin block and generic personas.
  • If it finds something, it rewrites the whole field and shows you the before and after before publishing.
  • Each "then" is something the persona sees: a message, an element, a state.
10b · flow F

Edge cases: find them and decide

Where to look

Five families

  • Limits: empty, maximum, one too many, odd characters.
  • Errors: network, database, external service, permissions.
  • Concurrency: two people editing, double click, stale state.
  • Performance: high volume, slow network, third-party limits.
  • Persona: role, language, device, accessibility.
The decision rule

Criterion or test?

  • High criticality (money, data, security, a critical journey) and clear behavior: becomes an acceptance criterion.
  • If not: it stays as a testing matter, for QA.
  • Medium criticality with very clear behavior: at the PO's discretion.
  • What is deferred is documented with its reason; it is not lost silently.
11 · dependencies and flow H

What do we start first?

The order comes from the Jira link graph, not from a hunch. That is why, before ordering, you have to discover the real dependencies and publish them.

Active dependency discovery

Before creating or editing a story, the AI builds a matrix (from, to, source) by reading the epic tree, the links that already exist and the data map. Valid sources: the PRD or SRS order, the master plan, the relationships between entities and what a person declared.

Filter the noise

"It needs login to exist" or "it needs the database" is a property of the project, not a dependency between two stories. The test: if the dependency disappears when sprints are reordered, it was noise.

You confirm, then it is published

The filtered matrix is shown to you before a single link is written. Each link is created one at a time and re-read to verify the direction: "A depends on B" has to read that way from A.

If the workspace does not have the dependency link type, the relates fallback loses the direction: the AI tells you so, in plain words.

With the links published, flow H does a topological order: what waits for nobody goes to Execution Sprint 1; what only waits for 1, to 2; and so on until the graph is empty.

illustrative example · only dependency and blocking links count

Two different sprints

Master Sprint and Execution Sprint

  • Master Sprint: strategic roadmap grouping, in .context/master-implementation-plan.md. It rarely changes.
  • Execution Sprint: operational batch that comes out of the topological order. It is recalculated every time stories or links change.
Where it lives and what it is worth

An input for planning

  • The skill delegates the writing to /project-context dev-roadmap, which regenerates §4 of .context/dev-roadmap.md without touching the hand-written sections.
  • It is an input for the planning meeting (capacity, priorities, other teams), not a commitment.
A cycle is a bug. If A depends on B and B on A, the ordering stops and the AI shows you the trapped stories. Which link to remove is a product decision: a person makes it, never the AI.

13 · stories with an interface

It doesn't wait for the mockup, but it leaves the row

A story is written, refined and left ready without any screen having been drawn. It is not postponed, not blocked and not downgraded because of that.

What it must do

Its row in the Story → Screen map

.context/design/master-design-plan.md · §8
  • If the project has a master design plan, each story with an interface is born with a line in §8.
  • The line names the screen where it renders, or says explicitly that there is no mockup covering it yet: 🔒 mockup-gated.
  • It is cheap, and it is what the design gate reads later on.
What it is not

Writing the row is not designing

  • The row is not a mockup.
  • When /sprint-development picks up the story, its design gate reads the row and resolves the screen's route at that moment.
  • A UI story created without a row reaches development already outside the repo's fidelity rule.
14 · safety rails

What the skill never does

The full invariants live in the compact rules of SKILL.md (the body no longer repeats the list). These are the ones a PM notices first.

Doesn't invent. A criterion, scope or business rule with no source (PRD, SRS, business map or what you said) is reported as a gap, that field is held back and it carries on with the rest.
Doesn't size for you. QA sets the AI Effort in shift-left and the agents measure the tokens. If QA marks High, it proposes splitting the story and you sign off.
Doesn't create links without your confirmation, nor use a symmetric link for something that depends on order without telling you.
Doesn't resolve overlaps or cycles on its own. It shows you the problem and waits for your decision.
Doesn't write the cache by hand nor hardcode field IDs, link names or tool commands: everything is resolved by slug or by the owning skill.
Doesn't say "Wave". It says Sprint, and Master Sprint or Execution Sprint when there is ambiguity.
Optional, for teams that need it: the delta specs pattern replaces the in-place editing of criteria with one source spec per feature plus one delta per story (added, modified, removed). It helps with several devs on the same feature or with audit; for small teams, the default flow is enough.
