00 · from specification to repo

A repo that starts up before the first story.

/project-bootstrap takes what /project-foundation left behind (PRD, SRS) plus DESIGN.md, and builds the technical base: backend with database, auth and types, frontend with the design system, and whatever integration pieces the project asks for. It runs once per project; after that, every story builds on top.

01 · when to use it

After the product is defined, before the first story

/project-foundation answers what gets built. This skill answers how the repo is set up so building can start.

Use it when

There is a specification and no code

  • A new repo already has its foundation (/project-foundation ran) but has no code yet.
  • An existing repo needs one more piece of infrastructure: "add OpenAPI to the API", "add bearer token auth", "connect the Supabase types to the frontend". Only the incremental pieces: the base does not run on top of an app that already exists (§01·b).
Do not use it for

What belongs to another skill

  • Defining the product (PRD, journeys, architecture decisions): that is /project-foundation.
  • Seeding the backlog in Jira: that is /product-management.
  • Implementing a story end to end: that is /sprint-development.
  • Unit tests and their framework: that is /unit-testing.
Before starting: the backend stack, the frontend stack and the database engine are read from .agents/project.yaml. If those values are empty, the skill sends you to /project-foundation first, because the infrastructure decisions come out of the SRS architecture.
01·b · greenfield only for the base

The base does not run on top of an app that already exists

The base phases (backend and frontend) create: tables, RLS, seeds, clients, middleware, layout, theme, the Tailwind config, pages and demo credentials. On a live app, each of those steps would overwrite something. That is why a script gives the verdict, never the AI looking at the tree: a gate the agent can satisfy by writing a believable value is not a gate. 

# on entry, before the session plan; the verdict and the exit code go to plan.md
bun run bootstrap:guard   # exit 0 = greenfield · exit 2 = existing app (with the signals) · --json
exit 0 · greenfield

Everything runs as written

  • The base phases and the incremental pieces.
  • A resumed run keeps the verdict its plan recorded: by then, what the guard would see is the skill's own output.
exit 2 · existing app

The base is refused

  • Any one signal is enough: the adoption lock, a package.json that declares next or react, or app files (routes, middleware, Tailwind config, components.json, migrations).
  • The AI cites the signals, names what it would have overwritten and sends you to /project-adoption (and to /design-system extract if the request was about how the UI looks).
  • The incremental pieces stay available and read the stack: block.
Fail-closed. With no recorded verdict, or an unreadable one, the base does not run. Saying "this is greenfield" does not unlock it: the fix for a wrong reading is to remove the signal the script cited and run it again. Deck for the other door: Project adoption.

03 · what it reads

What it reads, in this order

This is the canonical order for an AI starting cold. Each one feeds a different scaffolding decision.

.context/PRD/

The feature inventory and the MVP scope: they decide what gets built.

.context/SRS/

The infrastructure decisions: database, hosting, auth provider, runtime. The database schema comes from the architecture ERD.

DESIGN.md at the root

Palette, typography and tokens. It is a mandatory input for the frontend: it has to exist before phase 2.

.agents/project.yaml

Project identity, backend and frontend stack, database engine and the URLs of each environment.

What already exists in app/, lib/, db/

If there is earlier scaffolding, it is detected and patched in place. Anything someone already edited is never overwritten.

04 · phases 0 and 0.5

First it checks for half-finished work, then it writes the plan

Both run in the main thread, with no subagents, even the first time: that way "resume or start over" is always an explicit decision.

The AI does

Looks for .session/project-bootstrap/progress.md. If it exists, it reads the plan and the latest entries and shows you the goal, the last closed phase and the next one.

If it does not exist, it drafts plan.md: goal, inputs, approach, phases, risks and verification checklist.

You decide

With a previous session: resume, restart (the earlier one is archived) or abort (nothing is touched).

With a new plan: which incremental pieces get added on top of the base. Without your approval, phase 1 does not start.

Output

.session/project-bootstrap/plan.md in draft state, which becomes approved when you approve it.

Every phase that finishes leaves an entry in progress.md: if the session is cut off, it resumes from there.

Gate plan approved, with the incremental pieces chosen.
05 · phase 1

Backend: the base every story reuses

It sets up the database, auth and the access layer, and fixes the conventions every future endpoint will follow. It is done once, before the sprints.

The AI does

Checks the git state and the tools. Without the Supabase MCP everything stops: it creates tables and policies through it, not with hand-written SQL scripts.

Creates the foundational tables (not the whole ERD), indexes, RLS per table and realistic seed data. Builds the Supabase clients, the session middleware and the centralized configuration. Reads the official documentation before installing each dependency.

You decide

The Supabase project: an existing one (you give its ID) or a new one.

How environment files are handled: the AI does not create a .env without asking you. You make the commits.

Output

Tables with RLS in the database, clients in src/lib/supabase/, configuration in src/lib/config.ts, generated types in src/types/supabase.ts.

Documentation in .context/backend-setup.md and .context/api-auth.md.

Gate types generated from the live schema, TypeScript with no errors and a full build passing.
Layers that do not collapse

api/ · schemas/ · db/

  • The boundaries between layers are framework architecture, not speculative abstraction: the simplicity rule in AGENTS.md exempts them on purpose.
  • api/schemas/ are the OpenAPI type facades: a single source of truth per domain.
  • Later, in review, a layer violation is a citable finding: /pr-review-lead checks them against this doctrine.
Secrets and configuration

Two places, never the code

  • Credentials in .env; non-secret configuration in .agents/project.yaml.
  • .env.example is not rewritten: it is in parity with cli/lib/variables-manifest.ts. A new variable goes in both, in the same commit.
  • Variables are validated at startup with a schema (Zod or equivalent).
06 · phase 2

Frontend: the design system comes from DESIGN.md

It sets up the project, the design system, the layout and a few demo pages that prove everything fits together. It does not implement features: that is left to each story.

The AI does

First of all, it confirms the backend exists: it reads src/types/supabase.ts and the Supabase clients, and stops if they are missing. With them it builds type helpers for the components.

Maps the DESIGN.md tokens to the Tailwind configuration and to CSS variables without asking you about colors: the file is already the source. Sets up the project in the current directory, with no generators that create subfolders.

You decide

The package manager.

The component strategy: shadcn/ui, components from scratch or Headless UI with custom styles. That question stays open even when DESIGN.md exists.

Which demo pages get built (two or three, the most representative of the domain).

Output

Components in src/components/ui/, layout in src/components/layout/, demo pages, global styles.

.context/design-system.md documents palette, components and usage.

Gate passing build and visual review: with /playwright-cli in a named session, or you do it with the server running.
No DESIGN.md, no phase 2. The design tokens are the frontend's entry contract. If the file does not exist, run /design-system first and then come back here. The default path is the repo root; a project with a different structure declares it in .agents/project.yaml.
06·b · the Baseline target

During the frontend analysis the AI asks one more question, after layout and priority components: which Baseline level should the UI code hold to.

Option What it means
Baseline Widely available (recommended) Features every major browser has shipped for roughly 30 months. Right unless the product needs newer ones.
Baseline <year> Admits features that became Baseline Newly available up to that year. Fits a product with a known modern-browser audience.
Choose for me It uses Baseline Widely available.
Where the answer lands: one line under a ## Web platform heading in .agents/instructions/agent-project.md: This project's Baseline target is Baseline Widely available. That file belongs to the project, so bun sync keeps it. modern-web-guidance reads the line before its first search; without it, it assumes Baseline Widely available.
Volatile features stay off. Features that are not Baseline yet are gated by default. Enabling them with npx modern-web-guidance@latest set-allow-volatile-features is a person's call; the AI never runs it.
07 · phase 3

Incremental pieces: you choose, not everything gets installed

Each piece adds a capability on top of the base. They are independent of each other and each one runs in its own subagent. Before writing, each one looks at what is in the repo and decides its scope: full if there are already endpoints or earlier structure, partial if the ground is empty.

Piece What it adds Where it lands Requires
OpenAPI Spec generated from Zod schemas at /api/openapi and the Scalar UI at /api/docs. The schema is defined once, next to the type: the documentation is not duplicated. src/lib/openapi/ base backend
API routes Folders per domain, Zod validation, standardized errors and an example endpoint; with OpenAPI present, the SRS endpoints are registered in the spec. src/app/api/ base backend
Bearer token Auth through the Authorization header for Postman, curl or external apps, without breaking the browser's cookie auth. src/lib/supabase/server.ts and the protected routes base backend
Per-environment URLs A helper that detects the environment (development, staging, production) and builds the correct base URL. It asks you for the staging and production URLs. src/lib/urls.ts base backend
Supabase types The schema → TypeScript pipeline, a regeneration script in package.json and clients typed with Database. src/types/supabase.ts base frontend
OpenAPI always with its UIThe spec without the Scalar route at /api/docs is not delivered: the contract has to be browsable from day one. No Redoc or Swagger in its place.
Bearer token never half-doneToken auth ships together with rate limiting and a secret rotation guide. Without those two, the feature is incomplete.
Types that follow the live schemaIf the database schema changes, the types are regenerated and TypeScript flags where to adjust. Skipping the generation leaves silent drift.
08 · closing each phase

Verify at the destination, then archive

Each phase closes with the lightweight stage verifier and the session ends with the footer of tools used. A check that fails is reported as it is: no invented fixes for an unknown stack, the AI asks you.

Build passes. The build of the chosen stack finishes without errors.
Server up. The frontend home and the backend health route respond.
TypeScript compiles with no errors across the whole repo.
Variables documented. Every new variable appears in .env.example.
Generated artifacts committed (OpenAPI spec, Supabase types). The skill recommends the commit; you do it or /git-flow-master.
With the plan checklist green, the folder .session/project-bootstrap/ moves to .session/.archive/ and a summary is left in persistent memory with the file path, so it can be found later.
09 · safety rails

What the skill never does

The full rules live in the frontmatter of SKILL.md (compact_rules) and travel in the compact registry the subagents receive (.agents/skills/REGISTRY.md).

Does not overwrite existing scaffolding. It detects what is there and patches in place, preserving what you edited.
Does not hardcode credentials, URLs or environment values in the generated code.
Does not skip variable validation at startup: a silently missing variable blows up in production, far from the cause.
Does not collapse the layers of the backend or the structure of the design system in the frontend.
Does not start the frontend without DESIGN.md, nor the database without generating its types.
Does not continue without the official documentation when it needs it: if no library documentation tool is available, it stops and tells you which one is missing, with no silent substitute.
Does not write the database layer or the UI layer without their stack skills loaded: supabase and supabase-postgres-best-practices before installing, touching the schema, RLS or migrations through the MCP, or generating types; the design set (frontend-design, ui-ux-pro-max, impeccable, emil-design-eng, modern-web-guidance) plus shadcn and tailwind-css-patterns before the component strategy. If they are not installed it says so once, points to bun setup and carries on; it never skips this silently.
Does not change the database outside the change doctrine. Everything goes through the database MCP: it reads list_migrations first, DDL goes only through apply_migration, it is verified at the destination and a migration that changes the architecture leaves its ADR.
Ready for features, not for production. Deploy, CI and observability hardening are added later, with other skills, as the product matures.

/testability-guide

To read more: .agents/skills/project-bootstrap/SKILL.md and its references/ folder, one reference per phase and per incremental piece.

The idea behind it. The base is set up once and done well: layers that do not mix, secrets outside the code, types that follow the live schema. The AI sets up and verifies; you choose the Supabase project, the pieces and the components, and make the commits.
