00 · de la especificación al repo

Un repo que arranca antes de la primera historia.

/project-bootstrap toma lo que dejó /project-foundation (PRD, SRS) y el DESIGN.md, y levanta la base técnica: backend con base de datos, auth y tipos, frontend con el design system, y las piezas de integración que el proyecto pida. Corre una vez por proyecto; después, cada historia construye encima.

01 · cuándo usarla

Después de definir el producto, antes de la primera historia

/project-foundation responde qué se construye. Esta skill responde cómo se para el repo para empezar a construirlo.

Usala cuando

Hay especificación y no hay código

  • Un repo nuevo ya tiene su fundación (/project-foundation corrió) pero todavía no tiene código.
  • Un repo existente necesita una pieza de infraestructura más: "agregá OpenAPI a la API", "sumá auth por bearer token", "conectá los tipos de Supabase al frontend". Solo las piezas incrementales: la base no corre sobre una app que ya existe (§01·b).
No la uses para

Lo que pertenece a otra skill

  • Definir el producto (PRD, journeys, decisiones de arquitectura): eso es /project-foundation.
  • Sembrar el backlog en Jira: eso es /product-management.
  • Implementar una historia de punta a punta: eso es /sprint-development.
  • Tests unitarios y su framework: eso es /unit-testing.
Antes de arrancar: el stack del backend, el del frontend y el motor de base de datos se leen de .agents/project.yaml. Si esos valores están vacíos, la skill te manda primero a /project-foundation, porque las decisiones de infraestructura salen de la arquitectura del SRS.
01·b · solo greenfield para la base

La base no corre sobre una app que ya existe

Las fases base (backend y frontend) crean: tablas, RLS, seeds, clientes, middleware, layout, tema, la config de Tailwind, páginas y credenciales de demo. Sobre una app viva, cada uno de esos pasos pisaría algo. Por eso el veredicto lo da un script, nunca la IA mirando el árbol: un gate que el agente puede satisfacer escribiendo un valor creíble no es un gate. 

# al entrar, antes del plan de la sesión; el veredicto y el exit code van a plan.md
bun run bootstrap:guard   # exit 0 = greenfield · exit 2 = app existente (con las señales) · --json
exit 0 · greenfield

Todo corre como está escrito

  • Las fases base y las piezas incrementales.
  • Una corrida retomada conserva el veredicto que registró su plan: para entonces, lo que el guard vería es la propia salida de la skill.
exit 2 · app existente

La base se rechaza

  • Cualquier señal alcanza: el lock de adopción, un package.json que declara next o react, o archivos de app (rutas, middleware, config de Tailwind, components.json, migraciones).
  • La IA cita las señales, nombra qué habría pisado y te manda a /project-adoption (y a /design-system extract si el pedido era sobre cómo se ve la UI).
  • Las piezas incrementales siguen disponibles y leen el bloque stack:.
Fail-closed. Sin veredicto registrado, o con uno ilegible, la base no corre. Decir "esto es greenfield" no lo destraba: el arreglo de una lectura equivocada es quitar la señal que el script citó y volver a correrlo. Deck de la otra puerta: Project adoption.
02 · el mapa

Una base en orden, y piezas que se suman encima

La base (backend y después frontend) se monta siempre y en ese orden. Las piezas incrementales son independientes entre sí: se eligen por necesidad y el resto se salta.

El hilo principal no escribe código. Coordina: cada fase de la base y cada pieza incremental va a su propio subagente, con un briefing de siete componentes que nombra la referencia exacta que tiene que leer. Al entrar, la skill además resuelve qué skills complementarias tenés instaladas para las categorías que declara su frontmatter: las del repo se cargan solas, las de tu usuario te las pregunta una vez.
03 · qué lee

Lo que lee, en este orden

Es el orden canónico para una IA que arranca en frío. Cada una alimenta una decisión distinta del scaffolding.

.context/PRD/

El inventario de features y el alcance del MVP: deciden qué se monta.

.context/SRS/

Las decisiones de infraestructura: base de datos, hosting, proveedor de auth, runtime. El esquema de la base sale del ERD de la arquitectura.

DESIGN.md en la raíz

Paleta, tipografía y tokens. Es la entrada obligatoria del frontend: tiene que existir antes de la fase 2.

.agents/project.yaml

Identidad del proyecto, stack del backend y del frontend, motor de base de datos y las URLs de cada ambiente.

Lo que ya existe en app/, lib/, db/

Si hay scaffolding previo, se detecta y se parchea en el lugar. Nunca se pisa lo que alguien ya editó.

04 · fases 0 y 0.5

Primero se fija si hay trabajo a medias, después escribe el plan

Las dos corren en el hilo principal, sin subagentes, incluso la primera vez: así "retomar o empezar" es siempre una decisión explícita.

La IA hace

Busca .session/project-bootstrap/progress.md. Si existe, lee el plan y las últimas entradas y te muestra el objetivo, la última fase cerrada y la próxima.

Si no existe, redacta plan.md: objetivo, entradas, enfoque, fases, riesgos y checklist de verificación.

Vos decidís

Con sesión previa: retomar, reiniciar (lo anterior se archiva) o abortar (no se toca nada).

Con plan nuevo: qué piezas incrementales se suman sobre la base. Sin tu aprobación, no arranca la fase 1.

Sale

.session/project-bootstrap/plan.md en estado draft, que pasa a approved cuando lo aprobás.

Cada fase que termina deja una entrada en progress.md: si la sesión se corta, se retoma desde ahí.

Gate plan aprobado, con las piezas incrementales elegidas.
05 · fase 1

Backend: la base que reusan todas las historias

Levanta la base de datos, la auth y la capa de acceso, y fija las convenciones que va a seguir cada endpoint futuro. Se hace una sola vez, antes de los sprints.

La IA hace

Verifica el estado de git y las herramientas. Sin el MCP de Supabase se detiene todo: crea tablas y políticas con él, no con scripts SQL a mano.

Crea las tablas fundacionales (no el ERD entero), índices, RLS por tabla y datos semilla realistas. Arma los clientes de Supabase, el middleware de sesión y la configuración centralizada. Consulta la documentación oficial antes de instalar cada dependencia.

Vos decidís

El proyecto de Supabase: uno existente (das su ID) o uno nuevo.

Cómo se manejan los archivos de entorno: la IA no crea un .env sin consultarte. Los commits los hacés vos.

Sale

Tablas con RLS en la base, clientes en src/lib/supabase/, configuración en src/lib/config.ts, tipos generados en src/types/supabase.ts.

Documentación en .context/backend-setup.md y .context/api-auth.md.

Gate tipos generados del esquema vivo, TypeScript sin errores y build completo en verde.
Capas que no se colapsan

api/ · schemas/ · db/

  • Los límites entre capas son arquitectura del framework, no abstracción especulativa: la regla de simplicidad de AGENTS.md los exime a propósito.
  • api/schemas/ son las fachadas de tipos de OpenAPI: una sola fuente de verdad por dominio.
  • Después, en review, una violación de capa es un hallazgo citable: /pr-review-lead las revisa contra esta doctrina.
Secretos y configuración

Dos lugares, nunca el código

  • Credenciales en .env; configuración no secreta en .agents/project.yaml.
  • .env.example no se reescribe: está en paridad con cli/lib/variables-manifest.ts. Una variable nueva va en los dos, en el mismo commit.
  • Las variables se validan al arrancar con un esquema (Zod o equivalente).
06 · fase 2

Frontend: el design system sale de DESIGN.md

Monta el proyecto, el design system, el layout y unas pocas páginas demo que prueban que todo encaja. No implementa features: eso queda para cada historia.

La IA hace

Antes de nada, confirma que el backend existe: lee src/types/supabase.ts y los clientes de Supabase, y se detiene si faltan. Con ellos arma helpers de tipos para los componentes.

Mapea los tokens de DESIGN.md a la configuración de Tailwind y a variables CSS sin preguntarte colores: el archivo ya es la fuente. Monta el proyecto en el directorio actual, sin generadores que crean subcarpetas.

Vos decidís

El package manager.

La estrategia de componentes: shadcn/ui, componentes desde cero o Headless UI con estilos propios. Esa pregunta sigue en pie aunque haya DESIGN.md.

Qué páginas demo se construyen (dos o tres, las más representativas del dominio).

Sale

Componentes en src/components/ui/, layout en src/components/layout/, páginas demo, estilos globales.

.context/design-system.md documenta paleta, componentes y uso.

Gate build en verde y revisión visual: con /playwright-cli en una sesión con nombre, o la hacés vos con el servidor corriendo.
Sin DESIGN.md, no hay fase 2. Los tokens de diseño son el contrato de entrada del frontend. Si el archivo no existe, primero se corre /design-system y después se vuelve acá. La ruta por defecto es la raíz del repo; un proyecto con otra estructura la declara en .agents/project.yaml.
07 · fase 3

Piezas incrementales: se elige, no se instala todo

Cada pieza suma una capacidad sobre la base. Son independientes entre sí y cada una corre en su propio subagente. Antes de escribir, cada una mira qué hay en el repo y decide su alcance: completo si ya hay endpoints o estructura previa, parcial si el terreno está vacío.

Pieza Qué agrega Dónde queda Requiere
OpenAPI Spec generada desde schemas Zod en /api/openapi y la UI de Scalar en /api/docs. El schema se define una vez, junto al tipo: la documentación no se duplica. src/lib/openapi/ backend base
Rutas de API Carpetas por dominio, validación con Zod, errores estandarizados y un endpoint de ejemplo; con OpenAPI presente, los endpoints del SRS quedan registrados en la spec. src/app/api/ backend base
Bearer token Auth por header Authorization para Postman, curl o apps externas, sin romper la auth por cookies del navegador. src/lib/supabase/server.ts y las rutas protegidas backend base
URLs por ambiente Un helper que detecta el ambiente (development, staging, production) y arma la URL base correcta. Te pregunta las URLs de staging y producción. src/lib/urls.ts backend base
Tipos de Supabase El pipeline esquema → TypeScript, un script de regeneración en package.json y los clientes tipados con Database. src/types/supabase.ts frontend base
OpenAPI siempre con su UILa spec sin la ruta de Scalar en /api/docs no se entrega: el contrato tiene que poder recorrerse desde el primer día. Ni Redoc ni Swagger en su lugar.
Bearer token nunca a mediasLa auth por token viaja junto con rate limiting y una guía de rotación del secreto. Sin esas dos, la feature está incompleta.
Tipos que siguen al esquema vivoSi el esquema de la base cambia, se regeneran los tipos y TypeScript marca dónde ajustar. Saltarse la generación deja una deriva silenciosa.
08 · cierre de cada fase

Verificar en el destino, después archivar

Cada fase cierra con el verificador liviano de etapa y la sesión termina con el pie de herramientas usadas. Un chequeo que falla se reporta tal cual: nada de arreglos inventados para un stack desconocido, la IA te pregunta.

Build en verde. El build del stack elegido termina sin error.
Servidor arriba. Responde la home del frontend y la ruta de salud del backend.
TypeScript compila sin errores en todo el repo.
Variables documentadas. Cada variable nueva figura en .env.example.
Artefactos generados commiteados (spec de OpenAPI, tipos de Supabase). La skill recomienda el commit; lo hacés vos o /git-flow-master.
Con el checklist del plan en verde, la carpeta .session/project-bootstrap/ se mueve a .session/.archive/ y queda un resumen en la memoria persistente con la ruta del archivo, para encontrarlo después.
09 · rieles de seguridad

Lo que la skill nunca hace

Los antipatrones completos viven en SKILL.md y viajan en el registro compacto que reciben los subagentes (.agents/skills/REGISTRY.md).

No pisa scaffolding existente. Detecta lo que hay y parchea en el lugar, preservando lo que editaste.
No hardcodea credenciales, URLs ni valores de un ambiente en el código generado.
No se saltea la validación de variables al arrancar: una variable faltante silenciosa explota en producción, lejos de la causa.
No colapsa las capas del backend ni la estructura del design system en el frontend.
No arranca el frontend sin DESIGN.md, ni la base de datos sin generar sus tipos.
No sigue sin la documentación oficial cuando la necesita: si no hay herramienta de documentación de librerías disponible, se detiene y te dice cuál falta, sin un sustituto silencioso.
Sale listo para features, no para producción. Deploy, CI y endurecimiento de observabilidad se suman después, con otras skills, a medida que el producto madura.
