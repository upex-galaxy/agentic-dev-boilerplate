GUARD: Guarded Unidirectional Agent-Ready Development

An agent writes code that looks like the code already there. When the repo has a clear shape and a machine watching it, the agent copies the shape well; when there are only rules in prose, it copies them badly and nobody notices. GUARD is the architecture this boilerplate teaches and checks: four layers, one direction, one door per feature, a registry, and lint before prose.

01The problem: the agent copies what it sees

The principles for product code (a folder per feature, aliases, at most two positional parameters) lived in prose and a reviewer upheld them. That fails two ways: the agent has no shape to copy and no registry to read before it creates something, and no machine tells it when it breaks a layer rule.

No shape

Every feature is born different

The agent imitates the first file it opened. If that file mixes data, rules and screen, the next one will too.

No control

A prose rule does not run

Nobody runs it on every commit. It surfaces in review, late and by hand, and the same finding comes back in the next PR.

The way out

Give it a shape and a check

A real example to copy, a registry to read before creating, and lint that names the broken rule and the root-cause fix.

02Where it comes from

GUARD was not invented from scratch. It combines three sources, and the full decision is in ADR-0023.

KATA

The QA repo already solved this

For test code, the QA boilerplate has layers, a generated manifest and a single entry point. KATA names test concepts (ATCs, fixtures, components) that have no product equivalent, so it does not apply as is: we reuse the idea and change the vocabulary.

Lauren Tan

"All Code Is Slop (Except Mine)"

The trust pyramid says you trust what a machine verifies. Every correction becomes a check. One folder per feature with import bans. No comments.

Matt Pocock

codebase-design

The interface is what you test: a module is tested through its public door, not through its internal files.

03The four layers

Dependencies point down. A layer imports only from the ones below it, and a feature is reached only through its index.ts. 

L4  app        src/app/                  composition only: read params, call actions, render
      |
      v   (through the door)
L3  features   src/features/<name>/     actions, domain, UI, types
      |   door: index.ts
      v
L2  adapters   src/adapters/            Supabase, external APIs, anything outside
      |
      v
L1  platform   src/platform/            config, env, DB client, utilities
Layer May import
app features (through their door) and platform
features adapters, platform, and another feature only through its index.ts
adapters platform
platform nothing above it
Aliases
Use the aliases the app's tsconfig.json declares (@platform/*, @adapters/*, @features/* and @/*) and no deep relative import.

04Rules R1 to R6 and what enforces each

Every rule has a concrete check that enforces it. Every lint message names the rule and the root-cause fix: move the code to the right layer or open the feature's door.

Rule Statement Enforced by
R1 one direction A lower layer never imports a higher one guard/layer-imports
R2 one door Outside features/x/ you import @features/x, never a deep path guard/feature-door
R3 thin app src/app/** never imports @adapters/*; data goes through a feature guard/layer-imports
R4 registry guard-manifest.json lists every feature and what its index.ts exports; read it before creating bun run guard:manifest:check and the pre-commit
R5 shape At most two positional params; files stay under the line limit max-params and max-lines
R6 no comments Toolchain directives and a one-line WHY only Critical Rule 18
Last resort
A lint-disable comment exists, but it carries its reason: eslint-disable-next-line <rule> -- <reason>. Move the code first.

05A story, end to end

This is how an agent walks through a user story when GUARD is in play.

  1. Read the manifest first. Before creating a feature or an action, look at what exists and what it exports. guard-manifest.json
  2. Place the code by layer. External data goes to adapters, business rules to the feature, the screen to app.
  3. Copy the example. The notes feature is the mold.
  4. Lint and manifest at commit. The pre-commit runs the rules and refreshes the registry. bun run lint:check && bun run guard:manifest:check
  5. Unit test through the door. Test what the feature exports, not its internal files.
  6. Live check. Check the real behavior, not only that it compiles.
  7. Human review judges what a machine cannot. Naming, intent, product.
  8. A repeated finding becomes a rule. If the same review comment shows up again, write a check (lint or manifest) and leave prose for what cannot be automated.

06The example feature

packages/guard-example/ is a minimal feature, notes, that passes every rule. The installer inserts it into src/ of a new project on first install and the updater never ships it. Three real excerpts:

The door

features/notes/index.ts

export { createNote, listNotes } from './actions';
export { NoteList } from './NoteList';
export type { NewNote, Note } from './types';

The only thing the rest of the repo may import.

An action

features/notes/actions.ts

export async function createNote(input: NewNote, repo: NotesRepository = notesRepository): Promise<Result<Note>> {
  const valid = validateNewNote(input);
  if (!valid.ok) { return valid; }
  return ok(await repo.insert(valid.value));
}

Validates with the domain and stores through the adapter. Two params, no comments.

The page

app/notes/page.tsx

import { listNotes, NoteList } from '@features/notes';

export default async function NotesPage() {
  return <NoteList notes={await listNotes()} />;
}

Composition only: no adapters, no business rules.

Verify
This repo checks it so it does not go stale: bun run guard:example:check (lint, types, manifest and tests).

07Adopting GUARD in an existing app

An adopted app keeps its folders. The plugin reads the layer map from ESLint settings.guard.layers, one glob list per layer, and uses the defaults when it is absent. An app with db/, api/ and lib/ maps them there and moves no file. 

// eslint.config.js
{ settings: { guard: { layers: { adapters: ['db/**'], platform: ['lib/**'] } } } }
Order
Warn first. The mapping is a step of the project-adoption skill. Warnings are pending work that you sort layer by layer without breaking CI.

08The bridge to QA

09Severity: warn first, then error

GUARD_ENFORCEMENT_LEVEL sets the level of every GUARD check and scripts/guard-manifest.ts mirrors it. The rollout takes two steps: first warn and, in a later release, error. The current value is in those two files. A check at warn never fails CI, so a warning is work owed, not noise.

Heads up
The flip to error is a release of its own. Projects that run bun sync get new warnings until then.
