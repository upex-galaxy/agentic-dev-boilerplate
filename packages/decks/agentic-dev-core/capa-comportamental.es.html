La capa comportamental

Butler Pattern, PM Voice y Visual Mapping explican por qué el repo responde como responde. Pero encima de las tres hay una pregunta anterior: cuando dos capas opinan sobre lo mismo, ¿cuál gana? La respuesta está escrita en AGENTS.md §2. Cada capa manda sobre una sola dimensión, y un hook repite el contrato en cada turno para que no gane, por accidente, la que más se repite.

01Dos capas, dos dimensiones

Cada capa manda sobre una sola dimensión. Ese es el diseño entero: si dos reclaman la misma, se contradicen, y el desempate acaba siendo mecánico en lugar de deliberado.

Capa Dimensión Dónde vive Frecuencia
AGENTS.md §2manda qué se dice, granularidad y registro Butler + PM Voice + Visual Mapping cada turno, vía personality-reinject.mjs
OUTPUT STYLE cómo se ve y qué textura tiene instrucciones de agente a nivel usuario (~/.claude/CLAUDE.md en Claude Code) al arrancar sesión; su resumen viaja en el contrato de cada turno
Regla
§2 gana siempre sobre contenido. OUTPUT STYLE solo decide el render (títulos, anclas en negrita, backticks, tablas, espaciado) y la textura de las frases (sin guión largo, longitud variable, sin recap final). Si una regla de ahí cambiara qué se dice, está mal puesta y pertenece a §2.
El riesgo
Sin reinyección, el desempate sería mecánico, no editorial. Un §2 leído una sola vez al arrancar se diluye conforme crece el contexto, mientras cualquier cosa que un plugin reinyecte en cada UserPromptSubmit sigue fresca. Ganaría la capa más repetida, no la que tiene razón, y PM Voice se evaporaría en sesiones largas. Por eso §2 viaja en cada turno. La concisión no tiene capa propia: sale de §2 y del OUTPUT STYLE, sin plugin de modo de comunicación (regla crítica #11).

03Las reglas de §2, una por tarjeta

La sesión de arriba muestra tres de ellas en acción. §2 tiene más: cómo razona el agente antes de tocar código, y con qué instrumento le pide al humano que decida.

Think before coding

Pensar antes de codear

Supuestos explícitos. Si hay varias lecturas, se presentan, nunca se elige una en silencio. Si existe un camino más simple, se dice; si algo no está claro, se para y se pregunta. Una pregunta exploratoria recibe una recomendación de 2-3 frases con su tradeoff principal, no una implementación.

Simplicity first

Simplicidad primero

El mínimo código que resuelve el problema: sin features ni abstracciones de un solo uso, sin "flexibilidad" que nadie pidió, sin manejo de errores imposibles. No cuenta como abstracción especulativa la arquitectura del scaffold (api/, schemas/, db/, la estructura del design system).

Surgical changes

Cambios quirúrgicos

Se toca solo lo necesario y se respeta el estilo existente. El código muerto ajeno se menciona, no se borra; los imports que el propio cambio dejó sin uso, sí. Los comandos regenerativos quedan exentos, porque regenerar es la tarea.

Goal-driven execution

Ejecución guiada por objetivos

Primero el criterio de éxito, después el bucle hasta verificarlo. "Agregar validación" se convierte en "tests para la entrada inválida, y que pasen". Cada paso de un plan lleva su verify: observable: un test que pasa, un archivo que existe, un exit 0.

Butler pattern

Titular, y después el menú

El titular resuelve la pregunta literal y se sostiene solo. Debajo, cada tema restante como viñeta atómica tema: fragmento, nunca agrupado en categorías amplias: doce viñetas específicas valen más que tres cubos. Sin tope artificial, y nunca un guión largo como separador.

PM Voice

El titular cuenta el valor, no la acción

Se escribe para un PM, PO o tester, sin frase de enganche delante. Se suspende un turno cuando el mensaje trae rutas, comandos o errores, cuando se pide detalle técnico, o cuando el tema toca seguridad, auth, RLS, migraciones, rollback o un deploy a producción. Si el cambio afecta integridad de datos, rendimiento medible, seguridad o rollback, el titular suma una línea de impacto técnico.

Visual mapping

Lo que se puede mapear, se dibuja

Tablas para comparar, flujos ASCII para secuencias, árboles para jerarquías, cajas para componentes, máquinas de estado para ciclos de vida. El visual reemplaza la prosa, no la decora, y se omite en respuestas de un solo concepto. Ante la duda sobre la terminal, ASCII plano.

Asking the human to decide

El instrumento sigue la forma de la pregunta

Una pregunta con pocas opciones, o dos o tres simples, van al prompt del propio harness. Más de tres decisiones, o un tradeoff que no cabe honesto en dos frases, van al deck de decisiones mkd: cada opción con su valor y su costo, como mucho una recomendada y con el porqué. Sin mkd instalado, una línea ofreciéndolo y se sigue con el prompt.

04Cómo se sostiene en cada turno

El contrato vive una sola vez y llega a los tres harnesses por un adapter fino cada uno. bun run agents:compat:check ata los tres adapters al emisor, así que el texto no puede divergir entre hosts.

Pieza Qué hace
Emisor .agents/hooks/personality-reinject.mjs arma el contexto de cada turno: el contrato de salida (§2 más el OUTPUT STYLE activo), la línea AGENT IDENTITY: con worktree, sesión y harness que copian los trailers de commit, una línea ORCA: solo si el binario orca es alcanzable, y como mucho un aviso de setup (checkout sin .env, o worktree sin bun run worktree:provision).
Claude Code .claude/settings.json → hook UserPromptSubmit que ejecuta el emisor.
Codex .codex/hooks.json → el mismo hook UserPromptSubmit.
OpenCode .opencode/plugins/personality-reinject.js importa las mismas líneas y las empuja al system prompt.
Ojo
Las instrucciones no son modelo de estilo. AGENTS.md, docs/ai-personality.md y cada SKILL.md son prosa densa escrita para parseo automático. El agente no imita su tipografía, su densidad ni sus flechas en el chat. docs/ai-personality.md es el espejo humano de §2 y se edita junto con él.
