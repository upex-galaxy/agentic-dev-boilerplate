The backlog is not committed: PBI as a Jira cache

.context/PBI/ mirrors Jira's epics, stories and bugs as local markdown. That mirror is not committed: two sessions that re-sync at different moments would produce conflicting commits of the same generated text. The rule, plainly: Jira is the source of truth, the disk is a cache. This deck explains the three tiers, the .gitignore ladder that protects them, and the defenses that keep the cache from lying.

01The problem: a duplicate database inside git

A committed Jira mirror looks harmless until two sessions work at the same time. Each one re-syncs at its own moment, each one commits its version of the same regenerated file, and a 3-way merge over a full rewrite means nothing: git cannot merge two snapshots of the same database taken minutes apart. Jira already IS the versioned, shared, cloud copy: committing it duplicates the database inside the repo and buys nothing.

Incident
The class of incident this model closes: a stale host. After an Atlassian site migration, an old copy of the URL left in the environment points the sync at the previous workspace. Because the sync OVERWRITES .context/PBI/, an outdated host corrupts the cache with content from another site while reporting success, and with the cache committed that corruption would enter git silently. That is why the host lives only in .agents/project.yaml → issue_tracker.atlassian_url and the resolver (cli/lib/atlassian-instance.ts) warns with both values if an environment copy disagrees.

02The model: three tiers, one question

Every path under .context/PBI/ is exactly one of three tiers. Before creating any file there, you decide the tier: there are no "sort of versioned" files.

Tier Source of truth In git? Recovered with
[SYNC] Jira No (gitignored) bun run context:hydrate
[COMMIT] This repo (README.md + templates/) Yes git checkout
[LOCAL] Nothing durable No Not recovered: disposable by design
The test
Could a PM read it and weigh in? It goes to Jira (field or comment). Does it drive a resume or a workflow between sessions? It goes to .session/sprint-development/<KEY>/progress.md: the resume contract reads that, never the PBI copy. Durable evidence goes to Jira, as an attachment or comment. Neither? It is [LOCAL] (context.md, progress.md, evidence/): it lives only on this machine and losing it must cost nothing. Nothing downstream may depend on a [LOCAL] file existing.
Rule
[SYNC] files are forbidden to write by hand: the sync overwrites them on every run and no file is protected. The flow is always author → push to the Jira field → sync → read the materialized copy.

03The negation ladder in .gitignore

The whole tree is excluded and the two committed exceptions are re-included right after. The exact shape matters: git cannot re-include a file whose parent directory is excluded, so collapsing the ladder into a single .context/PBI/ line silently drops the exceptions. 

# ===== PBI: Jira-backed cache (Jira is the source of truth) =====
.context/PBI/*          ← excludes the CONTENTS (/*), not the directory
!.context/PBI/README.md  ← re-included: [COMMIT] tier rules
!.context/PBI/templates/ ← re-included: [COMMIT] skeletons

.context/PBI/            ← WRONG: excludes the directory and the negations die

Each story's context.md / progress.md / evidence/ are deliberately left un-negated: they are [LOCAL] and stay on the disk of whoever made them.

Verify
Any change to the ladder is checked with git check-ignore -v: on .context/PBI/README.md it must not report an ignore, and on a stories/.../story.md it must. Two commands, zero faith.

04Cold clone and hydration

A fresh clone brings an almost empty .context/PBI/: only the README and templates/. That is the intended state, not a broken checkout. The full cache is rebuilt with one command: 

bun run context:hydrate   # = jira:sync-issues pull --include-comments
  • Requires ATLASSIAN_EMAIL and ATLASSIAN_API_TOKEN in .env; the host comes from .agents/project.yaml → issue_tracker.atlassian_url. bun run jira:check validates the full setup.
  • Whoever has no Jira access cannot hydrate and keeps the cache empty: they can work on framework code and committed docs, but not on per-ticket work. It is a question of Jira permissions, not of the repo.
  • One-off reads go through the same script: bun run jira:sync-issues get PROJ-42 --include-comments fetches ONE issue with all its custom fields (acli view returns null for customfield_*). In bulk: jira:sync-issues jql "<query>"; scoped: pull --epic <KEY> or pull --story <KEY>.

06Defenses of the shared workspace

The same Jira project is shared by the dev side and the sibling QA boilerplate. The sync ships four defenses so that artifacts from one side do not contaminate the other's tree:

QA-Artifact filter

QA process epics, kept out of epics/

An Epic with the QA-Artifact label is a bucket of QA artifacts, not a product module: it is filed under qa-artifacts/. Three signals in order of trust: the label (authoritative), the keys cached in qa.qa_epics.*.key, and the QA  name prefix as a last resort.

Altitude guards

An STP never passes as an ATP

The QA ladder puts ATP: / ATR: / ATS: at Story altitude; FTP: (feature), STP: / STR: (sprint) and MTP: (master) live higher up. A link to an artifact of higher altitude is named in an INFO and never materialized inside the Story folder.

Declarative pull

The scope lives in yaml, not in the script

Which work types pull sweeps is declared by .agents/jira-required.yaml → work_types. Epic, Story and Bug carry sync: default: Epic and Story arrive by walking the epics, Bug has its own sweep. Improvement, Tech Story and Tech Debt are custom types (sync: optional) and are requested with --types; Defects arrive nested under their coverable parent. Types present in Jira that the run will not touch are named, so an empty folder reads as configuration and not as a bug.

Visible orphans

_orphans/ is a work list

A Story with no parent Epic lands in epics/_orphans/ instead of failing. A Test whose only home is internal Xray membership (GraphQL-only, this repo has no Xray client) is left as a visible orphan: the fix is to re-link it in Jira. Defects with no coverable parent are reported with their keys so they can be re-linked.

07What a consumer project lives with

A consumer project may keep tracking [SYNC] files in git. When bun sync runs, a post-apply hook lists what git tracks under .context/PBI/, subtracts the committed allowlist (README.md + templates/**) and, if anything is left, saves a migration recipe for the consumer's AI agent in .agents/prompts/pbi-cache-migration.md (gitignored, single use) and points to it with a row in the final table. The hook never touches the git index: untracking is destructive-adjacent work that the agent does with a recovery point in place.

  1. Full recovery tag, before untracking anything: everything that follows depends on this point. git tag pbi-pre-cache-migration
  2. Untrack exactly the paths outside the allowlist (the files stay on disk). git rm -r --cached -- <paths outside the allowlist>
  3. Commit the untracking. git commit -m "chore: untrack .context/PBI cache (Jira is the source of truth)"
  4. Rebuild the cache from Jira (ATLASSIAN_* credentials in .env). bun run jira:sync-issues pull
  5. Diff the tag against the rebuilt cache and push to Jira any content that only existed in git and never reached Jira (to the field, or to its comment fallback), then re-run the pull. The sync overwrites with Jira's truth, so that content is now only visible through the tag. Only after this step can the migration be reported as done, and the tag is kept until the team confirms nothing was lost. git diff pbi-pre-cache-migration -- .context/PBI
Atomic delivery

The ladder arrives whole or not at all

The .gitignore sync of bun sync groups a run of lines with a common prefix that contains a negation as an all-or-nothing group: a re-include ladder applied halfway is worse than not applying it. The question about new lines (a card in the local bun sync page, or the terminal with --headless) offers it as a single option.

repoOnlyPaths

The maintainer's files never travel

The updater filters boilerplate-only paths before offering anything: .github/workflows/pages.yml and ci.yml, the boilerplate's own .context/master-implementation-plan.md, and the per-instance jira-fields.json / jira-workflows.json catalogs. The list lives in REPO_ONLY_PATHS (cli/update-boilerplate.ts). A consumer regenerates their own; the update only touches the framework.
