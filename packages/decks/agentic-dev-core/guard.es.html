GUARD: Guarded Unidirectional Agent-Ready Development

Un agente escribe código que se parece al código que ya existe. Si el repo tiene una forma clara y una máquina que la vigila, el agente la copia bien; si solo hay reglas en prosa, las copia mal y nadie se entera. GUARD es la arquitectura que este boilerplate enseña y comprueba: cuatro capas, una sola dirección, una puerta por feature, un registro y lint antes que prosa.

01El problema: el agente copia lo que ve

Los principios para el código de producto (carpeta por feature, alias, dos parámetros posicionales como máximo) vivían escritos en prosa y los sostenía un revisor. Eso falla de dos maneras: el agente no tiene una forma que copiar ni un registro que leer antes de crear algo, y ninguna máquina le avisa cuando rompe una regla de capas.

Sin forma

Cada feature nace distinta

El agente imita el archivo que abrió primero. Si ese archivo mezcla datos, reglas y pantalla, el siguiente también lo hará.

Sin control

Una regla en prosa no se ejecuta

Nadie la corre en cada commit. Se descubre en la revisión, tarde y a mano, y el mismo hallazgo vuelve a aparecer en el PR siguiente.

La salida

Dar forma y poner un guardia

Un ejemplo real para copiar, un registro que se lee antes de crear y lint que dice qué regla se rompió y cuál es el arreglo de raíz.

02De dónde viene

GUARD no se inventó desde cero. Junta tres fuentes y la decisión completa está en ADR-0023.

KATA

El repo de QA ya resolvió esto

Para el código de pruebas, el boilerplate de QA tiene capas, un manifiesto generado y un único punto de entrada. KATA nombra conceptos de test (ATC, fixtures, componentes) que no existen en el producto, así que no se aplica tal cual: se toma la idea, no las palabras.

Lauren Tan

"All Code Is Slop (Except Mine)"

La pirámide de confianza: confías en lo que una máquina verifica. Cada corrección se convierte en un check. Una carpeta por feature con prohibiciones de import. Sin comentarios.

Matt Pocock

codebase-design

La interfaz es la superficie de prueba: se prueba un módulo por su puerta pública, no por sus tripas.

03Las cuatro capas

Las dependencias apuntan hacia abajo. Una capa solo importa de las que tiene debajo, y cada feature se alcanza únicamente por su index.ts. 

L4  app        src/app/                  solo compone: lee params, llama acciones, pinta
      |
      v   (a través de la puerta)
L3  features   src/features/<nombre>/   acciones, dominio, UI, tipos
      |   puerta: index.ts
      v
L2  adapters   src/adapters/            Supabase, APIs externas, todo lo de afuera
      |
      v
L1  platform   src/platform/            config, env, cliente de BD, utilidades
Capa Puede importar
app features (por su puerta) y platform
features adapters, platform, y otra feature solo por su index.ts
adapters platform
platform nada de lo que tiene encima
Alias
Usa los alias que declara el tsconfig.json de la app (@platform/*, @adapters/*, @features/* y @/*) y ningún import relativo profundo.

04Las reglas R1 a R6 y quién las hace cumplir

Cada regla tiene un guardia concreto. Cada mensaje de lint nombra la regla y el arreglo de raíz: mover el código a la capa correcta o abrir la puerta de la feature.

Regla Enunciado La hace cumplir
R1 una dirección Una capa baja nunca importa una alta guard/layer-imports
R2 una puerta Fuera de features/x/ se importa @features/x, nunca una ruta profunda guard/feature-door
R3 app delgada src/app/** nunca importa @adapters/*; los datos pasan por una feature guard/layer-imports
R4 registro guard-manifest.json lista cada feature y lo que exporta su index.ts; se lee antes de crear bun run guard:manifest:check y el pre-commit
R5 forma Dos parámetros posicionales como máximo; archivos bajo el límite de líneas max-params y max-lines
R6 sin comentarios Solo directivas del toolchain y un porqué de una línea Regla Crítica 18
Último recurso
Un comentario de desactivar lint existe, pero lleva su razón: eslint-disable-next-line <regla> -- <razón>. Antes se mueve el código.

05Una historia de punta a punta

Así recorre un agente una historia de usuario cuando GUARD está en juego.

  1. Lee el manifiesto primero. Antes de crear una feature o una acción, mira qué existe y qué exporta. guard-manifest.json
  2. Ubica el código por capa. Dato externo va a adapters, regla de negocio a la feature, pantalla a app.
  3. Copia el ejemplo. La feature notes es el molde.
  4. Lint y manifiesto en el commit. El pre-commit corre las reglas y regenera el registro. bun run lint:check && bun run guard:manifest:check
  5. Test unitario por la puerta. Se prueba lo que la feature exporta, no sus archivos internos.
  6. Verificación en vivo. Se comprueba el comportamiento real, no solo que compila.
  7. La revisión humana juzga lo que una máquina no puede. Nombres, intención, producto.
  8. Un hallazgo repetido se vuelve regla. Si el mismo comentario aparece otra vez, se escribe un check (lint o manifiesto) y la prosa queda para lo que no se puede automatizar.

06La feature de ejemplo

packages/guard-example/ es una feature mínima, notes, que pasa todas las reglas. El instalador la inserta en src/ de un proyecto nuevo en la primera instalación y el updater nunca la envía. Tres extractos reales:

La puerta

features/notes/index.ts

export { createNote, listNotes } from './actions';
export { NoteList } from './NoteList';
export type { NewNote, Note } from './types';

Lo único que el resto del repo puede importar.

Una acción

features/notes/actions.ts

export async function createNote(input: NewNote, repo: NotesRepository = notesRepository): Promise<Result<Note>> {
  const valid = validateNewNote(input);
  if (!valid.ok) { return valid; }
  return ok(await repo.insert(valid.value));
}

Valida con el dominio y guarda por el adapter. Dos parámetros, sin comentarios.

La página

app/notes/page.tsx

import { listNotes, NoteList } from '@features/notes';

export default async function NotesPage() {
  return <NoteList notes={await listNotes()} />;
}

Solo compone: ni adapters ni reglas de negocio.

Verificar
Este repo la revisa para que no se pudra: bun run guard:example:check (lint, tipos, manifiesto y tests).

07Adoptar GUARD en una app que ya existe

Una app adoptada conserva sus carpetas. El plugin lee el mapa de capas de settings.guard.layers en ESLint, una lista de globs por capa, y usa los valores por defecto cuando falta. Una app con db/, api/ y lib/ las mapea ahí y no mueve ningún archivo. 

// eslint.config.js
{ settings: { guard: { layers: { adapters: ['db/**'], platform: ['lib/**'] } } } }
Orden
Primero en warn. El mapeo es un paso de la skill project-adoption. Los avisos son trabajo pendiente que se ordena por capa, sin romper el CI.

08El puente con QA

Las acciones que una feature exporta son lo que QA automatiza como ATC de KATA. El manifiesto las nombra, así que el criterio de aceptación de una historia, la acción de la feature y el ATC comparten un mismo vocabulario.

09Severidad: primero aviso, después error

GUARD_ENFORCEMENT_LEVEL fija el nivel de todos los checks de GUARD y scripts/guard-manifest.ts lo refleja. Se despliega en dos pasos: primero warn y, en un release posterior, error. El valor vigente está en esos dos archivos. Un check en warn nunca rompe el CI, así que un aviso es trabajo pendiente, no ruido.

Atención
El cambio a error es un release aparte y su propio cambio. Los proyectos que hacen bun sync reciben avisos nuevos hasta entonces.
