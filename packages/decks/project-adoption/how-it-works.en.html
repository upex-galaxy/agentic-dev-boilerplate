00 · adopting an existing app

An app that already exists is not rewritten: it is read.

/project-adoption teaches the agentic layer to an application that already has its own code, schema, CI and conventions. It reads the app without writing anything, proposes a single plan, waits for your approval and only then fills in the agentic surfaces, so that each skill works with the app's real stack and not with the boilerplate defaults. The app's code, schema, CI and dependencies do not change.

01 · when to use it

After installing, before working on stories

It is the front door for an existing app. A new project enters through another one, and everything that comes after has its own skill.

Use it when

The adoption is installed and the app still has to be taught

  • "Adopta esta app" (adopt this app) · "la adopción quedó instalada" (the adoption is installed) · "adoptar la app existente" (adopt the existing app): the installer with --adopt already ran and is committed.
  • "La adopción sigue siendo correcta?" (is the adoption still correct?) · "adoption drift check": mode check, read-only.
Do not use it for

What belongs to another skill or another step

  • A project from scratch: /project-foundation and then /project-bootstrap.
  • Installing the files into the app: that is the updater run with --adopt, which this skill never replaces.
  • The business maps (/project-context), the branch strategy (/git-flow-master Strategy Setup), the visual identity (/design-system extract) or creating Jira fields, workflows or issues (/jira-administration, /product-management).
02 · install and understand

Two layers, two moments

Installing the tooling and understanding the app are different jobs. The first is done by a command that asks nothing about the app; the second is done by this skill, which asks everything the files do not answer.

Install layer

The updater with --adopt

  • It delivers what the app lacks and never overwrites what it has: a file that belongs to the app at the same path stays as it is, shows up as a merge row and goes into updater.protected_paths.
  • package.json only gains the tooling's devDependencies and the scripts the app does not declare. A script name that already exists is kept and reported.
  • It does not rewrite git history, does not rename, does not run git init and does not touch any database.
Understanding layer

This skill

  • It reads the app and writes identity, the stack: block, environments, tracker catalogs and protected paths.
  • With that, the rest of the skills read the app's real stack instead of the boilerplate defaults.
  • It never replaces the installer: without its lock, it stops.
# from the root of the app repo, with a clean tree
bunx create-agentic-dev@latest --doctor --preflight   # read-only: can it be adopted?
bunx create-agentic-dev@latest --adopt   # hands over to the updater with --adopt

# with a screen, the updater opens its local page (the terminal keeps the full log);
# review the parity table in its final report, bun install, commit the adoption;
# then, in a session:
/project-adoption
What the first version supports. A Next.js app on the Postgres family (Supabase or plain Postgres) that uses bun, one app per adoption. The set lives in V1_SUPPORTED (cli/lib/stack-descriptor.ts): anything outside it stops the preflight or the analysis with the field and value that failed, and nothing is written. Install details: INSTALLER.md, section "Adopt an existing app".

04 · phases 0 to 2

Read everything before touching anything

The seal is measured, not promised: after phase 2, git status --porcelain may only differ from the one in phase 0 by the plan file.

Phase 0 · resume, gate and signals

If a run is half done, it offers to resume, restart or abort, and waits. The gate requires .template/installer.lock.json to say adopted: true and the tree to be clean. With no lock, the files were never installed; with a greenfield lock, the repo was scaffolded and it is a job for /project-bootstrap.

Then it runs the detection signals: each subsystem ends up PENDING or ADOPTED. The pending ones are the work list for this run.

Phase 1 · analysis

The stack fingerprint comes from bun run agents:setup --stack --dry-run --non-interactive: each value carries the file it was read from, and what is not detected stays absent, never guessed. Outside V1_SUPPORTED, the run stops here without writing even the plan.

It reads the repo conventions (adoption parity, hooks, tooling isolation, environment files by name only, CI, branches), probes the tracker read-only and runs the app's scripts for the baseline. What the files do not answer goes into a single questionnaire.

Phase 2 · the plan

It writes .context/reports/project-adoption-plan.md with the header Status: PENDING APPROVAL, verifies the seal and stops. Any change you ask for edits the plan and asks again.

The AI does

Runs the signals, dispatches three read-only analysts and measures the baseline.

Builds the plan from the analysts' facts and your answers.

You decide

Project identity, environments, tracker and which app the adoption covers in a monorepo.

Whether the app's test is safe to run for the baseline.

The yes that moves the plan to APPROVED.

Output

The signals table and the plan in .context/reports/, which the whole team reads.

Whatever stayed unanswered, as ## Discovery Gaps.

Gate the plan approved in this run, with who approved it and the date in the header.
Detecting is not guessingA value with no evidence in the app is a question or a gap, never a default from the boilerplate.
A script that writesIf the baseline changes versioned files, the AI records it, reverts nothing on its own and asks.
Several Next.js appsIn a monorepo it asks which one this adoption covers and pins it in stack.app_root. Never two in one run.
05 · phases 3 to 7

Write only what the plan approved

One writer per phase, each with the approved rows of its phase and nothing else. Every write is verified by reading the destination back.

Phase 3 · identity, stack, environments, protected paths

bun run agents:setup --stack writes the stack: block with the values from the plan; bun run agents:setup fills in identity and environments. Every collision the app already owned goes into updater.protected_paths, with a splice that leaves the rest of the yaml byte for byte. A framework skill the app had copied by hand is replaced by the upstream copy the adoption kept (.agents/prompts/adopt-upstream/), only if its row has its own approval line and with a prior backup in .backups/project-adoption/; if the team keeps it, it stays in the protected paths.

Phase 4 · credentials

Only .env, only values you give in this run, never repeating them. Then restart the session: each MCP server reads the .env with its loader when it starts.

Phase 5 · tracker catalogs

It loads /acli and syncs the catalogs against the app's own instance, never with the UPEX reference flag. A missing field is not created: the plan names the fallback and says that creating it is a Jira admin's decision. And the adoption does not hydrate the whole project: the backlog cache is filled per story.

Phases 6 and 7 · instructions and API contract

If the installer left an instructions merge pending, it is applied as is, with its own approval line and a prior backup; the app's text is never summarized or reordered. The <app>-context skill the adoption wrote only changes in its description, rewritten from the analysis so it routes by the app's real domain; the preserved text of the app is never touched. The API contract is synced only if the app serves a spec and the routes of the output did not exist before.

The AI does

Rereads the approved plan before each phase and writes only its rows.

Rereads the yaml, reruns the signal, reparses the file: a "done" is not enough.

You decide

The credential values, which you type only into .env.

The instructions merge, with an approval separate from the plan's.

Output

.agents/project.yaml with the app described, the .agents/jira-*.json catalogs and the merged AGENTS.md.

Gate each phase verified at the destination before moving on to the next.
06 · phases 8 and 9

The app has to come out the way it went in

Verification is fail-fast and in order: it stops at the first failure, reports it with its output, proposes the fix and waits. It never fixes anything on its own. 

# phase 8, in this order
bun run agents:compat:check
bun run vars:check
bun run vars:env:check
bun run harness:env:check
bun run jira:check                 # skipped if the plan recorded "no tracker"
bun run setup:doctor               # stack section: no issues, no drift
bun run tooling:types:check        # the tooling's own scope, never the app's tsconfig
bun run tooling:lint:check
the app's build / lint / types / test   # exit codes == phase 1 baseline
The failure that matters most

An app script that changed

  • If the app's build, lint, types or test do not give the same exit code as in the baseline, the run is not finished.
  • The report names the script, the two codes and the first new error.
Phase 9 · close

The signals as a report

  • It reruns the phase 0 signals and prints the final table.
  • Marks the plan Status: COMPLETED with its results block.
  • Proposes the commit through /git-flow-master. It never does it silently.
  • Optionally offers a read-only architecture scan (shallow modules or modules that leak into each other). You pick a candidate in another session.
Idempotent. The same signals are the work list on the way in and the report on the way out. A second run on an app that is already adopted says there is nothing to do.
07 · rails

A refusal list and a permission list

The agentic layer lives inside the app's tree, so "the target repo is read-only" is not enough. The refusal list travels verbatim in every subagent briefing.

Never writes or deletes a file of the app under stack.app_root that existed before the adoption.
Never touches a database: no migrations, no SQL, no RLS, no seeds, no connection, in any environment. The live schema is read later by /project-context data.
Never changes dependencies, the package manager or the lockfile.
Never edits the CI, the README.md, the tsconfig.json, the eslint or prettier config, .gitattributes, the middleware or a script in the app's package.json.
Never touches git or Jira on its own: no history, remotes, branch protection or rulesets, no projects, fields, workflows or issues. It never pushes.
A secret value is written nowhere: not in the plan, a report or a commit, not in the .env. The .env receives only non-sensitive values; you write the secret yourself.
Can write

Only with its approved row

  • .agents/project.yaml, the .env (non-sensitive values only) and the .agents/jira-*.json catalogs.
  • AGENTS.md + CLAUDE.md, only through the merge the installer saved.
  • The framework skill folders the app had copied, replaced by the saved upstream copy (with their own approval), api/openapi* when they did not exist before, and the description of the <app>-context skill.
  • The plan, the optional architecture scan (.context/reports/project-adoption-architecture.md), .session/project-adoption/ and the plain-text copies of MCP credentials that bun run harness:env retires.

What the team owes

Reported, never created

  • A dedicated identity for automation (testing.automation_identity).
  • The GitHub account for autonomous delivery (autonomous_delivery.automation_gh_account).
  • A dedicated database role for read-only checks.
the plan names the skill that needs it and what the team has to provide
No invented PRD. The product documents of an adopted app are the business maps and the glossary. /sprint-development accepts them in place of a PRD or an SRS, and no skill writes one to get past a gate.

09 · after adopting

The hand-off, in order and never chained on its own

When it closes, the skill leaves you each next step with the phrase that triggers it. None starts by itself.

First · new session

/project-context refresh-all

The business maps read from the app's code and schema. They go in a separate session because they weigh in tokens. Deck: Project context.

After the maps

/project-foundation, Discovery only

The development guide and the domain glossary, which complete the app's product documents. Deck: Project foundation.

Its own session

/git-flow-master Strategy Setup

The project's own branch strategy and the host protection, read-only first. Deck: Git flow master.

Optional

/design-system extract

DESIGN.md written from the app's live theme. Deck: Design system.

Optional

/testability-guide

The /qa page inside the app and the credentials artifact. Deck: Testability guide.

Optional

/project-bootstrap, types add-on

The database types in stack.database.types_path when they are missing. The base bootstrap phases do not run on an adopted app. Deck: Project bootstrap.

To read more: .agents/skills/project-adoption/SKILL.md and its references: references/adoption-workflow.md (the phases, the signals and the refusal list) and references/plan-template.md (the plan sections). The installation is in README.md, section "Adopt an existing app".

The core idea. A live app has already made its decisions. The adoption records them so the other skills respect them: it reads before writing, writes only what is agentic and proves at the end that the app builds, lints and tests the same as before.
