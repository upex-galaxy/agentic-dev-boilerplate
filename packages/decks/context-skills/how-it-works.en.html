00 · context skills

The business map arrives on its own, you don't hunt for it.

Which entities the product has, what each role can do from each screen, what each route changes: no script pulls that from a source. An AI writes it by reading the code, the schema and the API contract. That is why each business map lives inside a context skill, as an HTML file a human opens in the browser and the AI reads by section with bun run context:map. This deck explains what a map is, how it is read and how it is kept honest.

01 · why a map is a skill

A synthesis is not a cache

.context/ holds what a SCRIPT pulls from a source of truth and what this repo itself is the source of truth for. A business map is neither of the two: two sessions would write it differently and redoing it costs thousands of tokens. It is written knowledge, and knowledge that has to arrive without anyone asking for it is a skill.

The question, for each piece of knowledge If the answer is yes, it goes to It is recovered with
Does a script pull it from an external source? (Jira, the OpenAPI spec, the schema) .context/ as a [SYNC] cache, or generated types bun run context:hydrate, bun run api:sync
Is this repo the source of truth? (ADR, PRD, SRS, glossary, design plan) .context/ as [COMMIT] git checkout
If not: the AI synthesizes it from the code, the database and the contracts A context skill: the generated map inside, the judgment in its rules Regenerating is expensive: it is fixed by section
Fact

Goes to the map

  • Two competent sessions would write it the same way: an entity, a route, a CRUD action. It is never copied into SKILL.md.
Judgment

Goes to the skill's rules

  • Two sessions would write it differently: "profiles use soft delete; a count without deleted_at IS NULL is wrong". It goes to ## Rules or to references/gotchas.md, with a date and how it was measured.
One file, no twin. The human and the AI read the same HTML. There is no copy in markdown and none under docs/: the twin is always the one that goes stale. For the other side, the Jira cache, see the deck the PBI cache.
02 · the maps the boilerplate ships

One aspect per skill, one generator per map

The single list of skills with a map is CONTEXT_MAP_SKILLS in cli/lib/context-maps.ts: each entry names its map, its generator and the old markdown it replaces. The table below is what the boilerplate ships; to know what is in your repo, read that constant.

Skill What it knows Generator Wins on a conflict
business-data-context Entities and relations, RLS, migrations, state machines, automated processes, integrations project-context mode data The live Supabase database (capability db)
business-feature-context Feature catalog, CRUD matrix, UI inventory, flows between features project-context mode features The frontend tree; the running app, for behavior
business-api-context Auth model, route groups, OpenAPI surface, journeys across routes project-context mode api The spec for the shape; the handlers and the running API, for behavior
They load by their descriptionA task that writes a migration brings the data map; one that touches a handler, the API map; one that touches a screen, the features map. Nobody has to say "map".
There is no domain map or infrastructure mapThe vocabulary lives in .context/business/domain-glossary.md, written by hand. PRD and SRS stay under .context/.
Each one cites the othersThe features map names the data and the routes behind each feature, and does not repeat them: it cites their skill.
03 · anatomy of a map

The contract the generator writes and the reader parses

A self-contained HTML file that opens from file://, with flat sections. Each section's id is the editing anchor: it is set at CREATE and never changes again. 

<!-- line 1 of a generated map -->
<!-- generated by project-context mode data; edited in place by business-data-context refresh; do not hand-edit -->
<!-- or, if it has not been generated yet -->
<!-- placeholder: run project-context mode data to generate this map -->

<section id="orders-lifecycle"
         data-sources="src/app/api/orders/, db:orders, migration:<file>"
         data-updated="YYYY-MM-DD">
  <h2>...</h2>  <p> <ul> <table> <code>  <!-- plain semantic HTML -->
  <figure data-diagram="state" data-for="orders-lifecycle"><svg>…</svg><figcaption>…</figcaption></figure>
</section>
...
<section id="discovery-gaps">  <!-- always the last one -->

Line 1 decides everything

The reader, the updater and the doctor read ONLY that line to know whether the map is generated or a placeholder. The generator it names comes verbatim from the CONTEXT_MAP_SKILLS entry.

One section per unit of fact

An entity, a flow, a feature, a route group. Never nested, each one opens with its <h2>. data-sources lists the signals it came from (the freshness check reads them); data-updated, the date.

No fact lives only in a figure

Everything a diagram shows is also in the text. One summary figure at the top, and one per section only where a drawing explains the mechanism.

discovery-gaps, at the end

What could not be verified. "I could not verify X" beats an invented answer. A section migrated from an old markdown map carries data-migrated-from once, until it is regenerated.

A generated map may have counts. Tables per schema, routes per group: it is a generated artifact and is exempt from Critical Rule #17, like any generated file.
04 · how it is read

The AI never reads the raw HTML

The inline SVG is nearly all of a map's weight and none of its facts. The reader, scripts/context-map.ts, strips the SVG, the <style> and the <head>, and prints each section as text with its id, its date and its sources.

You need Command
The whole map, as text bun run context:map <slug>
One section (a dispatch that touches an entity or a route group) bun run context:map <slug> --section <id>
The index, for a freshness check (id · date · sources) bun run context:map <slug> --list
The map drawn, for a human bun run context:map <slug> --open
In a briefing

The command is injected, not the path

  • The Skill Resolver (rule 5 of skill-resolver.md) injects only the context skills whose ASPECT the dispatch touches, as bun run context:map <slug> --section <id> for the sections it touches. Never all of them: a subagent that touches one aspect pays for one.
  • A dispatch that names no aspect receives none. When in doubt, name it in the Goal.
Placeholder

It means "there is no map", not an empty system

  • The reader warns on stderr which generator to run and exits with 0. A migration is never planned as if the schema were empty: the human is handed the mode that generates it.
  • It exits with 1 on an unknown skill, a missing map or a section id that does not exist, and in that case it lists the known ids.
Cite with a date. A map fact is cited with its section id and its data-updated. A section older than the migration it describes is a hypothesis to check against the database, not an answer.
05 · create and update

No path regenerates a whole map

Generating is the job of project-context: its modes, its gates and the order of refresh-all are explained in its own deck. Here is what happens to the map. The section id is what makes the saving mechanical: one edit on one <section> block.

Map state What runs What it writes
Missing or placeholder The mode's CREATE: all sections from the sources. If the old markdown it replaces exists (the legacy list of its entry), it is read as input and cited in data-migrated-from The whole file, once
Generated The mode's UPDATE: freshness check, regenerates ONLY the stale sections, shows a diff per section and WAITS for your approval The approved sections
The facts of a section with a figure changed That figure is redrawn Un <figure>
The AI does

Reads every source the mode asks for. What it could not verify goes to discovery-gaps, not to the body.

After writing a map, it reviews that skill's ## Rules and gotchas against the new map and PROPOSES changes.

You decide

Which mode runs: if you don't name it, the AI asks.

Whether an UPDATE's diff is applied.

Output

references/<map>.html inside its skill, and nothing else: the mode writes only that file.

The old markdown maps in .context/business/ are never deleted.

Gate an existing map is not overwritten without your explicit approval of the per-section diff.
06 · is it stale?

Each section says where it came from, and that says when it expired

The check walks --list and compares each signal in data-sources against its date. The generic signals are in the doctrine; each skill adds those of its aspect in its own references/refresh.md.

Signal Stale when
A repo path git log --since=<data-updated> --oneline -- <path> returns any commit
db:<table>, migration:<file> There is a later migration, or the database (capability db) shows a column, constraint, policy or trigger the section does not describe
openapi:<x> The contract changed since the date (output of bun run api:sync, or the git log of the spec)
route:<path> The handler or the page changed
The aspect's own signals Declared by each skill's refresh.md: for example cron:<job> and webhook:<event> in data, auth:<scheme> in API, a flag or a role gate in features
No sources, no freshness. A section that declares no sources is reported as unknown, never silently as fresh.
07 · the skill corrects itself

It proposes with evidence, applies with your yes

A context skill runs no workflows. All it does is keep its map honest: when a session sees something that contradicts a section (a column the map omits, a status the map calls impossible, a CRUD action missing from the matrix), it proposes the edit.

The five steps
1Locate--list, then --section <id> of the section concerned. 2EvidenceMeasured: a query, a request, a file in a commit, a session. Without evidence there is no proposal. 3ProposeTo the session's owner: you in the main thread, or the conductor if it is a supervised worker. An unattended routine applies only if its brief names that map or section; otherwise it leaves it in its report, like a one-shot subagent. 4Apply, only with approvalRe-read the section (another session may have edited it), edit THAT block, update data-updated and the sources; the figure, only if its facts changed. 5Verify--section <id> prints the new text.
Two paths, never mixed
AA contradicted sectionThe context skill writes it, after your yes, with the five steps. BSeveral stale sections, or something newDone by the UPDATE of a project-context mode. The skill hands you that mode; it does not rebuild sections itself. =Silence is not approvalOnly a yes applies the edit. 
# the proposal, in a single message (references/refresh.md)
business-data-context · proposed edit to section <id> (updated <date>)
evidence: <what was observed, how, where: query / request / file@commit / session label>
before: <the sentence or row as the map has it>
after:  <the replacement>
figure: <unchanged | redraw: why>
apply? (yes / no)
Verified before proposingData, against the database; features, against the running app or the route file; API, against the handler, the OpenAPI types or a real request.
An id is never renamedA renamed entity, feature or group is a new section, plus a line in discovery-gaps during a refresh.
A judgment follows the same pathA new rule for READING the map goes to ## Rules or to the gotchas, dated and measured, with the same approval.
08 · write scope

It writes in its references/ and nowhere else

The skill declares it in its frontmatter with metadata.writes: [references/], and a lint enforces it. No Jira, no .context/, no other skill, no migrations and no product code.

Only a skill of kind context declares metadata.writes. On any other kind, the lint flags it as an error.
Every target is inside its own references/. A target outside is an error.
It ships references/refresh.md, the procedure that runs its write path. Without it, an error.
No tracker tag in the body or in refresh.md: it edits its map, never a tracker.
Who enforces it: the CONTEXT-WRITES rule of scripts/lint-skills.ts, which runs with bun run skills:check. In the same lint, STALE-PATH is strict inside a context skill: every .context/ path it cites has to exist (only the .context/PBI/ cache is exempt). It cites, never copies.
09 · the figures

The diagrams capability is a skill, not an MCP

The figures are drawn by the diagram-design skill, which cli/install.ts installs at project level; a user install or a harness plugin works too. It is the only capability resolved by the presence of a skill and not by a tool suffix.

Before drawing

Can diagram-design be loaded?

  • If not: STOP at the point of use, naming the install line. Never a map with a hand-drawn SVG or ASCII in its place.
The style

It is diagram-design's business

  • A .diagram-design marker at the root (profile: <slug>) picks a saved profile if the project wants one. Two machines may draw differently: what matters is in the text. 
# the line the STOP names (mcp-capabilities.md)
bunx skills add https://github.com/cathrynlavery/diagram-design --skill diagram-design --yes
10 · delivery and owner

Upstream delivers it once; after that it is yours

Every <aspect>-context skill is project-local: the updater never delivers it, overwrites it or deletes it (isProjectLocalSkillPath in cli/lib/updater-core.ts). Those of CONTEXT_MAP_SKILLS are the only exception, and only for delivery.

It arrives as a placeholder

bun sync delivers the skill's folder when it is missing (collectContextMapBootstrap), with a placeholder map inside.

Never touched from upstream again

From there on, nothing in the updater overwrites or deletes what is inside: the map is the synthesis of YOUR product, and so are its rules and gotchas.

A placeholder is flagged, it does not block

A map that is missing or still a placeholder (with the old markdown next to it, if any) shows up as an informational row in the final report of bun sync (on the page and in the terminal), and bun run setup:doctor prints the same line, with the generator to run.

11 · your own context skill

For an aspect the maps do not cover

billing, auth, stripe: the judgment layer over an aspect that a competent session would misread. project-context mode context-skill creates it, always through skill-creator. The sources hold the facts; the skill, the rules for reading them.

The AI does

Reads in full what the skill will cover and lists every place where it can be misread: soft delete, RLS that hides rows from a role, states with different names in the database, API and UI.

Runs each candidate through the three questions of §01: only judgment stays as a rule.

You decide

The aspect and what it rests on.

On UPDATE, whether the diff is applied: rules are added with a date, never rewritten.

Output

.agents/skills/<aspect>-context/ with metadata.kind: context, plus references/gotchas.md.

The project's own, never sent upstream.

Gate bun run skills:check green and bun run skills:registry with the new block in REGISTRY.md; no sentence repeated from the map or the code.
What it covers has to exist firstA map, a module, a contract. A skill about nothing ends up being the source by accident.
Data, features and API already have an ownerA data-context request is answered by pointing to business-data-context, never with a second source on the same aspect.
No measurement, no ruleEvery rule carries a date and how it was measured. What was not measured goes to memory, not to the skill.
12 · what you tell the AI

Context skills have no modes: they are generated, read and loaded

Generating a map is a project-context mode. Reading it is a repo command, the same on every host. Loading the skill happens on its own, by its description, or by naming it.

Claude Code

/project-context data

Generates or updates the data map. Same with features or api.

OpenCode

load the project-context skill, data mode

No slash: you name the skill and the mode in the sentence.

Codex

load the project-context skill, data mode

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:project-context data

Slash with the /skill: prefix. In a new folder, /trust once.

# read, on any host
bun run context:map business-data-context --section <id>
bun run context:map business-feature-context --list
bun run context:map business-api-context --open   # for you, in the browser

# your own context skill
/project-context context-skill billing        # or: load the project-context skill, context-skill mode
13 · around the maps

Who generates them and who reads them

The maps do not belong to a single workflow: one writes them and several consult them.

Generates them · modes and gates

/project-context

Its modes data, features and api write the maps; master-plan requires the generated data map. Its gates and its order live in its SKILL.md.

Chains them · Discovery

/project-foundation

Its Discovery phase runs the map modes and verifies the data map with bun run context:map before the master plan.

Reads them · per story

/sprint-development

To assess the impact of a story that touches several domains. If a map is still a placeholder, it goes on without it and notes that in the plan.

Reads them · backlog

/product-management

Its dependency pass uses the entity graph, the CRUD matrix and the route catalog before creating or editing a story.

To read more: agentic-dev-core/references/business-context-maps.md (the whole doctrine), skill-scaffold.md §3 to §5 (the principle and the own skill), the SKILL.md and the references/refresh.md of each context skill, and cli/lib/context-maps.ts.

The idea underneath. What an AI synthesizes by reading the product is expensive to redo and comes out different every time. That is why it is stored only once, inside the skill that brings it into the session, read by section and fixed one section at a time, with evidence and with your yes.
