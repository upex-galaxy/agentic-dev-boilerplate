00 · runs with nobody watching

Deliver overnight, without guessing.

/autonomous-delivery is the layer between a scheduler and /sprint-development. An interactive pipeline assumes a human picked the ticket, confirmed its state and is around if something goes sideways. With nobody on the line, all three assumptions are false. This skill implements nothing: it establishes what is true, picks work that is genuinely unblocked, hands it to the owning skill and leaves a record the next run can start from.

for whoever leads the team and whoever is the product owner fired by a scheduler, not a person git is the truth, the tracker a hint

01 · when yes and when no

A scheduler fires it with a mode. That is its whole surface

A cron, a routine or a scheduled wake-up opens a session with no human present and hands it the mode. If a person is on the line and named a ticket, this skill is redundant: its only value is the audit, selection and handoff layer, and that layer is pure cost when a human already chose.

Situation Goes to
Per-ticket work with a human present /sprint-development, directly
Seeding the backlog or refining criteria of a named ticket /product-management, directly
Branches, pull requests, conflicts /git-flow-master
Defining the product from scratch /project-foundation
Infrastructure scaffolding /project-bootstrap
A TDD slice of unit tests /unit-testing
A scheduled, unattended run, with a mode /autonomous-delivery <mode>
Preconditions

If one is missing, it ends in phase 0

  • .agents/project.yaml with the autonomous_delivery: block and git_strategy.branches: the branch every ancestry check runs against is integration, or production when integration is null (solo-main, github-flow, trunk-based). An integration: null is valid and does not end the run: in that case the run never merges and the ticket stays on an open PR.
  • .context/dev-roadmap.md as the source of the dependency edges.
  • A complete .env: credentials are read by variable name, and never go into a report.
  • An identity with push permission, verified in phase 0 and not at the first push.
No improvising

The report names the file and the key

  • A missing requirement is not worked around: the run stops and says exactly what is missing and where. The dispatched skill's preconditions are verified by that skill, and this one fails fast when told.
02 · modes and caps

Three modes, each with a cap that is not negotiable

Every story we measured ended up as a chain of thousands of lines: two do not fit in the context of one run. The caps come from that measurement, not from caution.

Mode Picks Cap Dispatches to Writes code
story The highest-priority story that is truly unblocked 1 per run, hard /sprint-development yes
bug Unblocked defects, oldest and most severe first up to 3, strictly in sequence /sprint-development (bug entry) yes
discovery Refinement gaps, epics or backlog definitions only, up to discovery_definitions /product-management never
No mode, no runThe first token of the arguments is the mode. A missing or unknown one is a fast-fail: nobody is there to answer, so it is never asked and never inferred from prose, and it never falls back to a default mode.
One bug at a time, fully closedThe second bug is not claimed until the first has gone through the phase 4 close. Three bugs are not three parallel threads.
The master switchautonomous_delivery.enabled en false, or a mode missing from modes, end the run in phase 0 with a one-line report. That is not a failure.
Your project's values live in one place: the autonomous_delivery: block of .agents/project.yaml. The skill's own block is an example with the safe value for each axis; quoting it as the project's state is a provenance error.
03 · phase 0, isolation and lock

First its own worktree, then the mode's lock

The collision that cannot happen is two runs implementing the same ticket on two branches. story and bug enter a worktree of their own, created by hand so it can be closed by hand. discovery touches no code and creates no branches: it works in the shared checkout and skips isolation entirely.

Note the primary

<<PRIMARY_ROOT>> comes from git rev-parse --git-common-dir, never from pwd. It is the same value from the primary and from every worktree. .session/ lives there for the whole run and is read and written by absolute path.

Create the worktree

With a generated name, never a fixed one. In Claude Code, EnterWorktree. In OpenCode, Codex and Pi, the portable route: git worktree add outside the primary, from origin/<integration-branch>.

Provision

bun run worktree:provision copies .env, .vercel/ and the rest that git ignores. It does not copy .session/: the lock only excludes another run if both see the same file.

Verify the base

git fetch and an ancestry check against the integration branch (or against production when integration is null). If it is wrong, it is realigned with git checkout -B. Never git reset --hard: rule #13 forbids it.

If the scheduler already assigned a worktree (the "Worktree" option of a Claude Code routine, the worktree mode of a Codex automation), the run does not create a second one: it works there, notes in the report that this option should be off, and does not delete it at the end. It is a degraded but working path. Under Orca, the file hook in orca.yaml audits it and removes it.

One lock per mode, never a queue

It is lock.json, in .session/autonomous-delivery/<mode>/ of the primary checkout, with owner, machine, worktree, start and a heartbeat that is refreshed at every phase boundary.

Finds Does
No lock Writes it and goes on.
A lock with a recent heartbeat Another run owns the mode: it exits cleanly with a report that names it. It does not wait, retry or carry on anyway. The next trigger is the retry.
A lock older than lock_staleness_minutes Abandoned: it claims it and notes it in the escalation log. The dead run's worktree stays for a human to audit and remove.
A lock from this same session An earlier phase of this run: it goes on.
The push identity is verified three timesgh auth status against automation_gh_account: in phase 0, right before the first push and right before any merge. A CLI with several accounts can switch identity in between, and the error only shows up at the merge, disguised as branch protection.
Resume without askingWith no user, phase 0 resolves the previous progress.md by table: branch on the remote, resume; branch missing, escalate (work was lost and is not silently redone); final phase complete, archive and start from zero.
04 · phase 1, audit

Git is the source of truth. The tracker is a hint

A tracker can say "ready for QA" with nothing on the integration branch: the merge automation fires on any pull request, including the internal ones of a chain. Every dependency decision in phase 2 rests on this, so it is verified, never inferred. 

# from most trusted to least; when two clash, the one on top wins and the clash is recorded
git ancestry against the integration branch            <- decides
open pull requests + branch state on the remote        <- explains
live tracker state                                     <- hints
queue file / board / claims                            <- claims
roadmap and design prose                               <- edges only, never state

# the most used check, always with a fetch immediately before
git fetch origin
git merge-base --is-ancestor <merge-commit> origin/<integration-branch>   # exit 0 == it really landed
Four sources, in parallel

One verifier per source

  • Git ancestry, on every merge commit that contributes to a dependency.
  • Open pull requests and unmerged branches.
  • Live tracker state, with its changelog and its comments.
  • The queue file, board or claims, read whole, not just your own row.
Why not a single agent

Because it would smooth over the contradiction

  • The four sources disagreeing is the normal case. A single agent reconciles them into a tidy story and erases exactly the signal phase 2 needs to see.
The AI does

Fetch, the four sources, the live migrations ledger with [DB_TOOL] and branch protection through both endpoints: the classic one returns 404 when the protection is a ruleset. Without the db capability (or with stack.database.engine: none) the ledger is skipped, the report says so and no ticket that touches the schema is claimed.

You decide

Nothing to decide. Every discrepancy between tracker and git goes in the escalation log, with evidence, so you can read it and so the next run knows how this tracker lies.

Output

A table, not a story: ticket, what the tracker says, merge commit, whether it is an ancestor, open PR, branch state and a verdict (merged, claimed-only, in-flight, not-started).

05 · phase 2, selection

It picks what is truly unblocked, or picks nothing

Four inputs, weighted and not averaged. The phase 1 verdict overrides the others when they disagree.

Input Rules over Never rules over
.context/dev-roadmap.md dependency edges, mockup gates, order the current state of anything
The tracker, queried now live status, owner, changelog whether the work merged
Phase 1 verdict whether the work merged what needs to be built
Queue, board or claims who holds which row when you read it whether a dependency shipped

Ready is not a state

It reads the refinement trail: open blocking questions, practice answers marked as drafts, edge cases left unticked, or a status change with no comment explaining it. Any of them means not ready, whatever the field says. It is a skip with a noted reason, not an escalation.

Growth check

A high estimate, a UI story with no mockup where the design plan expects one, an architecture decision implicit in the criteria, more than one migration or a new authorization route: it is not claimed without a human present. It is noted and the next one is taken.

The claim protocol

It writes its name on the row, saves and reads the file again. If there is now another name, a peer won: it backs off and takes the next candidate. It never fights over a row or edits another run's.

An empty run is a correct result. If nothing survives, it exits cleanly with a report that says what it considered and why it dropped each one. Picking marginal work to avoid handing in an empty report is exactly the failure this phase exists to prevent.
06 · phase 3, execution

It dispatches to the owning skill and does not repeat its stages

Every dispatch carries the seven-component briefing. Component 7 (rules) carries the migrations gate, the worktree path, the ban on rebasing already pushed branches and the context stop procedure: a rule that lives only in this skill never reaches the executor.

Mode Dispatch What this skill adds
story /sprint-development, new story entry ticket key, the phase 1 table, the claim, the worktree path, the migrations gate, the context budget
bug /sprint-development, bug entry (root cause first) the same, once per bug, in sequence
discovery /product-management the gap found in phase 2 and its evidence

The migrations gate

Writing the migration file is technical work and is always autonomous. Applying it to a shared database is irreversible and hits every concurrent agent: it is a different act, with a different gate, according to autonomous_delivery.migrations.

migrations: Additive change Destructive change (drop, rename, rewrite)
confirm (default) Escalates and ends with a clean stop. The escalation entry asks for approval: target, what it does, that it is additive. Escalates all the same, with a second real option in the entry: defer it.
autonomous Goes on. Still escalates and ends. autonomous never covers this.
unrestricted Goes on. Goes on. Opt-in and dangerous on purpose: for a database with no production data to lose. It is never the default.

A case the gate does not open: with stack.database.migrations_tool in prisma or drizzle, the database change doctrine says to consult the team before applying, and nobody is on the line. The run writes the generated migration, pushes it and escalates, whatever migrations:.

The number comes from the live ledgerImmediately before writing the file, never from listing the local directory: the ledger can be ahead of your branch because of a peer's unmerged migration.
Re-read after every applyAnd compare the live definition against the committed file. A migration is never applied just to make a local error go away.
Green tests are not evidenceAt least one assertion has to go through a real production write path. Fixtures that seed the column the code reads, and not the one production writes, keep the suite green over a dead data path.
Phase 3.5, per ticket

Cleanup right away, not at the end

  • Confirm the branch is pushed (or that there were no commits).
  • Rescue the dispatched skill's local .session/ with bun run worktree:audit <path> --rescue; if it exits with an error, it does not go on.
  • git worktree remove <path> and a line in progress.md.
Optional

One supervised worker per ticket

  • When the orchestration gate passes (binary and reachable runtime), a story or bug dispatch can go to one worker per ticket. Lock, audit, selection, caps and gates stay with this skill; the worker stops at an open PR and the merge stays with the run. With integration: null the same holds for the whole run: it never merges, and the merge to production is stage 5 of /sprint-development, a human decision.
07 · the budget contract

What runs out first is context, not the clock

In the run this skill came out of, every generation of workers retired because of context, several in the middle of a ticket. It is designed for that.

Handoff on the go

handoff.md is filled in at every phase boundary and after every finished slice, per context_budget.handoff_checkpoint. A session that ran out of room cannot write down why.

Measure its own budget

At every phase boundary. On reaching context_budget.stop_at_remaining_pct it stops taking work: no new slice, no background agent, no scheduled wake-up.

The clean stop, in this order

Push first. Then rescue records, the resume state in handoff.md (branch, SHA, PRs, the next concrete command), the last entry of progress.md, release the lock and report. 

# the clean-stop sequence
1. PUSH the branch         <- always first: unpushed work in a disposable worktree
                                  is the only unrecoverable loss in this system
2. rescue session records
3. resume state in handoff.md, written for a stranger picking it up cold
4. last entry of progress.md
5. release the lock
6. report
A run that delivers a clean handoff is a success. It is judged by whether the next one can pick it up, not by whether it shipped. Dying mid-ticket with unpushed work is the failure it is designed against.
08 · who decides what

It decides the technical calls alone. It escalates only four things

It follows agentic-dev-core/references/decision-protocol.md: search the record, follow what is already decided, a scored judge panel if the question is truly new, and escalate only what warrants it. Everything is written where phase 1 of the next run will find it. 

SEARCH THE RECORD -> already decided? FOLLOW IT
        |
        | not decided
        v
  product / new security / irreversible / reserved?
        |  no                                  |  yes
        v                                      v
  SCORED JUDGE PANEL (3-5 lenses)           ESCALATE (informed)
        |                                      |
        +---------> WRITE IT DOWN <------------+
The record it reads first

The escalation log, whole

  • .session/autonomous-delivery/escalation-log.md, plus .context/ADR/ and the sibling tickets. It looks for the shape of the question, not its wording: a ruling that governs you may have been written an hour ago by a run you never saw.
  • Escalating here is expensive: nobody is there to answer, and a stop over a technical question costs a whole scheduled turn.
Product: it is configuration

decision_authority.product

  • escalate (the right default): a product question stops the run.
  • decide: there is no human PO. A decision subagent scores the options, posts the ruling on the ticket under a heading with the profile that decided, and the run goes on. It is never presented as a human signature.
  • New security, irreversible and reserved items escalate under either setting.
Escalating is a clean stopIt writes the entry (what happened, why it is in this category, what the human has to decide, what waiting costs), pushes, releases the lock, notifies and ends. It never leaves a session parked waiting for an answer that cannot arrive.
Two channels, two jobsescalation_channel carries only escalations, something a human has to resolve. report_channel carries the summaries. With null, the report file is the notification.
Discovery creates, the operator vetoesThere is no approval gate: it creates up to its cap, notes each key in discovery/created-log.md (append only) and reports it. On start, it reads that log against the tracker: a closed or deleted ticket is a standing veto and is not recreated, not even under another title.
Three brakes when a fix run startsWhat a run produces passes three brakes: the app's own checks, the Stage 3 review of /sprint-development done by a reader who did not write the work, and a person's review after the run ends. None of them makes the run wait or narrows the merge permission. A fix run never starts because another one failed (anti-pattern A23), and a failed ticket is retried three times at most before it is reported BLOCKED.
Decision logEvery decision made alone leaves a row in decisions.tsv, in the mode's session directory, with six columns. If the show-me-your-work skill is not installed, the skill writes the same columns by hand. A failure to log is reported and the run goes on.
For the product owner: your control over discovery is the veto after the fact. Closing a story in Backlog costs one click. The skill forbids reintroducing an approval wait, or a softer version of one, because an unanswered proposal left several triggers in a row creating nothing, and the cap per run is what bounds the damage.
09 · phase 4, close and report

Each step can be lost with the one before it, hence the order

Nothing evaporates silently: every discrepancy, every autonomous decision and every check the run could not do shows up named in the report.

1 · The owning skill's close, verified. That the automatic tracker transition really happened, that the owner really changed, the handoff comment and the cache sync. This skill does not reimplement it: it checks that it happened.
2 · Rescue before deleting. This skill's state already lives in <<PRIMARY_ROOT>>, but a dispatched skill may have written a .session/ inside the worktree: bun run worktree:audit <worktree> --rescue.
3 · Release the lock. Also if it escalated or stopped on budget: the lock belongs to a running session, not to an unfinished ticket.
4 · Write the report in .session/autonomous-delivery/<mode>/run-report.md, also for the empty run.
5 · Post the summary to report_channel if one is configured. Never an improvised destination.
6 · Archive the session and close the memory with the archive path.
7 · Close its own worktree, the last step. ExitWorktree(remove) in Claude Code, git worktree remove from the primary on the portable route. Never another run's, and never one the scheduler assigned.
Artifact Scope and life What for
run-report.md one run; overwritten on every run and archived what this run did, for a human catching up
handoff.md one run, written continuously; archived what the next run cannot get from anywhere else
escalation-log.md all runs and modes; append only, never archived every stop, every ruling, every discrepancy
progress.md one run; append only, archived mechanical state for resuming, with what is left unpushed
The first thing a lead reads: the "Not verified by this run" section of the report. What a scheduled run could not check is named exactly, so whoever can knows where to start. It is never left implicit.
10 · guardrails

What it never does, with nobody watching

The rules that have to bind the executor live in ## Compact Rules and reach every briefing through .agents/skills/REGISTRY.md. Every observed hazard, with its trigger and its check, is in references/hazard-catalogue.md.

Never advances a dependency on a status change in the tracker. Only git ancestry decides whether something shipped.
Never rebases, force-pushes or rewrites pushed history. On a branch a subagent already pushed, it merges the base. And a denied operation is a signal to stop and name the missing permission, never a puzzle.
Never touches its own permission configuration to regain a capability.
Never improvises an identity or credential when the declared one is missing. A worktree without its .env is the most common form of that temptation: it fails closed and reports.
Never guesses a transition. A slug missing from .agents/jira-workflows.json triggers nothing: it leaves the issue where it is and the report recommends bun run jira:sync-workflows.
Never commits regenerated output without reading it. Types or clients generated from a shared instance absorb a peer's unmerged schema.
Never edits another run's row, branch or worktree, except to claim a free row per the protocol.
No AI attribution in commits, pull requests or tracker comments (Critical Rule #3).
Editing a rule changes nothing until the registry is regenerated with bun run skills:registry. The registry is what reaches a briefing: a rule that did not reach the briefing did not reach any executor.
11 · what the scheduler tells the AI

Invoking it in every terminal

The routine's prompt writes it, not a person. The mode is always explicit: story, bug or discovery, defined in the skill's ## Mode routing.

Claude Code

/autonomous-delivery bug

The skill's slash command and the mode as the first argument.

OpenCode

carga la skill autonomous-delivery, modo bug (load the autonomous-delivery skill, mode bug)

No slash command: the routine's prompt names the skill and the mode.

Codex

carga la skill autonomous-delivery, modo bug (load the autonomous-delivery skill, mode bug)

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:autonomous-delivery bug

Slash command with the /skill: prefix. In a new folder, /trust once.

When you set up the routine, leave the scheduler's worktree option off. The skill creates and closes its own isolation on every host: that way phase 4 can delete the run's worktree instead of leaving it on disk for a human.
12 · around this skill

Who it works with

It selects and dispatches; every stage of the work is done by its owner. Out of scope are QA verification, which starts from the ready-for-QA state, and choosing what to build, which is product and escalates.

Dispatched · story and bug

/sprint-development

Implements, reviews and deploys each ticket. Its Stage 4 close is what phase 4 verifies.

Dispatched · discovery

/product-management

Refinement, epics and criteria: the only skill that calls the discovery mode.

Alongside · git

/git-flow-master

Branches, pull requests, merges, conflicts and the planning of PR chains.

Upstream · edges

/project-context dev-roadmap

When the edges or the order in .context/dev-roadmap.md are stale or missing.

Optional · workers and routines

/orca-orchestration

Launches, supervises and closes the dispatched workers, and registers the run as a scheduled routine. Only when it passes its gate; the what stays with this skill.

To read more: .agents/skills/autonomous-delivery/SKILL.md and its three references in references/ (audit-and-selection.md, hazard-catalogue.md, run-report-format.md). Related doctrine: agentic-dev-core/references/decision-protocol.md and session-management.md.

The idea behind it. Shipping is what goes out; a state you can resume from is what is not negotiable. A run with nobody watching is worth the record it leaves: what was true, what it chose and why, what it could not check.
