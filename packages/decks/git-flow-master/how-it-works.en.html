00 · the version control layer

What was decided for the repo, applied on every push.

/git-flow-master is the single entry point for everything that happens in git: branches, commits, pushes, pull requests, conflicts and PR chains. It assumes no branching model: it reads the one the project chose, checks what the host enforces for real and adapts every command to that.

for whoever codes and whoever leads the repo the strategy lives in .agents/project.yaml it merges on evidence: auto-merge once the checks pass

01 · when to use it

Every time the work touches git

It fires even if you do not name it: if the request looks like a branch, commit, push or PR, it is this skill. The other skills in the repo hand off to it when they reach that layer.

Use it when

Code has to move through git

  • You start work: "start work on PROJ-123", create a branch.
  • Commit and push: "commit and push", "subir cambios" (push changes).
  • Open a pull request: "abre un PR contra staging" (open a PR against staging).
  • There are conflicts or the push was rejected.
  • A change is going to end up huge and has to be split into several PRs.
  • You want to choose or change the repo's branching strategy.
Do not use it for

Anything that is not version control

  • Implementing a feature: that is /sprint-development, which calls this skill for the PR.
  • Writing tests: that is /unit-testing.
  • Refining the backlog: that is /product-management.
  • Editing code in general: the skill works strictly on the version layer.
If the request is ambiguous ("hagamos lo de git", let's do the git thing), the skill does not guess: it reports the repo state (Step 1) and asks what you need.

03 · Step 2 · the branching strategy

A default is not a decision

The strategy is stored in the git_strategy block of .agents/project.yaml and read on every invocation. It is never inferred from a skill example or from another project.

Strategy Shape Working branch comes from The PR targets
solo-main A single long-lived branch, main. Everything lands directly. main main, when there is a PR
main-integration main + an integration branch (staging or similar). integration integration
enterprise Integration + many feature/*, release/*, hotfix/*. integration (hotfix: main) integration (hotfix: main)
trunk-based Only the trunk; branches under a day old, behind feature flags. main main
gitflow main + develop + release and hotfix. develop (hotfix: main) develop; release and hotfix: main
github-flow main always deployable; branch, PR, merge, deploy. main main
gitlab-flow GitHub Flow + environment branches (pre-production, production). main, which is its integration branch main; promotion goes through the environments

How it finds it

First the block: if git_strategy.strategy has a value, that is the decision. If not, it looks at the branches (only main, main + an integration branch, many feature/*) and the repo hints (.gitlab-ci.yml, release/* branches). If nothing is enough, it shows you the catalog and you pick. It never picks silently.

Chosen or inherited

The boilerplate ships the block filled in with solo-main. What separates "this project chose solo-main" from "nobody chose" is meta.strategy_source: inherited or chosen. Only Strategy Setup stamps chosen.

The offer, never the execution

If the block is missing in a new repo, if the project is not configured yet (project.project_name empty), or if the project already has a name but the strategy is still inherited, the skill offers Strategy Setup once per session and tells you what the default costs: no integration branch, no promotion path, no review gate of its own. A "no" carries on with the strategy in place, writing nothing.

04 · operation · Strategy Setup

A questionnaire, branches only if needed, one block written

It is the only operation that creates long-lived branches and writes the git_strategy block. The other operations adapt to what this one leaves behind.

Question Applies to Options (default first) Stored in
Q1 · integration → production promotion strategies with an integration branch fast-forward only · merge commit · squash decisions.promote_method
Q2 · merging the working branch multi-branch strategies merge commit · squash · rebase + merge decisions.feature_merge
Q3 · hotfixes production differs from where work happens branch from production + same-day back-merge · always through integration · no policy decisions.hotfix_policy
Q4 · protected branches all strategies direct push, merge mode, admin bypass, minimum reviews policy.*
The AI does

Resolves the strategy, skips the questions that do not apply or are already answered, creates the branches the answers imply and syncs by fast-forward only.

You decide

The strategy and each questionnaire answer. Once you answer, the branches are created with no second OK and reported.

Output

The git_strategy block written in place inside .agents/project.yaml, with strategy_source: chosen and policy_source: declared.

Gate Never --force, not even --force-with-lease. If integration and production diverged in both directions, the sync stops and hands over to conflict resolution.
The sync push follows the push policy like any other push. At the end, Setup offers to carry the policy to the host with bun run git:policy: read first, then a dry run, and the write only with your yes.
05 · operation · push

The variable decides whether the AI asks

Before pushing to a protected branch, the skill resolves git_strategy.policy.direct_push_to_protected (AGENTS.md, Critical Rule #4). The answer is never written in the rule: it is in the value.

Value What the AI does
allowed Pushes without asking and without a gate. The stored value is the standing authorization; asking anyway would turn allowed into confirm.
confirm Asks before every push and waits for a yes. A team chose this value on purpose, so the ask stays.
forbidden Does not push to the protected branch: it opens a working branch, pushes it and sends the change as a PR, with no question.
evidence Pushes without asking only when the pre-push gate passes (the hook runs bun run edd gate). On a fail: no push, no question, fix forward and retry.
block missing or null Reads as evidence.
Before the push

The state picks the command

  • No upstream: git push -u origin <branch>.
  • Upstream behind: git push.
  • Upstream diverged: it stops and hands over to conflicts. It does not force.
Admin bypass

Only offered, and with a double check

  • Only if policy.admin_bypass: true.
  • It asks whether you really are an admin: the skill cannot know your role.
  • It confirms the specific irreversible action with you.
  • With false, it never offers it.
Which branches count as protected comes from the strategy: main always, the integration branch when there is one, develop in gitflow and release/* in enterprise. On any of them, never --force, --force-with-lease or --no-verify without an explicit request from you and a branch nobody else uses.
06 · Step 1b · parity with the host

What is declared is intent; what rules is the host

The policy block records what the team decided. GitHub records what is enforced. They drift apart, and the surprise arrives at the worst moment: a merge rejected halfway through. That is why the reconciliation is a script, not a procedure.

Command Reads the host Writes What for
bun run git:policy plan no nothing See which ruleset derives from the block.
bun run git:policy verify yes nothing On the first push, PR or merge of the session. Exits 1 on an unaccepted drift.
… verify --stamp yes meta.policy_verified y policy_source Record the reconciliation when it is clean.
bun run git:policy apply yes nothing (dry run) Show the exact payload before proposing the write.
… apply --yes yes the host ruleset Write, with your choice. Never to cover a drift you did not read.
What the script knows

Two mechanisms, and a push proves nothing

  • It checks classic protection and rulesets. A 404 on the classic one does not mean "no protection".
  • A push that goes through does not prove there is no rule: admins skip it and the rule still applies to everyone else. If the remote says Changes must be made through a pull request, it was a bypass.
  • require_code_owner_review without a CODEOWNERS file is not strict: it is impossible to meet, and every merge ends up being a bypass.
On a drift

It is reported, never fixed on its own

  • (a) fix .agents/project.yaml so it matches the host;
  • (b) change the host configuration;
  • (c) accept the difference and note why in policy.accepted_divergences.
  • Any of the three needs your choice.
# an accepted divergence: one verify field, with its reason git_strategy: policy: accepted_divergences: - field: main.direct_push_to_protected enforced: blocked (pull_request rule) accepted: <sign-off date> reason: why the two sides differ on purpose
Accepted is not silenced. verify lists it as ACCEPTED with its reason and exits 0; --stamp records policy_source: accepted, different from verified.
An old exception shows up by itself. An accepted divergence that no longer matches any drift is reported as a note, so the list does not collect dead exceptions.
apply loosens nothing without permission. Removing a guard, lowering approvals, turning off code-owner review or widening the merge methods requires --allow-loosening for that specific waiver.
What is not verified is called that. With policy_source: declared, the AI does not tell you what the remote requires: it says "declared, not verified".
07 · operations · branch and commit

Branches with a picked name, commits with a single reason

The AI picks the branch name, groups the commits, runs them and reports what it did. It asks for no OK on a branch name, a commit set or a PR body: the only stops are the closed list in .agents/skills/edd/references/human-gates.md.

Branch

Prefix + key + slug

  • Prefix by the dominant change: feat, fix, refactor, test, docs, chore, in that order of precedence.
  • With a key: feat/PROJ-123-bulk-assign. Without a key: refactor/split-auth-utils.
  • It branches from the base branch the strategy sets.
Commit

Conventional, atomic, explicit

  • One commit, one responsibility. Tests go with the behavior they prove.
  • feat(PROJ-123): add bulk-assign action.
  • Never git add -A or git add .: each path, by name.
  • If a hook rejects the commit: fix the cause and make a new commit, never --amend.
feat(PROJ-123): add bulk-assign action Optional body: the outcome, not the list of files. Worktree: <name|primary> Session: <label>
The trailers are forensic, not attribution. The last two lines of every commit an agent session writes say which checkout and which session produced it, copied from the AGENT IDENTITY: line the prompt hook injects (unknown if it cannot be resolved). They name no tool. Forbidden: "Generated with…", an AI Co-Authored-By: or any branded trailer such as Claude-Session:. .husky/commit-msg runs scripts/check-commit-trailers.ts and warns, without blocking.
One more trailer can go above those two. When the docs contracts gate names a LINT.IfChange region, and the pages it cites were not touched and still describe the behavior correctly, the commit carries Docs-Checked: <label> <reason> above Worktree: and Session:. Never by reflex and never without a reason: a label alone does not count, and the pre-push hook and CI block the push without that trailer or without the page edits.
08 · operation · pull request

It opens with full context and merges on evidence

The base comes from the strategy, the body is built on the spot, and the merge follows git_strategy.policy.merge_mode.

Base and title

The base is the one the strategy sets (table in section 03). If you change it with --base, the AI flags it against the default. The title follows the commit format, under 70 characters.

Body

Summary, Changes, Test Plan, Traceability (issue, branch, base, strategy, worktree and session), Evidence and Merge danger (way in or way back, blast radius and rollback). What the skill cannot complete stays visible so you can edit it: it is not deleted silently. The body carries the evidence block printed by bun run edd render --pr and goes out with gh pr create --body-file, with no review round first.

Labels, reviewers, draft

Set before review, without asking: labels only from gh label list (never invented), the owner of the work as assignee, a reviewer only under human-approves (from CODEOWNERS).

Merge by mode

auto: once bun run git:policy verify --merge {base} exits 0, gh pr merge --auto --{method}, and GitHub merges when the checks, edd/evidence included, pass. human-approves: the same call, and a person approves. manual: it opens the PR and stops. The method is a merge commit unless decisions.feature_merge says otherwise.

After opening: the watcher

It arms .agents/skills/edd/scripts/pr-watch.sh on its own PR, labels the terminal tab and ends the turn. On merged: git fetch and git merge-base --is-ancestor confirm the merge is on the base.

How many approvals are missing, and according to whom

With the policy verified it says "the host requires N approvals on the base". With the policy only declared it says "declared require_pr_reviews: N, not verified against the host".

Gate No --auto before bun run git:policy verify --merge {base} passes; on a protected base that fails it, the skill stops and tells you. The gate catches mistakes and drift, not a deliberately forged check.
09 · operation · conflicts

Diagnosis before the fix

A wrong fix here costs hours. The AI looks at git status, git diff --check and the state files in .git/ to know what happened before resolving anything.

explain the cause→ safest option→ resolve step by step→ verify→ how to avoid it
Merge and rebase

Content, renames, rebase

Content conflicts, rename or delete conflicts, and rebase or cherry-pick conflicts.

Branches

Rejected push, loose HEAD

Diverged branches, rejected push, detached HEAD, unrelated histories.

Local work

Stash and hooks

A conflict when applying a stash, or a pre-commit hook that rejected the commit.

When in doubt

Aborting wins

git merge --abort, git rebase --abort: aborting always beats guessing.

Destructive options are never picked silently. The AI resolves a non-destructive conflict itself and reports it. Force push, hard reset, a rebase skip that drops commits or aborting a merge with uncommitted work are presented to you as an option, with their risk, and wait for your decision; so does a conflict whose two sides disagree on product behaviour.
10 · Step 4 · chained PRs

Over 400 lines: it gets split, and the decision travels with its trace

Above that review budget, defect detection drops sharply. Before opening PRs, the skill walks a tree of three questions and stops at the first leaf.

Question If yes If no
Q1 · is it mostly mechanical? (rename, formatting, generated code) size-exception: one PR, the AI's call, with a Why size-exception: line go to Q2
Q2 · does it split into 2 to 4 independent slices, each safe on its own on the base? stacked-to-main: small PRs on the base go to Q3
Q3 · is there shared scaffolding that a partial merge would break? feature-branch-chain: one integration branch, child PRs, one final PR decompose the story again: it is a planning smell
Chain strategy: feature-branch-chain Decision trace: Q1=No (new domain logic, not a rename) · Q2=No (slice 2 does not compile without the types from slice 1) · Q3=Yes (shared schema used by slices 2 to 4) → feature-branch-chain Decided by: /git-flow-master §Chained-PR decision tree (branching-strategies.md)
A label alone is not a decision. /sprint-development blocks its Stage 2 on this answer and rejects a strategy name without a trace. Each answer carries the reason for this change, and this skill is the only authority that can fill in those lines. If the real diff exceeds the estimate, it is decided again: the budget is not stretched silently.
11 · isolated work

One session, one worktree, one branch

A worktree is a second working directory over the same .git, with its own branch and its own index. It is useful for two parallel AI sessions, a hotfix with a feature open, or risky work you do not want to mix in.

create→ bun run worktree:provision→ work→ bun run worktree:audit <wt> --rescue→ remove

Create: git is the canon, the harness is a shortcut

git worktree add ../dir -b feat/x main works on any host. A harness's own tool (in Claude Code EnterWorktree, or a worktree managed by Codex) is a harness path, never the repo canon, and needs the same two steps around it. OpenCode has no equivalent: it uses git.

Provision before working

A new worktree brings only the versioned files. worktree:provision copies the ignored inputs that cannot be rebuilt (.env, .vercel/, local settings), installs dependencies and creates the .claude/skills alias. The list lives in code: PROVISION_COPIES in cli/lib/worktree.ts.

.session/ is never copied

Durable state (plans, progress, locks, reports) lives in <<PRIMARY_ROOT>>, the main checkout, and is cited by absolute path from the worktree. A copy silently diverges and dies with the worktree.

Audit before removing

worktree:audit is read-only and exits 1 while there is state that lives only in the worktree; --rescue copies it to the main checkout without overwriting anything. With Orca, the versioned orca.yaml runs both steps as setup and archive hooks, but the CLI skips the archive hook unless given --run-hooks; without hooks, run bun run worktree:audit <wt> --rescue by hand.

What is not versioned does not travel. A new file without git add stays in the original directory: move it, or commit it before creating the worktree.
Stash is repo-wide. It is not a way to pass work between sessions: commit on your branch.
Provenance is in the commit. The Worktree: and Session: trailers say who wrote an orphan branch. An old worktree is reported, never deleted if it belongs to another session.
12 · safety rails

What the skill never does

The full list lives in SKILL.md (Compact Rules, which already gather the critical rules and the antipatterns). These are the ones most visible from the outside.

It does not rewrite pushed history. No force push to a shared branch, and no --amend or rebase on commits already published: a new commit is added.
It does not discard changes globally. Never git restore ., git checkout -- ., git reset --hard, an untargeted git stash or git clean -f: another session may be in the same tree. Only paths this session modified (Critical Rule #13).
It does not commit secrets. .env, credentials or tokens in git are forever; that is why each path is added by name.
It does not chain PRs without naming the dependency in the body of each one.
It does not quote examples as configuration. The blocks in references/ are illustrations; the answer about a project comes from its own .agents/project.yaml, quoted.
It does not fake a PR. If gh is missing or not authenticated, it stops and tells you.

The slash loads the skill; the rest of the phrase picks the operation.

No slash: you name the skill in the phrase.

Same pattern as OpenCode, in the CLI or Desktop.

The core idea. Git policy is decided once, stored in one place and checked against the host. After that, every branch, commit, push and PR applies it without anyone having to remember it. The AI executes and delivers on evidence; you choose the strategy, accept or reject the divergences, and approve only where merge_mode asks you to.
