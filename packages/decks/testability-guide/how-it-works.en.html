00 · the app, ready to test

A page that explains how to test the app, and a closed place where the credentials live.

/testability-guide generates a public page inside the app, /qa, the Software Testability Guide for QA, and builds a separate credentials artifact that you publish wherever you choose. The page teaches how to test the app across the database, API and interface layers; the artifact holds the real values. When you run it again, it detects what changed in the stack and patches only that.

for people who code and people who lead runs after the app exists the page never carries a secret

01 · when to use it

When there is a real app that someone has to test

It describes an app that already works. Against an empty scaffold there is little to document, and the skill tells you so before going on.

Use it when

QA needs a front door

  • Human testers or AI agents need a single page inside the product that explains how to test it.
  • You want to create or refresh the credentials artifact behind the page's button.
  • The stack moved (auth changed, the database was migrated, a new MCP appeared) and /qa went stale.
  • You ask for "guía de testeabilidad" (testability guide), "credenciales para testing" (credentials for testing) or "update /qa page".
Do not use it for

What belongs to another skill

  • Defining the product (PRD, journeys, architecture): /project-foundation.
  • Setting up backend, frontend, OpenAPI, auth or env: /project-bootstrap. This skill can run when that one finishes.
  • Implementing a story: /sprint-development.
  • Unit tests: /unit-testing.
  • Formal test cases or a test management system: out of scope.
02 · two artifacts

A public page and a closed artifact that point to each other

They are never duplicated. The page's button opens the credentials destination, and the artifact's footer links back to /qa.

Page /qa (in the app) Credentials artifact
Holds Placeholders and the procedure The real values and .env blocks to copy
Who sees it Readable by anyone who reaches the page Only the QA group, with the destination's native permission
Answers "How do I test?" "What do I paste?"
Where it lives In the repo, at the path you choose (default /qa) A Jira epic by default, or Confluence, Notion, another tool, or pasted by hand. Never in the repo.
"Public" means public documentation, not public credentials. If the product is an internal tool or a customer-facing product where an operational page would leak information, the skill closes /qa in production. If it is a practice platform where the page is the front door for external testers, it leaves it open on purpose. It detects this in discovery; if it is not clear, it asks you.

04 · phase 0

Two different memories: the session and the snapshot

The skill keeps state in two places that solve different problems. Mixing them up is the easiest mistake to make.

Within a run

.session/testability-guide/

  • Holds plan.md and progress.md. Detects an interrupted run: for example, the AI cut off between the page and publishing.
  • Phase 0 reads it first. If it exists, it shows you the goal, the last completed phase and the next one, and waits: resume, restart (archives it) or abort.
  • When it finishes cleanly, the folder moves to .session/.archive/.
Between runs

The qa-guide-snapshot comment

  • Lives at the very top of the generated page file and is committed.
  • Detects code drift: the stack changed between two complete runs.
  • Phase 2 reads it. It survives the session being archived: it is the signal for the next invocation.
05 · phase 1

Discovery: everything is detected, nothing is guessed

The same generator runs against very different projects: one with Supabase Auth and Redoc, another with its own JWT login and Swagger UI. A hand-written route goes wrong in most of them.

The AI detects

Framework and version, UI kit, icons, light/dark theme, language, auth model (every one it exposes), login endpoint and token shape, docs UI and the OpenAPI spec route.

Database engine and QA role, MCP config files per agent, how the .env gets activated, mono or poly repos, default branch and where the deploy SHA comes from.

It never does

Read .env or credentials files. From .env.example it lists variable names, never values.

Install anything, start the dev server or run the suite: that is phase 8.

Output

A short paragraph that feeds the snapshot, the page's qaConfig object and the idempotency diff.

Whatever was not detected stays as an explicit gap (<detected: none>), and the page says "ask your lead". Never an invented value.

In the same phase: how testable is the product?

It scores three layers. The page is built the same way at any score; what changes is the flag and the recommendation you get.

Layer Testable when… If missing
UI Critical flows (login at minimum) have stable selectors, data-testid or role. Flag and a recommendation for a selector convention.
API There is a programmatic path to a token for Authorization: Bearer, with expiry, and a discoverable contract. High flag. It recommends a normal password login plus an endpoint that issues a token with expiry.
DB A read-only QA role exists to inspect without the app in the middle. Flag. If there is only a superuser, the run stops (see security).
It recommends, it does not build. The token endpoint, the data-testid attributes or the QA role are work for /project-bootstrap or /sprint-development. And a passwordless login is not deficient by itself: if there is also a personal token issuer, the API counts as testable.
06 · phase 2

Idempotency: running it again never rewrites from scratch what did not change

If /qa already exists, the AI reads the snapshot, repeats discovery and compares field by field. It shows you the diff before touching anything. 

/* qa-guide-snapshot
   skill-version=…  stack=…  ui-kit=…  auth-method=…  docs-route=…  openapi-spec=…
   db=…  repos-shape=…  mcp-config-files=…  page-features=…
   language=…  publisher=…  credentials-source=…  default-branch=…
   build-sha-source=…  testability=…  generated=…  content-hash=…
*/

shape of the comment, with the values omitted · the canonical field list lives in references/idempotency-snapshot.md

Diff result What happens
No-op Only the date or a minor version changed. Reports "up to date" and exits.
Surgical patch A field that affects code changed (stack, auth, database, language…). The sections that field drives are regenerated, only those; the rest stays byte for byte the same.
Re-publish only The credentials destination changed; the page is not touched.
Page upgrade The page is from a flatter version (no highlighting, no request cards). It offers it to you; it never applies it on its own.
Full re-scaffold A major jump in skill-version or three or more code fields moved at once. Only with your OK, and it keeps a copy of the previous page.
Your hand edits

They are respected

  • Whatever sits between qa-guide:user-region:start and :end survives every patch.
  • If a patch lands on top of a region of yours, the AI shows you the conflict before writing.
No snapshot

It asks before overwriting

  • A /qa with no comment (or an unreadable one) is treated as hand-made: "shall I take it and regenerate it with a snapshot?"
  • The content-hash is written in two passes: a placeholder when generating the page and the real hash after publishing.
07 · phase 3

Your decisions, in a single message

The questions arrive together, each with its default and its cost. You can answer "all defaults". Whatever you already said in your initial request is fixed and is not asked again.

Question Default What to know
Q1 · credentials destination Jira epic The body is portable: switching destination later is cheap.
Q2 · database role for testers Read-only qa_* role Writes go through the API. A superuser is always rejected.
Q3 · page route /qa Unless it clashes with the host's route architecture.
Q4 · redirect from an old route Yes, if there is a sibling page Server-side redirect; the old route stays alive for one release cycle. With no sibling, it is skipped.
Q5 · language of the visible text The host's Follows the app's language signal. With no signal, it asks you; if nobody can answer, it writes in English and reports it. Identifiers and data-testid stay in English.
Q6 · code highlighting Pre-answered by detection Reuses the host's; if there is none, server-side Shiki.
Q7 · UI driver for agents playwright-cli if its skill is present; the Playwright MCP as an alternative.
Q8 · request viewer Postman-style cards; curl blocks if the kit cannot.
Gate once you answer, .session/testability-guide/plan.md is written; when you accept it, it goes from draft to approved and only then does phase 4 begin. On a surgical patch, only the questions whose value changed come back.
08 · phase 4

The page: sections §1 to §7, one config object

Its own layout with a fixed index and a hero, not a list of accordions. Every value the page shows comes from qaConfig, the bridge between detection and rendering.

§1 · Credentials, at the very top

The first thing a tester sees: a button that opens the credentials destination in another tab. With no destination detected, a gap and no button.

§2 · Architecture and repos

Frontend → API → database with the detected stack, the MCP layer underneath, and the official repos (one if it is a monorepo, two if it is a polyrepo).

§3 · The three forces (trifuerza) and the .env

UI + API + DB, and how the variables get loaded: the agent opens without them, each MCP reads its .env at startup and a command that needs a value runs with bunx varlock run. If one fails to load, the MCP returns 401/403 and you have to exit, fix it and come back in.

§4 · Database, two paths

The database MCP or a URI for the editor's SQL extension, with the same read-only role. The MCP comes from the stack: block of .agents/project.yaml: DBHub by default, and a Supabase app adds the Supabase MCP tab as well, also read-only. Roles, revoked columns or the RLS test, only if the project has them.

§5 · API, two paths

The project's real auth requests, the OpenAPI MCP or the Postman one, and the link to the detected docs UI. The OpenAPI MCP only lists endpoints and reads their schemas: authenticated requests run with curl and each tester's personal token. With no path to a token, it says so: it never invents an endpoint.

§6 · UI with Playwright

A fixture that bridges UI and API according to the detected auth shape, and the playwright-cli cookbook for agent-driven exploration.

§7 · Quick reference

Demo users, an endpoint table taken from the spec and the most common errors.

Adapts to the host

Uses what the app already has

  • The host's UI kit, icons and light/dark theme mechanism. No parallel system.
  • The framework's idiomatic route (App Router, Pages, Remix, Astro, SvelteKit, Nuxt, Vite with React Router). Any other framework: it stops and asks you.
  • A data-testid on every interactive element, one per node.
Dependencies

A single exception

  • It adds no dependencies. A component is missing: it creates it locally, in the host's style.
  • The exception is a syntax highlighter that runs on the server (Shiki or whichever the host already uses): zero JavaScript on the client. And it is skipped if the host forbids new dependencies.
09 · the build stamp

Which deploy am I looking at? The page tells you

Under the subtitle, the page shows the short SHA of the deployed commit, linking to the commit when a repo is detected. A finding is tied to a commit, and "is my fix in yet?" gets answered on the page itself.

How it reads it

At runtime, on the server, from the platform variable whose name detection noted in qaConfig.build. On Vercel it is VERCEL_GIT_COMMIT_SHA.

What it never does

Write the SHA into the /qa code: it would be stale on the next deploy.

Show other platform variables next to it (commit message, author, secrets).

No SHA

Locally, or on a deploy without git metadata, the same node shows a visible line: build local, sin SHA de despliegue (local build, no deployment SHA).

The qa-build-sha node is always there, with the full SHA in data-sha (empty in the fallback), so automation can read it.

A redeploy is never drift. The snapshot stores only the variable name (build-sha-source), and the content-hash covers the credentials body, which does not carry the SHA. When the change reaches a deployed environment, verification compares data-sha with the commit that environment should be running and confirms a deploy exists for it. An empty data-sha there means the source is missing: you fix the source, you never write the value by hand.
10 · phases 5 and 6

Credentials: written once, published wherever you choose

The markdown body of references/credentials-content-template.md is the single source of truth. Each destination is a thin adapter that changes the wrapper, never the content.

What it holds

Straight to the point

  • Who the audience is and the "what lives here and what lives in /qa" box.
  • Environments table, from environments in .agents/project.yaml.
  • UI auth: each tester creates their own user (default, with self-service sign-up or magic link) or a table of shared demo accounts, when there is no sign-up of its own.
  • DB auth: the raw URI for a SQL editor and the separate fields the MCP reads. They are not interchangeable.
  • API auth: a .env block with the base URL and the spec URL, with no slot for the token; each tester generates their own and uses it by name with curl.
  • How to activate the MCPs, security and a footer that points to /qa.
What it never holds

A secret written by the AI

  • Every sensitive value comes out as the literal <see secrets store>. A person fills it in inside the destination, where the audit trail stays.
  • The body is not written to any file in the host's repo.
  • Not even when pasting by hand: a chat can be captured or logged.
Destination (Q1) Tool Detail
Jira epic (default) /acli Markdown → ADF with the acli skill's converter; every snippet comes out with a copy button. Tables are built by hand and verified by reading the epic back.
Confluence page /acli or the Atlassian MCP Page restriction to the QA group.
Notion page Notion MCP if present Shared only with specific people.
Another tool with an MCP or CLI The detected MCP or CLI For example a secrets manager or an internal wiki.
Pasted by hand None It hands you the body and the steps; you give it back the final URL. It warns if the URL looks public.
If there is no tool

Falls back to pasting by hand

  • Destination chosen but no MCP or CLI available: the body is never lost. It tells you what to install or where to paste.
If the tool fails auth

It stops

  • A 401/403 does not trigger the fallback: it hides the real problem. It names the .env variable and asks you to restart the agent session, because the MCP reads the environment at startup.
After the first publication, the artifact belongs to a person. The lead fills in the real values inside the destination. That is why a re-run first reads the current body: if it was curated by hand, it does not overwrite it. It offers to leave it untouched with a comment pointing to the refreshed /qa (recommended), a guided merge, or overwriting and accepting the loss of what was curated. Leaving it untouched is a successful result.
11 · phase 7

Security audit, before anything goes out

It runs before any publish call and applies to every adapter: none can skip it. If a point is not met, nothing is published.

Never a superuser or schema-owner credential. If it is the only one available, it stops and hands you the SQL to create a read-only qa_* role. Even if you insist, it does not write it into the artifact.
Never secrets that sign sessions (NEXTAUTH_SECRET, JWT keys, server-side OAuth secrets). If they appear with a value in .env.example, it stops and recommends rotating them.
Never production write credentials. Only the read role; writes go through the API.
Never re-publishes something that already leaked into git history without rotating it first.
On the page: no credentials, no private hostnames, no third-party analytics or scripts. Demo accounts of intentionally public scope may show their password; each tester's own never. When in doubt, emails only.
On the destination: access closed with the native permission (restricted view of the epic, page restriction, sharing with specific people).

at the end of every run an audit trail is left: destination, artifact URL, path, whether a superuser was rejected, whether rotation is needed and the testability flags

12 · phases 8 and 9

Verify in order, and let the work come in through a PR

"Done" means every check in references/verification-checklist.md passed. If one fails, it gets fixed and you start over from the first.

Types, build and lint

With the scripts the host's package.json declares, never one assumed. Lint rules are not turned off: the page gets fixed.

Browser smoke

With /playwright-cli against the dev server: loads, title, build stamp, the button opens the destination in another tab, the code blocks, the redirect if there was one, and a screenshot for the PR.

The destination looks right

A person confirms this one: snippets with a copy button, closed access and the link back to /qa.

The diff has no secrets

No passwords, no tokens, no private hostnames, no literal SHA inside app/qa/.

Complete snapshot and self-check

The hash placeholder has already been replaced by the real one. And the closing questions: did it read the code before writing?, the credentials at the very top?, the PR against the detected default branch?

Commit + PR

Delegated to /git-flow-master with the branch name, the commit messages and the PR title. The skill never pushes, opens the PR or touches branches on its own.

The push policy

Whether something can go straight to a protected branch is not this skill's call: it is resolved by /git-flow-master with git_strategy.policy.direct_push_to_protected from .agents/project.yaml.

When it finishes

The session is archived in .session/.archive/. The snapshot stays on the page: it is the signal for the next run.

14 · security rails

What the skill never does

The full rules live in the frontmatter of SKILL.md (compact_rules) and travel in the compact registry that subagents receive (.agents/skills/REGISTRY.md).

It does not write credential values in the page or in the artifact's body: it references variables by name.
It does not skip drift detection or regenerate from scratch when a targeted patch is enough.
It does not close /qa in production by reflex: only when an operational page would leak; a practice platform leaves it open.
It does not use real data: no PII and no production data. Only demo users and sanitized fixtures.
It does not duplicate the credentials body across destinations: one source, thin adapters.
It does not assume nothing changed without re-reading the snapshot and comparing it to the current stack.
It does not write the deploy SHA into the code: it is read at runtime.
It does not go on without the tool it needs: if library documentation or web search is missing at the step that requires it, it stops and tells you which one is missing, with no silent substitute.
15 · what you tell the AI

Invoking it in each terminal

This skill has no named modes: the same invocation creates the page the first time and updates it the next times. You name the skill and say what you want, in Spanish or English.

Claude Code

/testability-guide create the QA guide page

The slash loads the skill; the rest of the sentence supplies answers ahead of time.

OpenCode

load the testability-guide skill: testability guide

No slash: you name the skill in the sentence.

Codex

load the testability-guide skill: update /qa page

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:testability-guide create the QA guide page

Slash with the /skill: prefix. In a new folder, /trust once.

What you say in the request already counts as an answer. "Publish the credentials as a Jira epic, page at /qa, text in Spanish" fixes Q1, Q3 and Q5: the AI confirms what is fixed and only asks about what is missing.

The underlying idea. Testing well starts with knowing how to get in. The page teaches the way in without a single secret; the artifact keeps the secrets behind a door with permissions. And every time the stack changes, the skill patches what moved and leaves your edits where they were.
