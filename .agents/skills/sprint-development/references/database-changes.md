# Database changes: read the ledger, apply through the DB MCP, verify

> Cited from: `SKILL.md` → `## Stack parameters` and input 9 (the migration trigger); `references/implement-story.md` Paso 2; `references/story-plan.md`; `autonomous-delivery` → Migration gate.

Every schema, RLS, function, trigger or seed change a story makes goes through the project's database MCP (capability `db`, `[DB_TOOL]`: Supabase, or a server of the same Postgres family). The MCP exposes the migration history itself, so nobody keeps a ledger by hand. What changes from project to project is who OWNS that ledger, and `{{stack.database.migrations_tool}}` in `.agents/project.yaml` names it.

## 1. Before any schema work

1. **Load the stack skills**: `/supabase` + `/supabase-postgres-best-practices` before the first schema, RLS, function or migration call (`agentic-dev-core/references/skill-composition-strategy.md` §3.5: not installed → say so once with the install path, then continue).
2. **Read the migration history through the MCP** (`[DB_TOOL]`, the tool ending in `list_migrations`) and the current shape of what you are about to touch (`list_tables`, or a read-only `execute_sql` on the catalog). Do it immediately before writing the change, not at planning time: a peer can apply one in between.
3. **Know which database the MCP points at.** It is the one `{{DB_PROJECT_REF}}` names for the active environment. A story never changes production; production is Stage 5, and only for a change already applied and verified on the integration environment.
4. **Read the record**: `.context/ADR/` and the data map's `migrations` and `access-control` sections (`bun run context:map business-data-context --section <id>`), so the change honors a settled decision.

## 2. Applying the change, per `{{stack.database.migrations_tool}}`

| `migrations_tool` | Who keeps the ledger | How the change is applied | What lands in the repo |
|---|---|---|---|
| `supabase-mcp` (greenfield default) | the database itself; the MCP's migration list IS the ledger | the MCP's migration-apply tool (`apply_migration`), one call per logical change, with a descriptive snake_case name | no migration file (`{{stack.database.migrations_dir}}` is null). The exact SQL applied goes in the PR body; an ADR records it when the change is architectural |
| `supabase-cli` | the same Supabase ledger table, mirrored by the files in `{{stack.database.migrations_dir}}` | the MCP's migration-apply tool, as above | the migration file, committed in `{{stack.database.migrations_dir}}` with the EXACT SQL applied and named with the version the MCP recorded (read it back from `list_migrations`), so the CLI and the database agree on what ran |
| `prisma`, `drizzle` | the tool's own ledger table, written only by the tool | the app's own tool, through the app's own script (read its name in the app's `package.json`); never the MCP's apply call, which would bypass that table and make the tool's next deploy fail or re-run | the migration in the tool's format, generated by the tool in `{{stack.database.migrations_dir}}` (plus the schema file it keeps). The MCP still reads the history before and verifies the live schema after |
| `none` | no ledger | a story that needs a schema change STOPS and reports it: the project has not chosen how its schema changes | nothing |

`{{stack.database.engine}}` = `none` means the app has no database: a story whose plan needs one is a finding for the user, never a database invented mid-story.

## 3. After every apply

- **Re-read the live definition** (the table, the policy, the function body) and diff it against the SQL you meant to apply. Do it on re-applies too. Typing SQL into an apply call by hand has dropped a clause before, caught only by this diff.
- **Regenerate the database types** when the app keeps them (`{{stack.database.types_path}}` non-null): `{{stack.package_manager}} run {{stack.scripts.db_types}}`, or the MCP's type-generation tool when that role is null. Read the regenerated file before committing it: generating from a shared live database can import a peer's unmerged tables (strip them only after proving nothing in your diff uses them, and say so in the PR body).
- **Re-read `list_migrations`** and confirm your change is the newest entry under the name you gave it.

## 4. Rules that hold whatever the tool

- **Never apply a change merely to clear a local error.** A local failure that seems to need a live schema change is a finding, not a step.
- **Destructive changes are confirmed first.** A drop, a rename, or a `CREATE OR REPLACE` that changes an existing live object's output stops for the user's OK, naming the target environment and what breaks. An additive change (new table, column with a default, index, new function) follows the story plan. `/autonomous-delivery` replaces this with its own Migration gate.
- **Fleet mode**: a worker never applies to a shared database; the conductor applies in merge order (`references/fleet-mode.md`).
- **RLS and DEFINER functions** keep their own gates: `references/rpc-authorization.md`.
- **No credentials in SQL, plans or PR bodies.** The MCP authenticates from the session's environment (Critical Rule #9: an auth failure STOPS the run).
- **The record**: the PR body carries the SQL applied and the `list_migrations` entry it produced. When the change is architectural and hard to reverse (a tenancy column, a new access model), an ADR records it with the migration name, so the history survives even when no file does (`agentic-dev-core/references/adr-doctrine.md`).
