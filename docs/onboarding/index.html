Agentic Dev Boilerplate

AI-driven development on Next.js + Supabase + TypeScript.

A skill-based practice that pairs your codebase with an AI agent. The agent reads a structured knowledge layer, plans features, writes code, opens pull requests, deploys to staging, and hands off to QA — with human checkpoints between every stage.

1.The fundamental idea

This repository is an AI-driven development boilerplate. It does not ship a backend or a frontend; it ships the instructions, the knowledge layer, and the tooling that an AI agent uses to build a Next.js + Supabase application on top of it. The repo is a starter — you scaffold the actual app inside it via /project-foundation and /project-bootstrap, then drive feature work through /sprint-dev.

For the machine to work, three families of moving parts cooperate: Skills orchestrate long, multi-phase AI work; Commands perform one-shot utilities; and Scripts are what you run yourself in the terminal to keep the configuration substrate healthy. All three feed off the same fuel — a system of variables defined in .agents/project.yaml that resolves to your project's specifics at AI session bootstrap.

The whole machine in one sentence

Three kinds of moving parts (Skills · Commands · Scripts) plus one variable substrate (.agents/project.yaml) — that is the entire mental model. The rest is detail.

Read agentic-development-engineering.md for the strategy behind the practice and CONTEXT.md for why the knowledge layer is split the way it is. This page focuses on how the pieces connect — what to invoke, in what order, and what each piece actually does.

2.Three categories of moving parts

Everything you can invoke in this repo belongs to one of these three categories. The mental model holds end-to-end:

Type What it is Where it lives Who invokes it
Skill
Multi-file markdown that orchestrates the AI through long, multi-phase tasks (subagents, decisions, references). .claude/skills/<name>/SKILL.md + references/ The AI auto-activates when your prompt matches the skill's triggers. Force-load via /skill-name.
Command
Single-file markdown for one-shot, focused utilities. .claude/commands/<name>.md You explicitly type /<name>. No auto-trigger.
Script
TypeScript CLI that runs in the terminal. scripts/*.ts and cli/*.ts You run bun run <script> directly.

The three categories share the same fuel: the variable substrate in .agents/project.yaml (and Jira metadata in .agents/jira.json + .agents/jira-required.yaml). Skills resolve {{VAR}} and {{jira.*}} placeholders against it on every AI session; commands use the same resolver; scripts read the YAML and write back to it. See §5 Circuit 1 for the full resolution flow.

3.The lifecycle: five phases

Each phase has a clear trigger, a deterministic output and a frequency. You move forward when the previous phase's output exists; you loop back to Maintenance whenever documentation drifts from reality.

One-time setup on the left, recurring work on the right. Maintenance feeds back into Daily Dev.

Click each phase to expand:

0 Bootstrap — install the foundation
Trigger
bun install → bun run setup (interactive installer for gentle-ai skills + 4 canonical MCPs + external CLIs) → bun run agents:setup → bun run jira:sync-fields → bun run jira:check. Or, if you cloned skills à la carte, run /agentic-dev-core first.
Produces
A populated .agents/project.yaml, CLAUDE.md, the foundation scripts (agents-setup, agents-lint, sync-jira-fields, check-jira-setup) wired into package.json, the workspace catalog at .agents/jira.json (custom field IDs), and the .mcp.json with credentials for Tavily, Context7, Supabase, n8n.
When to repeat
One time per repo clone. If you cloned the full repo, the foundation is already in place — only bun install, bun run setup, and bun run jira:sync-fields are needed. 
bun install
bun run setup                 # interactive: gentle-ai skills + MCPs + CLIs
bun run agents:setup          # interactive walkthrough for project.yaml
bun run jira:sync-fields      # catalog Jira custom fields
bun run jira:check            # verify the catalog against the manifest
bun run lint:agents           # validate placeholders
1 Foundation — define the product
Trigger
/project-foundation — runs Constitution → Architecture (PRD + SRS) → Discovery (orchestrates /business-data-map, /business-feature-map, /business-api-map, /master-implementation-plan + embedded project-dev-guide).
Produces
idea/* (constitution), PRD/*, SRS/*, .context/business/business-data-map.md, .context/business/business-feature-map.md, .context/business/business-api-map.md, .context/business/project-dev-guide.md, .context/master-implementation-plan.md. The skill orchestrates each phase with explicit human checkpoints.
When to repeat
Once per product. Re-run only when the product undergoes a major pivot or architectural change. 
/project-foundation
2 Scaffold — wire the Next.js + Supabase skeleton
Trigger
/project-bootstrap. Runs strictly AFTER Phase 1 — it consumes .context/ + SRS/.
Produces
Backend (DB schemas, API base, types, error handling), frontend (design system, project skeleton, routing), and incremental features (OpenAPI + Scalar UI, API routes + middleware, bearer-token auth, env vars + URL builders, Supabase types generation). Two strict sub-phases: Plan (no writes, presents the diff) → user approval → Implement (writes).
When to repeat
Once per project. Re-run only when adding a new infrastructure layer (e.g. switching auth providers, adding a new API surface). 
/project-bootstrap
3 Daily Dev — the workflow skills
Trigger
Pick the skill that owns the current stage:
  • /product-management — backlog seeding, epic creation, INVEST/AC refinement (before development).
  • /sprint-dev — per-story 12-step loop: planning → implementation → code review → staging deploy → (gated) production deploy. The mega-orchestrator.
  • /unit-testing — TDD red-green-refactor for an isolated unit. Composable mid-flight from /sprint-dev.
  • /git-flow-master — end-to-end git operator (auto-detects the branching strategy and adapts every commit / push / PR).
Produces
Implementation plans, feature branches, commits, pull requests, code-review verdicts, staging deploys, and Jira transitions all the way to Ready For QA. Optionally, gated production deploys with a rollback plan.
When to repeat
Every sprint. Every ticket. Designed to be invoked many times per week.
4 Maintenance — fix drift as it appears
Trigger
When .context/, CLAUDE.md, or .agents/ drifts from reality (the project shipped new modules, new Jira fields, new endpoints).
Produces
Synced memory files and re-cataloged Jira fields:
  • /sync-ai-memory — audit + patch the 5 always-included docs (README.md, CLAUDE.md, CONTEXT.md, docs/agentic-development-engineering.md, docs/getting-started.md) plus any auto-detected high-frequency markdown.
  • /business-data-map, /business-feature-map, /business-api-map — regenerate the business maps under .context/business/.
  • /master-implementation-plan — regenerate .context/master-implementation-plan.md (high-level dependency-cascaded roadmap).
  • bun run jira:sync-fields — re-catalog Jira custom fields when a new prompt requires a new field.
  • bun run jira:check — verify the Jira workspace still satisfies jira-required.yaml against jira.json.
  • bun run lint:agents — verify every {{VAR}}, {{jira.<slug>}}, and <<VAR>> placeholder still resolves.
When to repeat
As needed. Treat drift like compiler warnings — fix them when they appear, not in batches.

4.The Jira state machine

/sprint-dev drives the ticket through a four-state Jira workflow. Every transition is owned by a specific stage of the sprint loop — the AI does not skip ahead. You confirm at the gates.

Each transition is owned by a sprint-dev stage. The repo never reaches "Done" — QA lives in the sister repo (agentic-qa-boilerplate).

Transition Owned by Trigger condition
Ready For Dev → In Progress Stage 1 — Planning Implementation plan presented and approved. Feature branch created (e.g. feature/UPEX-123-add-login).
In Progress → In Review Stage 3 — Code Review All commits pushed. PR opened against staging. Review run (single-perspective; escalate to /judgment-day for sensitive paths).
In Review → Ready For QA Stage 4 — Staging Deploy PR merged into staging. Staging deploy green. Smoke check OK. QA can now pick the ticket up.
Mnemonic: Planning opens the ticket, Code Review opens the PR, Staging Deploy opens the door to QA. Production is gated and lives outside the state machine.

A note on the sister repo

This boilerplate is a dev-side machine. Once a ticket reaches Ready For QA, it is the QA team's job to validate it, file bugs, and eventually move it to Closed. The QA workflow lives in the sister repo agentic-qa-boilerplate, with its own Jira state machine (Ready For QA → In Testing → Tested / Closed) and its own skill set (/sprint-testing, /test-automation, etc.). Do not invoke QA-side skills from this repo.

5.How everything connects internally

Two circuits explain the wiring. Circuit 1 is about variable resolution (the static substrate). Circuit 2 is about subagent orchestration (the dynamic execution model).

Circuit 1 — Variables

Variables flow: you fill the YAML once → AI reads it on every session → placeholders resolve to real values before any tool call.

.env vs .agents/project.yaml — two separate systems

Do not conflate them. They have different consumers, different lifecycles, and only one of them is committed.

.env .agents/project.yaml
Purpose Next.js + Supabase runtime secrets and config (also the MCP credentials Claude reads at session start). AI context-engineering variables for {{VAR}} resolution.
Consumers Next.js runtime (next dev, route handlers, server actions), Supabase client, MCP servers (Tavily, Supabase, n8n), test runners (Vitest, Playwright), Atlassian CLI (acli). AI agents (Claude Code, OpenCode, Cursor, Codex) when resolving skill / template / doc references.
Examples LOCAL_USER_EMAIL, STAGING_USER_PASSWORD, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, TAVILY_API_KEY, ATLASSIAN_API_TOKEN. PROJECT_KEY, WEB_URL, API_URL, JIRA_URL, DB_MCP, default_env.
Secrets? Yes (passwords, tokens, API keys). No — must remain commit-safe.
Committed? Gitignored. .env.example is the committed template. Committed.
Lifecycle Edited per developer / per CI runner. Edited once when adopting the boilerplate; rarely changes after.

The variable substrate has four syntaxes that look similar but resolve from different files. The full contract lives in .agents/README.md; the short version:

  • {{VAR_NAME}} → resolves from .agents/project.yaml (project-level static config). Env-scoped vars like {{WEB_URL}}, {{API_URL}}, {{DB_MCP}} resolve against the active environment (default testing.default_env).
  • {{environments.<env>.<var>}} → explicit cross-env reference, useful when a prompt needs to compare values across environments regardless of the active one.
  • <<VAR_NAME>> → session variable, computed at runtime by the calling skill (e.g. <<ISSUE_KEY>> extracted from the git branch). Never persisted.
  • {{jira.<slug>}} → portable Jira custom-field reference, resolves through .agents/jira-required.yaml (manifest) + .agents/jira.json (workspace catalog). Used by /sprint-dev and /product-management when they need to read or update fields like acceptance_criteria_gherkin.

Circuit 2 — Orchestration

Each workflow skill declares its own dispatch points; the canonical briefing template + dispatch patterns live in agentic-dev-core/references/ so subagents load them once, fresh.

This is the canonical pattern the workflow skills follow. The orchestrator reads its own dispatch strategy, writes a 6-component briefing for each subagent (Goal · Context docs · Skills to load · Exact instructions · Report format · Rules), and the subagent loads tool skills (/acli, /git-flow-master, /playwright-cli) to actually run shell commands. This is what keeps the main conversation lean — the heavy reading happens inside subagents.

7.Skills catalog

Every skill that ships in .claude/skills/. Some you invoke directly; others (the tool skills and the foundation) load automatically when a workflow skill needs them.

Categories — Foundation hosts shared references and bootstraps the repo · Workflow drives a stage of the pipeline · Generator defines or scaffolds the project · Tool wraps a CLI/MCP for I/O · Reference is loaded passively by other skills.

agentic-dev-core Foundation

/agentic-dev-core

Bootstraps the foundation files (CLAUDE.md, .agents/, scripts, package.json entries) AND hosts shared references (briefing template, dispatch patterns, orchestration doctrine) that other skills cite on demand. Two roles, one skill.

agentic-dev-onboard Reference

/agentic-dev-onboard

Walks new users through this repo's dev flow — stack, Jira workflow, when to use /sprint-dev vs /sdd-*, MCPs, env vars. The tour ends when the user knows which skill to call next.

project-foundation Generator

/project-foundation

Defines a brand-new product via Constitution → Architecture (PRD + SRS) → Discovery (business-data-map, api-architecture, project-dev-guide). Runs once per product.

project-bootstrap Generator

/project-bootstrap

Scaffolds the technical infrastructure: backend (DB schemas, API base, types), frontend (design system, routing), and incremental features (OpenAPI + Scalar UI, bearer-token auth, env vars, Supabase types). Plan → approval → implement.

product-management Workflow

/product-management

Continuous product management — backlog seed from PRD, epic creation, story refinement (INVEST + 3-amigos), AC quality refinement (Gherkin), edge-case enumeration. Runs before development picks the ticket up.

sprint-dev Workflow

/sprint-dev

Per-story 12-step loop: planning → implementation → code review → staging deploy → (gated) production deploy. The mega-orchestrator. Drives Jira through Ready For Dev → In Progress → In Review → Ready For QA.

unit-testing Workflow

/unit-testing

TDD red-green-refactor for an isolated unit. Test naming (AAA / Given-When-Then), mocking patterns, coverage strategy. Composable mid-flight from /sprint-dev for TDD slices. Vitest by default.

git-flow-master Tool

/git-flow-master

End-to-end git operator — auto-detects the project's branching strategy (solo-main, main+staging, GitFlow, GitHub Flow, ...) and adapts every commit / push / PR / conflict-fix / chained-PR plan to it.

acli Tool

/acli

Atlassian CLI cookbook for Jira Cloud + Confluence Cloud — work items, projects, boards, sprints, fields, transitions. Resolves the [ISSUE_TRACKER_TOOL] pseudocode tag.

Reusable knowledge skills

Six knowledge-only skills (no orchestration) that workflow skills load on demand for stack-specific guidance.

frontend-design Reference

/frontend-design

Production-grade frontend interfaces with high design quality — distinctive, polished UI that avoids generic AI aesthetics.

next-best-practices Reference

/next-best-practices

Next.js best practices — file conventions, RSC boundaries, data patterns, async APIs, metadata, error handling, route handlers, image/font optimization.

next-cache-components Reference

/next-cache-components

Next.js Cache Components — PPR, the use cache directive, cacheLife, cacheTag, updateTag.

next-upgrade Reference

/next-upgrade

Upgrade Next.js to the latest version following official migration guides and codemods.

playwright-cli Tool

/playwright-cli

Browser automation CLI for AI-driven smoke checks: screenshots, tracing, video recording, session management, request mocking. Resolves [AUTOMATION_TOOL] pseudocode.

resend-cli Tool

/resend-cli

Operate Resend (email service) from the terminal — send emails, manage domains, contacts, templates, webhooks.

Skills installed via gentle-ai (user-level)

Run bun run setup once to install the SDD orchestrator (/sdd-init, /sdd-explore, /sdd-propose, /sdd-spec, /sdd-design, /sdd-tasks, /sdd-apply, /sdd-verify, /sdd-archive, /sdd-onboard) plus /judgment-day, /cognitive-doc-design, /comment-writer, /issue-creation, and engram (persistent memory). 8.Commands & Scripts

One-shot utilities — neither orchestrate long flows like skills nor maintain config like setup scripts. You type them by name.

Commands

Single-file markdown at .claude/commands/<name>.md. Invoke with /<name>.

  • /sync-ai-memory Audit + patch the 5 always-included docs (README.md, CLAUDE.md, CONTEXT.md, docs/agentic-development-engineering.md, docs/getting-started.md) plus auto-detected high-frequency markdown. Preserves human-authored structure.
  • /business-data-map Generate / update .context/business/business-data-map.md — entities, flows, state machines, external integrations.
  • /business-feature-map Generate / update .context/business/business-feature-map.md — feature catalog by domain, CRUD matrix, API inventory, flags.
  • /business-api-map Generate / update .context/business/business-api-map.md — auth model, critical journeys, architecture, external integrations.
  • /master-implementation-plan Generate / update .context/master-implementation-plan.md — high-level dependency-cascaded roadmap of what to build first and why.

Scripts

TypeScript CLIs declared in package.json. Run with bun run <name>.

  • bun run setup Interactive installer — gentle-ai skills + 4 canonical MCPs (Tavily, Context7, Supabase, n8n) + external CLI verification (vercel, supabase, acli, playwright, resend).
  • bun run agents:setup Interactive walkthrough that fills .agents/project.yaml.
  • bun run lint:agents Validate every {{VAR}}, {{jira.<slug>}}, and <<VAR>> reference resolves against the manifest + catalog.
  • bun run jira:sync-fields Catalog all custom fields from the live Jira workspace into .agents/jira.json.
  • bun run jira:sync-issues Sync Jira issues (Story / Bug / Task / Epic) with their acceptance_criteria_gherkin field and other custom data into local context.
  • bun run jira:check Verify the Jira workspace satisfies .agents/jira-required.yaml.
  • bun run api:sync Sync OpenAPI spec from the live API and regenerate api/schemas/ types.
  • bun run up Update the boilerplate from upstream — pulls latest skills, scripts, and conventions while preserving local edits.
  • bun run lint / lint:fix Lint the codebase with ESLint. lint:fix auto-fixes.
  • bun run format / format:check Format with Prettier. format:check only verifies.
  • bun run type-check Run tsc --noEmit against the whole project.
  • bun run onboarding Serve this onboarding page on a local port and open it in the browser.

Run bun <script> --help on any script for usage. The Vitest binary is installed locally — no global install needed.

9.TL;DR mental model

  • Skills = play scripts for the AI (multi-act, with characters that delegate).
  • Commands = single-act utilities you type by name.
  • Scripts (bun run …) = what YOU run in the terminal to keep the fuel (.agents/project.yaml + Jira fields) healthy.
  • .context/ = what the AI KNOWS about the project (generated by /project-foundation and the /business-*-map commands, kept fresh by /sync-ai-memory).
  • Application code = the real product, scaffolded by /project-bootstrap and built feature-by-feature via /sprint-dev.

Fill project.yaml first (bun run agents:setup), then let the AI define the product with /project-foundation, then scaffold the Next.js + Supabase skeleton with /project-bootstrap. From there, /sprint-dev drives every Jira ticket from Ready For Dev all the way to Ready For QA.
