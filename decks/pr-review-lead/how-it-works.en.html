00 · peer review

Feedback with evidence, not with opinion.

/pr-review-lead acts as Tech Lead on a teammate's pull request, in this repo or in another one you point it at. It reads the doctrine that code actually documents, reads the diff, and every finding points to a line of code, to a doctrine section, or says out loud that it is an opinion. Nothing goes to GitHub without your explicit OK on the final draft.

for whoever leads and whoever develops you pick the rigor before reading never posts without your OK

01 · when yes, when no

Review someone else's work, not your own

The skill has neighbors that also "review". Each one answers to someone different, and has its own door.

You need Use
Feedback on a teammate's finished PR (from this repo or another), with a score and evidence, posted only after your OK /pr-review-lead
The review pass inside a story's pipeline: an independent adversarial agent, findings adjudicated by the orchestrator, back to stage 2 /sprint-development etapa 3, references/review-pr.md
Review your own uncommitted changes before opening the PR The harness's code review flow
Open the PR, resolve conflicts, manage branches, merge /git-flow-master
What they share

One checklist and one scale

  • Both read the same review-pr.md §"Review checklist". This skill uses it by reference and never copies it: a change to the checklist is made there, once.
  • Both speak the same severity scale, the one in §"Adjudication contract": BLOCKER, MAJOR, MINOR, NIT. A finding means the same thing no matter who raises it.
What sets them apart

Who they answer to

  • Stage 3 answers to the orchestrator of ONE story and never posts anything.
  • This skill answers to a person reviewing SOMEONE ELSE's PR: it adds the rigor lens and the score, and posts only with an explicit OK.
02 · the map

Eight steps, and anything external happens in the last one

No modes: a single run, from step 0 to step 7. Up to step 6 everything stays in the conversation. Only step 7 writes something other people can see.

03 · step 0, the preflight

How strict to be is decided before reading a single line

It is mandatory on every run. It is skipped only when the request already said it ("review it strict", "be flexible with the patterns"), and what was already given is never asked again.

Level What gets reported Pattern findings Weight of a Pattern in the score
Flexible Only what is evidently broken or puts correctness, security or data at risk They do not appear, unless they are also a correctness or security risk None
Standard (recommended) The same bar as Flexible, plus pattern deviations Light observations, as a comparison: "the documented pattern does X, this PR does Y" None: they are informational and never subtract
Strict A literal pass against every doctrine file that applies Labeled finding, even if it works fine Small, capped: never dominates like a Real
Strict widens what counts as a finding, it does not lower the bar of proof. A Pattern is still a Pattern at any level: rigor never turns a pattern note into an error.

Why the lens exists

It comes from a real session in the sibling QA boilerplate: an architecture deviation that broke nothing was scored with maximum severity, and the user corrected it. Almost nobody implements an architecture to the letter, and a deviation that breaks nothing is not an error the way a bug is.

Pattern, in Standard

The page queries Supabase directly

  • review-pr.md §"Architecture & Structure" documents the separation: data access goes in lib/api/. This page skips it, and works just the same.
  • It is stated as a comparison, with the citation, without drama and without touching the score.
Real, at any level

The RPC trusts p_user_id

  • A new function filters by the id the caller passes it, without tying it to auth.uid() (rpc-authorization.md): any authenticated user reads other people's rows.
  • It is BLOCKER even if you asked for softness with patterns.
04 · step 1, load the doctrine

First you read, then you opine

It never reviews against remembered conventions or generic "best practices" that were not checked to be documented. The doctrine is read fresh on every run, never from memory of an earlier session.

PR from this repo

AGENTS.md plus whatever the PR touches

  • §1 Critical Rules and §2 SIMPLICITY FIRST and SURGICAL CHANGES of AGENTS.md, plus the sections its router names, for example agent-code-quickref.md (§10, stack quick reference).
  • If the branch names a story, its acceptance criteria and its plan via bun run jira:sync-issues get <KEY>: "does it do what the story asked?" is the first item on the checklist.
PR from another repo

Probe before assuming

  • Does it have its own AGENTS.md, .agents/skills/ or .context/? If so, that doctrine rules and THEIR paths are cited.
  • Being born from this boilerplate is a signal, not proof: the fork may have diverged. If it has no doctrine, this repo's is used and you are told once, at the very top. 
# the probe (references/evidence-and-doctrine-lookup.md §"External repo")
gh api "repos/<owner>/<repo>/contents/AGENTS.md" -q '.content' | base64 -d
gh api "repos/<owner>/<repo>/contents/.agents/skills" -q '.[].name'
gh api "repos/<owner>/<repo>/contents/.context" -q '.[].name'

The doctrine map widens or narrows per PR

For a three-line fix, not everything is loaded. The full table lives in references/evidence-and-doctrine-lookup.md §"Doctrine map".

05 · step 2, gather the PR

You read the diff, never the description

A big diff is sometimes almost all noise. The skill separates it before reading line by line, and tells you what it set aside.

Noise versus work

Commit headlines first: a lockfile, regenerated Supabase types, an OpenAPI type sync or a template sync commit are not reviewed line by line. They are named.

Generated files still get checked

For one thing only: that it matches what generated it. A generated file edited by hand is a finding.

PR too large

gh pr diff fails with PullRequest.diff too_large. The way out is to page through the patches file by file, never to skim the description.

Many files

Not all the diffs are brought into its own context: work is dispatched per file or per group (UI, API, DB, tests) with a 7-component briefing. A few files are read inline.

A claim is not evidence. "All tests pass", "verified on staging", "CI green": they are noted as claims unless the run, the deploy or the output can be pointed to. A well-backed one earns a Positive; an unverified one is never presented as its own finding.
06 · step 3, analyze

Every finding answers "where does this come from?"

It points to a line of code, points to a line of doctrine, or is labeled an opinion. There is no fourth option.

Code evidence

<file>:<line> from the diff, with the line quoted.

With no local checkout, it is quoted as it appears in the patch.

Doctrine evidence

<file> §<Section> or Critical Rule #N, with the sentence that backs the claim.

Always a section title, never a line number: numbers move with every edit (Critical Rule #17).

Opinion

Said in those words: "this is a general best-practice opinion, it is not in this repo's documentation".

Disguising it as a rule erodes trust in all the other citations.

The checklist, plus what the reviewer of other people's PRs adds

It walks review-pr.md §"Review checklist" in its order (acceptance criteria first) and adds fronts that a story reviewer may not reach.

Layer boundaries

api/ / schemas/ / db/ in the backend and the design system structure in the frontend are framework architecture (project-bootstrap B1). Collapsing them is a finding, not a simplification.

UI fidelity · Rule #14

The reference is the current live UI plus the tokens in DESIGN.md; the mockup is inspiration. A change is a defect if it matches neither the live UI nor the design system and has no spec-only ratification in §5 of master-design-plan.md.

Following the improved live UI where the mockup differs is not a finding.

ADRs

A choice that passes the three-gate test in adr-doctrine.md §1 (hard to reverse, surprising without context, with a real trade-off) and has no ADR, or that contradicts an Accepted one in .context/ADR/, is a finding.

Two axes

If the PR comes with a ticket, plan or acceptance criteria, the review runs on two axes: a Spec reviewer and a Standards reviewer, each in fresh context, with the briefs in review-pr.md ## Two-axis review. Every finding carries its axis.

Lying tests

New tests are reviewed with LT-1 (tautological), LT-2 (cannot fail) and LT-3 (tied to structure), defined in unit-testing/references/tdd-workflow.md. They are Real findings at every rigor level.

Three buckets, and every finding lands in only one

The bucket, not the severity label, is what moves the score. Inside Real and Pattern the severity uses the shared scale, in the conversation's language (in Spanish: Bloqueante, Mayor, Menor, Nit) and in English in what is posted.

Bucket What it is Examples
Real Something evidently wrong, or a risk to correctness, security or data, beyond anyone's architectural taste. It weighs at every level Unmet criterion, hardcoded credential (Rule #1), RPC that trusts the identity it is handed, destructive migration with no way back, unratified UI divergence, lying tests
Pattern It works, breaks nothing, but departs from a documented convention. It is a comparison, not a verdict. Its weight depends on step 0 More than two positional parameters, a deep relative import, domain logic in a shared utility, a naming slip
Positive What was done well, held to the same bar of evidence. It is neither optional nor a courtesy: it is always filled in Tests that pin down behavior and not implementation, a migration with its down path, a clean ADR, a reused component, live UI evidence attached
07 · steps 4 and 5, checkpoint and triage

First a table for you, still nothing for the author

The table groups by bucket and severity, always with the evidence column, and closes with the strengths and a score out of 10 with its reason in one line. 

# shape of the checkpoint (references/output-and-posting-flow.md, step 4)
| # | Bucket  | Severity  | Location      | Observation (with evidence)              |
| 1 | Real    | BLOCKER   | <file>:<line> | ... rpc-authorization.md §"Actor bind"   |
| 2 | Pattern | MINOR     | <file>:<line> | ... comparison, not error. review-pr.md  |

Strengths:
- <positive with its own evidence>

Score: X.X / 10: <reason tied to the buckets that moved it>

How the score is built

It starts at 10 and subtracts. The full rubric is in references/severity-and-scoring.md §"Scoring rubric".

Finding Subtracts
Real BLOCKER From 1.5 to 2.5, depending on blast radius: a leaked anon key in a demo weighs less than a cross-tenant read with real data
Real MAJOR From 0.5 to 1
Real MINOR From 0.1 to 0.3
NIT Nothing
Pattern Nothing in Flexible and Standard. In Strict, 0.1 to 0.2 each, capped: ten pattern nitpicks on a PR with no real defects leave it comfortably above half
Positive It does not add. A PR with one blocker and excellent positives is still a PR with a blocker: both things get said

The triage is yours

Your context (the team's norms, what you consider worth raising) decides what goes out. The skill reclassifies as you ask and does not defend the first pass.

"Only the blockers and majors"Filters what goes into the draft. It does not re-analyze: it only narrows.
"That's not an error, it's a pattern"Moves it from Real to Pattern, recalculates the score with the new weight and asks you whether you accept it before going on.
"Let's not be so harsh on patterns"It is a rigor change midway: it re-walks every Pattern at the new level and shows you the table again before drafting anything.
Gate you know which findings go and you accepted a score. Before that nothing gets drafted: a draft nobody asked for is a draft that gets redone.
08 · steps 6 and 7, draft and OK

An honest sandwich, and then your yes

Praise, constructive, praise. With a real strength at each end, not a filler compliment wrapped around a list of complaints.

The AI does

Writes in English (Critical Rule #12), unless you ask for another language for THAT comment. Every constructive point carries the citation from the table.

Runs the prose through the humanizer skill if it is installed: a person is going to read it. Code, paths and citations stay intact.

You decide

The tone, if there is no preference already set.

The OK, on this draft. "Looks good" while severity is still being discussed is not "post it" once the final one is shown.

Output

A plain comment on the PR, posted from a temporary file.

Its URL, confirmed by reading the PR back.

# the confirmed draft, in a file in the session scratch
gh pr comment <N> [--repo <owner>/<repo>] --body-file <scratch>/pr<N>_review.md

# read it back: the comment has to be on the PR
gh pr view <N> [--repo <owner>/<repo>] --json comments -q '.comments[-1].url'
Gate the URL that gh pr comment returns matches the read-back (Critical Rule #16: the exit code is not the outcome). Then the temporary file is deleted.
A batch, half approved. "Post #1, hold #2" posts exactly that subset and says what was left pending and why. A yes for one PR is never consent for a sibling that is still in triage.
09 · hard rules

The guardrails that are not negotiable

They live in ## Compact Rules and in ## Rules of the skill; the compact ones travel to subagents through .agents/skills/REGISTRY.md.

Never posts without the OK from step 7. No exceptions. An OK for another PR does not carry over, and silence is not approval. A supervised worker needs the OK that the conductor relays from the person, and a routine with nobody around posts only if the brief names this PR and asks for it; otherwise it saves the draft and reports it.
Drafting and posting are not delegated. They are tone decisions and an action that others see: they stay with the orchestrator, never with a subagent.
Reviewing is not fixing. It never pushes commits to the PR it reviews. A fix you want goes through the author, or a separate branch via /git-flow-master.
No formal review unless asked. It does not approve or request changes on GitHub unless you ask for that specific action: the default artifact is a comment.
No "best practice" is presented as a repo rule without its file §section. When it is opinion, it says so.
There are always strengths. Zero positives on a PR that has them is not rigor, it is lack of calibration.
/git-flow-master is loaded before the first gh (.agents/instructions/agent-tool-resolution.md §6.5).
10 · what you tell the AI

Invoking it in each terminal

No modes. Naming it and the PR is enough, or phrases like "review this PR", "act as tech lead" or "revisa este PR". If you already state the rigor ("review it strict"), step 0 does not ask.

Claude Code

/pr-review-lead owner/repo#123

The skill bar, with the PR you want to review.

OpenCode

load the skill pr-review-lead

No bar: you name the skill and the PR in the sentence.

Codex

load the skill pr-review-lead

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:pr-review-lead owner/repo#123

Bar with the /skill: prefix. In a new folder, /trust once.

The PR can be given in several ways: owner/repo#N, the PR URL, "the PR for the current branch" or a raw diff.

Loaded before any call to gh. Opening, merging or fixing the PR is its job, never this skill's.

The base · how it talks

Behavioral layer

How the human is asked and how reports are made. Step 0 is a three-option question through the harness prompt, as AGENTS.md §2 requires.

To read more: .agents/skills/pr-review-lead/SKILL.md and its references in references/ (rigor and scoring, evidence and doctrine, drafting and posting). The shared checklist: sprint-development/references/review-pr.md.

The underlying idea. A review that mixes bugs with tastes and does not say where each thing comes from teaches the author to ignore it. This one separates what breaks from what merely departs, cites everything, names what was done well, and leaves the last word before publishing to you.
