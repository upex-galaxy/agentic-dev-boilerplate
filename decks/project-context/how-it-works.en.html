00 · project context

The context the AI reads before it plans, written with evidence and approved by you.

/project-context generates and refreshes the context artifacts that the other skills take for granted: the business maps (data, features, API), the master implementation plan and the development roadmap. It also builds a project-specific context skill for an aspect the maps do not cover. It runs one mode at a time, and when the artifact already exists it never overwrites it without showing you the diff and waiting for your yes.

01 · when to use it

When the project's mental model is missing or has gone stale

Every artifact it produces is a synthesis: someone read the code, the schema and the backlog and wrote down what they mean. This skill does that reading, and does it again when the sources change.

Use it when

You need to map, prioritize or sequence

  • "Mapea el dominio" (map the domain) · "inventario de features" (feature inventory) · "cómo funciona el API" (how the API works): a business map is missing, or the code changed and the map did not.
  • "Plan maestro de implementación" (master implementation plan) · "qué construimos primero" (what do we build first): epic order and why.
  • "Roadmap de desarrollo" (development roadmap) · "qué historia sigue" (which story is next): ticket order and what unblocks what.
  • "Arma una skill de contexto para billing" (build a context skill for billing): an aspect of the product that no map covers and that a session would misread without rules.
Do not use it for

What belongs to someone else

  • A story's plan, file by file: that is the planning stage of /sprint-development.
  • The full endpoint catalog or the contract types: they come from bun run api:sync over the OpenAPI spec.
  • A data-context, feature-context or api-context skill: those aspects already have an owner, the business map skills. The request is answered by pointing to them.
  • Delivery dates: the master plan orders work, it does not estimate it.

03 · the contract

The rules that hold in every mode

They live in ## Compact Rules of the skill. The compact ones travel to the subagents through .agents/skills/REGISTRY.md.

One mode per run. The first word of the arguments is the mode if it matches one; if not, it comes from the phrase; if not even that, the AI asks. A bare "refresh the context" is never refresh-all.
It never invents business facts. It reads every source the reference asks for, and what it could not verify goes to the mandatory ## Discovery Gaps section of the artifact, not to the body.
It never overwrites without approval. An existing artifact is updated with a candidate, a diff and your explicit yes. A generated map is never regenerated whole.
The old markdown map is read, not deleted. A .context/business/business-*-map.md from an earlier version comes in as input (the legacy list of CONTEXT_MAP_SKILLS, in cli/lib/context-maps.ts) and stays where it was.
Missing capability = stop at the point of use. It needs db, library-docs, web-search and diagrams (the map figures, resolved by the presence of the diagram-design skill). Without one, it names the capability and waits; never a silent substitute.
It reads the stack: block once per run. It is in .agents/project.yaml and parameterizes every mode: app_root says where the code is (one app per run; the other workspaces of a monorepo stay as a Discovery Gap), database.schema_source says whether the schema comes from the live database through the db capability (live) or from the migration files, read offline (migrations; there db becomes optional), and an app that calls Supabase directly from its code has a direct API that the api mode also maps. Without the block it uses the defaults in .agents/project.schema.yaml and leaves a Discovery Gap that names bun run agents:setup --stack. A null value means the app does not have it: it is skipped and said so.
After writing, it only adds the missing pointer. If the artifact is not in the shared Key paths or in .agents/instructions/agent-project.md, it adds it to agent-project.md, never to AGENTS.md. It never writes operating prose in CLAUDE.md, which is the generated shim.
The rest of the arguments travel as they are. Project path, module filter, epic key or Master Sprint name: whatever each reference defines.
04 · create or update

If it does not exist, it writes it. If it does, it proposes it to you.

You do not choose CREATE or UPDATE: it comes from the state of the artifact. What changes between artifacts is which part gets regenerated in an UPDATE.

Artifact How it detects the state CREATE UPDATE
Business map bun run context:map <skill> --list: placeholder notice or list of sections Builds each section from the sources and writes the file once Per-section freshness check, regenerates only the stale sections, shows a diff per section and waits. It never changes a section's id.
Master plan does .context/master-implementation-plan.md exist? Generates it from scratch New version, diff summary, confirmation. It highlights what moves up or down in Master Sprint.
Development roadmap does .context/dev-roadmap.md exist? The whole document Surgical: regenerates only the execution sprints section and keeps what was written by hand (column, edges, gates, local blockers).
Context skill does .agents/skills/<aspect>-context/ exist? The scaffold, after the analysis Candidate, diff, wait. It adds dated rules; it never rewrites an existing one.
The AI does

Detects the state, reads the sources, builds the candidate and compares it with what is there.

If a map changed, it checks the ## Rules and the gotchas of its skill against the new map.

You decide

Whether the diff goes in. Without your yes, the existing artifact is not touched.

What to do with a rule the new map contradicts: the AI proposes it for "No longer true", it never deletes it.

Output

Only what was approved, plus the discovery-gaps section, even if empty: proof that someone looked.

Gate for a map: bun run context:map <skill> --list prints every section, with the run date on the ones written, and no placeholder notice.
05 · dependency gates

A hard gate stops the run. A soft one leaves a noted gap.

Each reference owns the exact wording of its gate. The general rule: if without the input the artifact would be a wish list, the gate is hard; if it is only poorer, it is soft and the gap is recorded as a Discovery Gap.

Mode Hard gate (stops) Soft gates (Discovery Gap)
data none: it is invoked on its own PRD and SRS under .context/ (it suggests /project-foundation)
features none the data map
api no OpenAPI spec, no backend with routes to scan and no direct API to Supabase the data map, the features map
master-plan a generated data map the features map
dev-roadmap at least one epic with child stories in the tracker its dependency links (without them it warns and builds a sparse graph, with the stories that have no edge in a mapping TODO), the data map, master-design-plan.md, master-implementation-plan.md
context-skill what the skill will cover has to exist: a map, a module, a contract none
"Generated map" is measured, not assumedbun run context:map business-data-context has to print sections. A placeholder notice counts as "no map", never as an empty system.
The stop message is literalA hard gate stops with the exact text from its reference, which names the missing step (for example, run /project-context data before the master plan).
Soft is not silently optionalThe run goes on, warns, and the limitation is written into the artifact with a suggestion of which mode to run next.
06 · refresh-all

All the context, in an order that is not negotiable

It only runs if you ask for it explicitly. Each step closes its own validation and its own approval before the next reference is loaded.

data

First, because the others use it: features and api read it, the master plan requires it.

features

Crosses each entity of the data map with its CRUD coverage.

api

Points its journeys at entities of the data map and features of the features map.

master-plan

Turns the maps into an epic order by value, blocking and urgency.

dev-roadmap

Breaks that order down into tickets, with the tracker's dependency graph.

It stops

On a hard stop or a no

  • A hard gate that fails cuts the whole chain.
  • A diff you reject does too: it does not jump to the next step.
  • A missing soft gate does not cut it: it stays as a Discovery Gap, as in every single mode.
Outside the chain

context-skill never enters

  • Scaffolding a context skill is a per-aspect decision, not a refresh.
  • /project-foundation, in its Discovery phase, runs the maps in the same order (data → features → api) and leaves the master plan for the end.
07 · data, features, api modes

Each map, a different look at the same system

Each map answers a different question and cites the others by section id instead of copying them. The golden rule of all of them: synthesize, do not dump. The live database serves the schema; the map writes what it means.

data · "where does X live and what touches it?"

Data map

Reads schema, RLS and migrations (through the db capability or, with schema_source: migrations, from the migration files), plus backend, frontend, PRD and SRS. It writes entities with their business role, who reads and writes each table, the migrations that changed the meaning of an entity, every important flow (no cap), state machines, automatic processes and integrations.

features · "what can the system do?"

Features map

A feature is any capability: endpoint, UI action, background process, integration. It writes the catalog by domain with its status, the CRUD matrix per entity, routes, UI, integrations and flags. If the PRD and the code disagree, the code wins and the difference goes to Discovery Gaps.

api · "how does the business operate through the API?"

API map

Narrative, not an endpoint catalog: tiered auth model, critical business journeys traced end to end, architecture behind the API and integrations with their visible failure mode. What the OpenAPI spec already expresses is linked, not repeated.

all · before the first figure

Figures with diagram-design

Check of the diagrams capability at the point of use. Every fact a figure shows is also in the text: the AI reads only the text. If the skill is not there, it stops; never a hand-drawn SVG or ASCII in its place.

When a map changes, the judgment layer is reviewed too. After writing, the AI checks the ## Rules and references/gotchas.md of the map's skill against the new content and proposes changes. And if a project context skill relies on that map, it offers to run context-skill in UPDATE: the facts just changed and a human is already looking at a diff.
08 · master-plan mode

What to build, in what order, and why that order matters

The strategy layer that sits on top of the maps. Written in the voice of a senior engineer talking to a tech lead who just arrived: a guide, not a catalog.

Gate and reading

Without a generated data map, it stops: a plan without a map of entities and flows is a wish list. Without a features map, it warns and goes on. It adds PRD, SRS, glossary and the git log to know what has already shipped.

Internal score

User value × blocking factor × urgency. The product places each unit in Master Sprint 0 (foundational), 1 (MVP), 2 (later) or leaves it deferred. The scoring table is not published: the conclusions are.

Dependencies and hidden couplings

It traces what each foundational item unblocks and always flags the features that share an entity but live in different epics: the typical origin of a schema redesign in the middle of a sprint.

Adopted app (adopted: true in .template/installer.lock.json): the plan covers only the work that is missing. What has already shipped goes in as a "Baseline (already shipped)" table above the priorities and is not scored again or placed in any Master Sprint; Master Sprint 0 is the foundational work that remains, never the rebuilding of what already runs.
The AI does

Orders each priority citing evidence: a flow from the data map, a row from the features map, a PRD priority or a named integration.

You decide

Whether the proposed order goes in. In UPDATE, look first at what moves up or down a Master Sprint: those are the changes that weigh most.

Output

.context/master-implementation-plan.md, with implementation gaps written as spikes.

Never dates, code, payloads or a story's plan. After a change in the Master Sprint structure, /project-context dev-roadmap follows.
09 · dev-roadmap mode

Which ticket is next, and what is blocking it

The sequence layer. It turns the tracker's dependency link graph and the local design context into an execution order. It owns the edges and the gates; never the live state of a ticket. 

# three documents, three altitudes
.context/master-implementation-plan.md   epic / strategy   "what to build and why that order"   ← master-plan
.context/dev-roadmap.md                  ticket / sequence   "what unblocks what, in which sprint"     ← dev-roadmap
.context/PBI/.../implementation-plan.md  story / files  "how a ticket is built"        ← /sprint-development
Section What it holds In an UPDATE
Epic column Which epic goes before which, forced by the entity topology of the data map What was written by hand is kept
Story graph Each hard or soft edge with its reason: what no other place holds Kept; new ones are added and a conflict is flagged
Execution sprints Parallel batches by topological order (Kahn) Regenerated from the live graph
Mockup gates Stories that do not start until their mockup arrives Kept
Live state A query recipe, never a state table Only the local lists are edited by hand: pre-development blockers and edges pending mapping
Order, not availability"Ready", "available" or "can start now" are forbidden. It writes "workable once PROJ-38 is dev-done" or "no prior edges". Whether it can be picked up depends on the live state, which this page does not know.
Two dates, never one"Edges last updated" and "Mockup gates last updated" separately, plus the line "Status snapshot: none". A single date would make the state look fresh.
A cycle stops everythingIf the graph has a cycle, the run stops, names the keys and asks you to reorient a link. It never breaks a cycle on its own.
Link catalog up to datebun run jira:sync-link-types before ordering: an old catalog mixes up dependencies with relations and corrupts the order.
No invented edgesA dependency that "feels" real is a refinement signal: the link is added in the tracker and the run is repeated.
Who uses it. /sprint-development consults it in its Phase 0b before taking a ticket, and queries the live tracker for the candidate and its direct blockers. /product-management delegates sprint ordering to it: the algorithm is still defined in its references/sprint-sequencing.md, and the writing goes through this mode.
10 · context-skill mode

The rules for reading correctly an aspect nobody mapped

An <aspect>-context skill (billing, auth, an integration like stripe) is the judgment layer over that aspect. The sources hold the facts; the skill holds the rules for reading them without getting it wrong.

Before writing

It reads in full what it will cover and lists every place where a competent session would misread: soft deletes, derived columns, RLS that hides rows from a role, states with different names in database, API and UI, behavior that changes between staging and production.

Three-question filter

If it can be regenerated, it stays in the map or the code. If it is a fact, same. Only the judgment that has to arrive without anyone asking becomes a rule, with a date and how it was measured. No measurement, no rule.

Build with skill-creator

SKILL.md from the template in agentic-dev-core/references/skill-scaffold.md, con metadata.kind: context, plus references/gotchas.md. If the builder is not installed, it builds the scaffold from the template and says so in the report.

Validation gate

What has to come out green

  • bun run skills:check: KIND-SUFFIX and STALE-PATH, strict for a context skill (every .context/ path it cites has to exist).
  • bun run skills:registry: the new block shows up in REGISTRY.md with kind: context.
  • A row in the «Project context skills» table of .agents/instructions/agent-project.md, with the triggers that route to it. Never in agent-skills-and-mcps.md: bun sync overwrites it on every update.
Never

Copy, or leave its place

  • Copy a table, a list of entities or endpoints from a map: the skill cites, it does not duplicate.
  • Push it up to the boilerplate: it belongs to the project by construction, and bun sync never delivers it, overwrites it or deletes it.
  • Write to Jira or Confluence, or edit another skill.
11 · what you tell the AI

Invoking it in each terminal

The skill name plus the mode. The first word after the name picks the mode, and the rest arrives intact at its reference.

Claude Code

/project-context data

The skill's slash plus the mode. With no mode, the AI takes it from the phrase or asks.

OpenCode

load the project-context skill, master-plan mode

No slash: you name the skill and the mode in the sentence.

Codex

load the project-context skill, dev-roadmap mode

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:project-context data

Slash with the /skill: prefix. In a new folder, /trust once.

# a map scoped to one module
/project-context data module=billing

# the roadmap of a single epic (or a Master Sprint name)
/project-context dev-roadmap {{PROJECT_KEY}}-12

# a project-specific context skill, about something that already exists
/project-context context-skill billing

# everything, in order, with one approval per step
/project-context refresh-all

# read an already generated map: the reader, never the raw HTML
bun run context:map business-data-context --section entities

To read more: .agents/skills/project-context/SKILL.md and its references in references/, one per mode. The anatomy of a map, its section-by-section reading, the freshness check and self-updating are in business-context-maps.md.

The underlying idea. This context is synthesis: two sessions would write it differently and redoing it is expensive. That is why each mode reads all its sources, notes what it could not verify instead of inventing it, and never replaces what already exists without showing you the diff.
