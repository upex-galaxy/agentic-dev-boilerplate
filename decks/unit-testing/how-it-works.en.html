00 · tests that pin down behavior

Tests that fail for the right reason, before the code.

/unit-testing designs and writes tests for one unit: a function, a class, a module. It covers the red-green-refactor cycle, how to name each test, what to mock and which coverage to look at. It runs on its own, on the code you point it at, or in the middle of a story, when /sprint-development finds a slice that is worth doing test-first.

for whoever codes works with the runner the app already uses tests behavior, not implementation

01 · when to use it

One unit, its tests, and nothing else

It is a deliberately narrow skill: it does not touch Jira, deploy or do code review. It produces tested code for one slice and hands control back.

Use it when

The request is about tests for one unit

  • "Escribe unit tests para esta función o esta clase." (Write unit tests for this function or class.)
  • "Haz TDD de este tramo" (do TDD on this slice), "red-green-refactor".
  • "Qué mockeo aquí?" (what do I mock here?) · "Cómo nombro este test?" (how do I name this test?)
  • "Qué cobertura le pido a este módulo?" (what coverage do I ask of this module?)
  • You are in Stage 2 of /sprint-development and the slice is pure logic, complex branches or the reproducer of a bug.
Do not use it for

What belongs to another layer

  • Implementing a whole story (plan, code, review, deploy): that is /sprint-development, which can call this skill inside.
  • E2E or integration tests: out of scope. The browser is /playwright-cli; designing those tests is part of a separate QA flow.
  • Running the regression suite before a release, or formal QA.
  • Deploy to production.
Unit tests are development work, not QA work. They are written while coding, not in a later phase. That is why the skill reads no Jira fields: a unit test is a concern of whoever writes the code, not an artifact of the flow.

This is the canonical order for an AI starting cold. It stops early when what comes next adds nothing for the slice.

The unit under test

Its public interface first: it is the contract the tests have to pin down.

The tests that already exist

The *.test.ts or *.spec.ts files in the same folder. They are extended, not duplicated.

Who calls it

The runner configuration

04 · entry 1

Standalone: from the pointed-at code to a coverage report

With no /sprint-development in between, it works against the code you point to and sorts itself out with what it finds.

The AI does

It identifies the unit and decides whether it goes test-first or after. It writes the tests with the project's naming convention and mocks only external dependencies.

It runs the suite until green and measures that unit's coverage.

You decide

Which unit, when the request is ambiguous: the AI confirms with you before writing. If nobody can answer (a worker or a routine), it picks the most likely unit, notes it and carries on.

The runner, only if stack.test_runner is null: the AI asks you and the choice is saved with bun run agents:setup --stack. With nobody present it decides, as a technical decision, and reports it as DECIDED.

Output

Test files next to the code, with the same name plus .test.ts.

A report: files added, passing tests and the coverage delta.

Gate tests green and the unit's coverage verified.

06 · red-green-refactor

The short cycle is what gives the value

Test before the code, in cycles of five to ten minutes. If a cycle runs past half an hour, the slice is too big: split it into smaller behavior steps.

Red · a failing test

The smallest test that captures one piece of behavior. It has to fail on the assertion; one that fails because the file does not compile tells you nothing. If it passes on the first run, something smells wrong: investigate before going on.

Green · the minimum code

The simplest thing that passes it. A hard-coded value is fine at this stage. No code for tests that do not exist yet.

Refactor · only on green

Extract, rename, deduplicate, with the tests watching. Refactoring on red is losing the safety net exactly when it is needed most.

Before the first cycle the seams are named: the points where the behavior can be tested without standing up the whole system. A worker or /autonomous-delivery takes them from the story's plan; if the plan names none, it uses the highest one that already exists and notes it in progress.md.

Type of code Test-first or after?
Business logic, pure functions TDD, strongly recommended
Algorithms, parsers, state machines, validations TDD
Bug fix TDD: the test that reproduces the bug goes first
Performance-critical code TDD, with benchmarks next to the assertions
Presentational UI components After (or component tests, which are often skipped)
Integration glue (DB wrappers, API clients) After; integration tests cover it better
Throwaway scripts, one-off migrations Skipped

rule of thumb: if it has branches, math or string parsing, it goes with TDD; if it mostly orchestrates other things, the test goes after or a higher level covers it

Cascading testsWriting all the tests and then all the code is not TDD: you lose the design feedback of the small cycles.
Green in one goFifty lines to pass one test: the test is not guiding the design. Shrink the slice.
Not running after every changeIt breaks the cycle. That is what watch mode is for.
07 · names

A name that explains the failure in one line

A test's name is what you see when it fails, almost always in a CI log and months later. If it cannot be named in a few words, the test does too much.

AAA · body structure

Arrange, Act, Assert

  • Prepare the inputs, call the unit, check the result.
  • The name says what is true, in declarative form.
  • Short and easy to scan; less explanatory when the behavior is complex.
Given-When-Then · BDD style

Precondition, action, result

  • Reads like a specification.
  • Useful for onboarding or for people who do not code.
  • Verbose: on a trivial test it feels ceremonious.
The hybrid the skill recommends: short describe blocks carry the context (the "given"), and each it states the behavior. Hierarchical context, failure messages that explain themselves, nothing repeated. 
describe('cart with items', () => {
  it('returns total including tax when item added', () => { ... });
  it('returns 0 when all items removed', () => { ... });
});

describe('cart with no items', () => {
  it('throws when attempting checkout', () => { ... });
});
Bad Good
testGetUser returnsUserWhenIdExists
testError throwsValidationErrorOnEmptyEmail
testBoundary appliesDiscountAtExactly100Threshold
callsApiOnce a behavior name, not an interaction with the mock

when the same rule holds for many inputs, parameterize and name the rule, not each case

08 · what to mock

Mock the edge of the system, not what is inside it

A test that mocks every collaborator verifies the mock graph, not the code. Real implementations are the default; the mock is for what makes a test slow, brittle or non-deterministic.

Tool What for
Stub Replaces the implementation with a fixed return value.
Spy Wraps the real implementation and observes the calls without changing the behavior.
Fake A working but simplified implementation: an in-memory database, a fake clock.
Mock A programmed expectation that fails if it is not called as expected. It tends to tie the test to the implementation: spies and stubs are preferred.
Mock

The external edges

  • HTTP, database clients, filesystem.
  • Time (fake timers or an injected clock) and randomness (a seed or an injected generator).
  • Code that depends on the environment: process.env, native modules.
Do not mock

What you are testing

  • The unit under test: that would be testing the mock.
  • Pure functions: they are deterministic, you call them and that is it.
  • What is not yours, when it can be avoided: wrap the library in an adapter of your own and mock the adapter.
Dependency injection first. If the function receives what it needs as an argument, the test passes it a fake and that is it, with no module patching. jest.mock or vi.mock are left for when the seam is unavoidable: side effects on module load, a third-party SDK. 
// service.ts: the dependency comes in as an argument
export async function getUser(id: string, db = defaultDb) {
  return db.users.findOne({ id });
}

// service.test.ts: a fake, no jest.mock
it('returns the user', async () => {
  const fakeDb = { users: { findOne: async () => ({ id: '1', name: 'A' }) } };
  expect(await getUser('1', fakeDb)).toEqual({ id: '1', name: 'A' });
});
Mocks that are not cleaned upState that leaks between tests and false positives. Clean them up in beforeEach, and restore a spy when done.
Five mocked dependenciesIf setting up the mocks takes more lines than the test, the unit is not a unit: test the leaves, and the orchestrator goes to an integration test or uses fakes.
A badly chosen async mockmockResolvedValue versus mockReturnValue: the wrong one breaks silently.
09 · coverage

A smoke alarm, not a goal

Low coverage means missing tests. High coverage does not mean good tests: a test that calls the function and asserts nothing also adds lines. What is useful is each PR's delta, not the global number.

What to measure

Branches before lines

  • Branch coverage is the most actionable metric: each side of every if, &&, || and ternary.
  • High line coverage with low branch coverage means half the conditionals are untested.
  • Mutation testing (Stryker in JS/TS) injects small errors and checks whether any test notices. Slow: weekly or nightly, on the critical modules.
In CI

Gates by delta, not a fixed threshold

  • Warn if a PR lowers coverage by more than 2 points; block if it lowers it by more than 5.
  • Fail if a critical-path file, declared explicitly, drops below its threshold.
  • A single global threshold punishes the refactor that deletes tested code and rewards filler.
Type of code Suggested coverage
Business logic, pure functions 90-100%
Public API methods 90% or more
Internal helpers 70-90%
Presentational UI components 60-80% (E2E covers the rest)
Glue, configuration, wiring 50% or more, or skipped
Generated code, throwaway scripts excluded

these are guides, not contracts: a helper at 70% that exercises every important branch is worth more than one at 95% whose missing 5% is the only error path

Noise is excluded so the number reflects real gaps: generated code (types, OpenAPI), third-party copies, *.d.ts files, configuration, migrations, stories and the tests themselves. If everything is excluded, the metric says nothing.
10 · guardrails

What the skill never does

The full anti-patterns live in SKILL.md and travel in the compact registry that subagents receive (.agents/skills/REGISTRY.md).

Does not test implementation details: private helpers, internal state, number of calls to internal methods. Internals get refactored freely; the tests should not even notice.
Does not skip the red. The test goes before the code and fails for the right reason.
Does not use weak assertions such as toBeTruthy() or toBeDefined() when an exact value is expected.
Does not share mutable state between tests. It is reset in beforeEach or created inside the test; otherwise you get failures that depend on the order.
Does not let a flaky test through as green. The cause gets fixed (timing, shared state, network) or the test is quarantined with a ticket.
Does not let lying tests through (LT-1 to LT-3): the ones that pass without checking the behavior or break on an innocent refactor. The table is in tdd-workflow.md, section Lying tests.
Does not test the framework: matchers, a library's internals, ORM mechanics. Your own logic gets tested.
Does not carry on without the official documentation when it needs it: if no library documentation tool is available, it stops and tells you which one is missing, with no silent substitute.
