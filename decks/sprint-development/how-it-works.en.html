00 · from ticket to deploy

One story, five stages, no gate skipped.

/sprint-development takes a Jira story all the way to deployed code. It plans before writing a line, checks what it builds against the running app, sends the diff to a reviewer who did not write it, and only then moves it to staging. Production is a separate event, with your approval.

for whoever codes, whoever leads and whoever prioritizes one story or a whole sprint, in order the plan lives in Jira, not in a local file

01 · when to use it

Every time a story moves into development

It is the repo's development loop. The same pipeline runs for a new story, a bug or an implementation left half done: only the input and what each stage receives change.

Use it when

There is code to carry from Jira to a deploy

  • You pick up a new story that is in Ready For Dev.
  • You start a feature spanning several stories and want a macro plan first.
  • A bug needs fixing: root cause first, then the diff.
  • A session was cut and you want to resume where it stopped.
  • PR feedback arrived or the CI went red.
  • You want to process a whole sprint, or promote something to production.
Do not use it for

What belongs to another skill

  • Defining the product: that is /project-foundation.
  • Setting up the infrastructure: that is /project-bootstrap.
  • Seeding or refining the backlog: that is /product-management.
  • TDD on a function: that is /unit-testing, which this skill calls midway.
  • Formal QA testing (E2E, exploratory, regression): out of scope; QA picks it up from Ready For QA.
Before you start: .agents/project.yaml filled in, product documents (the PRD and the SRS, or the business maps of an existing app), the story in Jira with refined acceptance criteria, CI configured, .env with the URLs and credentials, and the terminal sitting in the project repo. If something is missing, the skill stops early and points you to the skill that prepares it.
Existing app and the stack: block. The app's scripts and paths come from the stack: block of .agents/project.yaml: each command runs from stack.app_root as stack.package_manager run stack.scripts.<role>. A script set to null means the app does not have it: that check is skipped and the report says so, without inventing one. The app's own conventions (import aliases, structure, test ids) win over the skill's defaults.

The stages always run in the same order because each one feeds the next: the implementation reads the plan, the reviewer reads the diff, the approval opens the deploy. Parallelism happens inside a stage, never between stages.

03 · before Stage 1

First, where it stopped and what blocks it

The three checks run in the main conversation, without subagents, and they always run: the first time too, so that resuming or starting from scratch is an explicit decision.

Phase 0 · is there a previous session?

The scope is the Jira key. If .session/sprint-development/<KEY>/progress.md exists, the AI reads the synced plan and shows you the goal, the last closed stage and what blocks it. It waits for your answer: resume, restart (archives the old one) or abort. If nobody is there to answer, a worker takes the answer from whoever launched it and a routine resumes on its own. Under .session/ only progress.md is written: the plan lives in Jira.

Phase 0b · the roadmap gives the order, Jira gives the status

Reads .context/dev-roadmap.md (if it does not exist, /project-context dev-roadmap generates it) to take the dependencies, the Execution Sprint and the ticket's mockup gates. Then it queries Jira live for the ticket and its direct blockers. If a blocker is not finished, or the ticket is already past development, it stops and asks you.

Startup read · warns, never blocks

Reads the shift-left handoff comment and the ATP as QA's test intent; if the ATP is missing, it warns QA with a comment and goes on. It also reads AI Effort: if it is High, it notes in the plan and in the PR that the story may be large and may be split, and you can break your work into small stacked PRs (about 200 lines and 2 to 5 files each). If it is not set, it notes it and goes on. An autonomous or fleet run never skips a story because of a High.

Epic check

Confirms that the parent epic has its two macro plans (feature-test-plan.md and feature-implementation-plan.md). If one is missing, it offers to generate it or to go on without it: you choose.

Status is queried, never read from a document. The roadmap is the authority on what depends on what; never on whether a ticket is finished. A recent date in that file says nothing about a ticket's status. When the query and the document do not match, the query wins and the old line is marked for the next /project-context dev-roadmap.
04 · Stage 1 · the design gate

A story with UI and no screen: it stops and you choose

This skill does not design and never writes a mockup. It does the check and the handoff, in Stage 1, for every story with UI, before planning code.

What it finds in master-design-plan.md What it does
§8 row and its mockup exist Builds with the screen spec (§4) and the frozen tokens (§2). A deliberate deviation is ratified in §5 before coding.
§8 row marked 🔒 mockup-gated The row already says what is missing: it is the gate's entry, not a block. One of the three routes.
No §8 row The same three routes, and the row gets written too.
The project has no master design plan Fidelity only with DESIGN.md (tokens, no reference screen), and it says so in the plan.
Route (a) · the one offered first

Just-in-time mockup

Hands off to the screens phase of /design-system: builds the brief, commissions the screens with the best method available and returns a bundle. A person ratifies each mockup.

Route (b)

Spec only, ratified in §5

Valid when no design tool is at hand or the screen is trivial next to existing patterns. If the deviation is architectural, an ADR too.

Route (c)

Only DESIGN.md

Token fidelity, no reference screen, with your explicit approval.

With nobody present

Who picks the route

A supervised worker asks whoever launched it. A routine follows the route its brief names; if it names none, it does not build that screen and reports it.

When the order flips

ADR before mockup

If the screen holds an irreversible decision (a delete confirmation is the deletion policy), the ADR is ratified first. Drawing first leaves the policy in the hands of whoever composed the screen.

The fidelity reference is the live UI + the tokens in DESIGN.md. The mockup is inspiration. A UI change that departs from the live UI or the tokens without ratification in §5 is a defect in review; following the improved live UI where the mockup says otherwise is not (AGENTS.md, Critical Rule #14). Whatever the mockup has that is good and the app lacks gets noted as a future tech story, not forced into this story.
05 · Stage 1 · planning

The plan is written in the session and lives in Jira

It is never skipped, not even for a bug: even if it is one paragraph of root cause before the diff. A feature of three stories or more starts with a macro plan; otherwise, straight to the story plan.

Read the criteria and the test plan

Each case of the Acceptance Test Plan maps to an implementation step. The ATP is always read synced with bun run jira:sync-issues get <KEY> --include-comments: from the story's field in jira-native, from the Test Plan issue in jira-xray. Never with a view of the field.

Read what is already decided

The ADRs in .context/ADR/ and the SRS are mandatory if the plan touches a migration or a path of auth, permissions, session or tenancy. A new technical decision that is architectural and hard to reverse gets promoted to an ADR before coding; the plan leaves the backlink.

Publish, sync, read back

The plan goes into the story's spec_implementation_plan field (or into a fallback comment if the field does not exist). Before publishing, it is converted to ADF and measured: over 30,000 characters is a STOP with a proposal of what to cut, never a trim. Then, sync and read the materialized implementation-plan.md.

Move the ticket

Ready For Dev → In Progress with the slug start_working, reading the assignee before and after. A slug the catalog does not have follows the fallback protocol in artifact-lifecycle.md: never a remembered id.

RPC gate If the story writes or changes a Postgres function that receives an identity or a scope from the caller (p_actor_user_id, or similar), the plan answers the six questions in rpc-authorization.md before Stage 2. A SECURITY DEFINER bypasses RLS: its WHERE picks rows, it does not authorize whoever asks.
The AI does

Reads story, ATP, ADRs and glossary; breaks it into steps; publishes and syncs.

You decide

The design route, whether to go on without a macro plan, and what leaves the plan if it does not fit.

Output

The plan in Jira, its copy in .context/PBI/ and the ticket in In Progress.

06 · Stage 1 → Stage 2

A PR nobody can review does not get started

At the end of the plan, the planner estimates how many lines the change will move. Past about 400 lines of diff, review stops finding defects. The decision to split is made before any code is written.

Forecast lines Review Size What happens
under 200 Low Moves on to Stage 2.
200 to 400 Medium Moves on, with a warning that the PR is nearing the budget.
over 400 High Gate: a PR chain strategy that is decided and has its trace is required.
The planner emits

It never picks the strategy

  • With Review Size High it writes Chain strategy: pending and leaves the trace empty.
  • The block stays at the foot of the plan, so it reaches Jira with it.
/git-flow-master decides

With the decision tree in view

  • Returns the strategy (stacked-to-main, feature-branch-chain or size-exception) with its Decision trace: and Decided by:.
  • The plan is updated in Jira and synced again.
The gate fails closed. A label without a trace, or a trace that only repeats the conclusion, counts as pending and blocks Stage 2. If the agent that writes the value could open its own gate with a plausible label, the gate would not exist.
07 · Stage 2 · implementation

Step by step, and green before every push

The implementation walks the plan one step at a time. It touches only what the story says: no drive-by refactors. If a function calls for TDD, it is handed to /unit-testing and you come back when the unit is green. The plan names the seams where to test, and hands them over.

Verification cap=3

Three checks in parallel

  • Lint, types / build and unit tests run at the same time; the orchestrator iterates only on what comes back red.
  • The commands come from the stack: block (the role lint, types or test, from stack.app_root) and from package.json, never from memory. A null role is skipped and reported.
  • It does not grow to five verifiers: there are three.
Commits

One per logical step

  • Semantic prefix, no AI authorship lines, with the forensic trailers.
  • Never --no-verify; a broken hook is fixed in its own commit.
  • Never force-push or rewrite what was already pushed.
A bug with an unclear causeIt calls the diagnosing-bugs skill and follows it through its six phases; then it fixes the bug, because that skill only diagnoses. If it is not installed, it first writes the failing command and says so once.
Out of scope: E2E and integration testsThat is QA and test automation work. Here, unit tests are what gets written.
Standards read inlinecode-standards.md (TS patterns, alias imports), error-handling.md (fail fast in public methods, null in utilities) and data-testid-standards.md.
The docs travel with the changeIf the story adds, renames or retires a skill mode, a script, a route, an MCP or an environment variable, or changes a behavior that some page describes, the same PR fixes every doc that names or describes it. bun run docs:check tests the mechanical part.
08 · Stage 2 and Stage 3 · live-UI

Tests pass with the screen broken: that is why you look at the app

A story with UI is validated against the running app, not against a reading of the mockup plus green lint, types and tests. A story without UI skips all of this.

Stage 2 · while it is being built

The dev server open

  • It re-renders after every change that matters: the bug shows up while coding, not later.
  • Sometimes it shrinks the scope: if the live app already has what the story took as new, the task goes from building to hardening.
Stage 3 · before approving

One final pass, in the browser

  • Every screen of the story: loading, empty and error states, responsive, navigation.
  • Every interactive criterion, end to end: click, typing, submit.
  • The evidence (screenshots) feeds the compliance matrix.
Tier Good for Not enough for
Tier 0 · authenticated HTTP probe Routes and status, auth redirects, server-rendered content, data in the markup, quick re-checks. Layout, computed tokens, client states, breakpoints, interactive flows, screenshots.
Tier 1 · browser (/playwright-cli) Everything that renders, gets touched or gets seen, and every screenshot cited as evidence. Never against a production build: always the dev server.
Gate A story with UI does not reach the merge with an open, unratified live-UI gap. Each gap is fixed on the spot, validated again, or ratified as a §5 divergence if it is a deliberate deviation you approved. A UI story approved with HTTP evidence alone breaks the rule.
09 · who enters the app, and how

One declared account, one named browser

The AI enters the app only as the account the project declares. If it is not declared, it stops: it never improvises another.

The identity

Declared by name, resolved at runtime

  • .agents/project.yaml → testing.automation_identity stores the names of the variables; the values live in .env.
  • A dedicated account, outside production, that belongs to no real person.
  • Empty slot or missing variable: STOP and report. No other account, no creating one, not your browser.
Always forbidden

Bypassing the app's login

  • Service role, secret or admin keys.
  • User administration APIs; generated magic links or reset links.
  • Hand-signed JWTs, hand-built cookies, impersonating any account.
  • If a check seems to need it, it is a finding to report, not a step.
# named session, in memory; the credential is only typed with --raw playwright-cli -s=<KEY> open <web url>/login playwright-cli -s=<KEY> snapshot playwright-cli -s=<KEY> --raw fill <ref> "$<EMAIL_VAR>" playwright-cli -s=<KEY> --raw fill <ref> "$<PASSWORD_VAR>" playwright-cli -s=<KEY> click <ref> playwright-cli -s=<KEY> close playwright-cli list # the proof: <KEY> is gone
Always a named session (-s=<KEY>), in memory and headless per .playwright/cli.config.json; never --persistent or --profile.
One identity, one live browser. Two subagents with the same account run one after the other; parallel work needs a second declared identity.
You close your own, by name. Never close-all, kill-all or pkill: they cut the sessions of other worktrees.
Session material is a secret. Cookies, storage state or .har: only in the session's scratch directory, deleted before the report, declared as secrets_materialized: and cleaned:. A cleaned: no is a block.
The rules travel in the briefing. A subagent does not read references/ on its own. Every dispatch that logs into the app carries in its component 7 the identity by variable name, the list of prohibitions, the hygiene contract and the browser session rules. An omitted rule is an absent rule.
10 · Stage 3 · code review

A reviewer who did not write the code, and someone who judges it

The branch is pushed and the PR is opened with /git-flow-master, which picks the base according to the repo's strategy. The Jira automation should move the ticket to In Review in about 30 seconds; if it does not, the skill fires pull_request and flags the gap.

The reviewer proposes

A fresh subagent, with no context of the implementation, goes through the checklist in review-pr.md: criteria covered, lint and build, standards, security, RPC authorization if there are migrations, UI fidelity. It returns findings with severity and file:line evidence. No evidence, no finding.

The orchestrator adjudicates

Each finding is checked against the diff and the criteria: legitimate gets fixed (back to Stage 2 through fix-issues.md), false-positive is dropped with a one-line reason. Applying a false positive is as much a defect as ignoring a real one. An architectural rework goes back to Stage 1.

The compliance matrix

One row per criterion scenario, with what proves it (test:, manual:, exempt: with a concrete reason, review-approved:) and its evidence. A row marked uncovered without justification stops the merge.

Severity Means
BLOCKER Stops the merge: a failing criterion, a security hole, a broken build, a risk of data loss.
MAJOR Fixed before the merge: a real defect, a standards violation with impact.
MINOR Low impact: it is fixed or a follow-up is opened.
NIT Cosmetic or preference: optional.
Two review axes. With a spec behind the story, two reviewers review in clean contexts, one against the spec and one against the standards, and each marks the axis of its findings; in solo mode they are two passes one after the other (review-pr.md, Two-axis review). The PR also declares its Merge danger: a one-way or two-way door, and the blast radius; for a diff that cannot be trusted to be contained it calls blast-radius, or judges it by hand if it is not installed.
Before the merge, too: the docs changes the story asks for go in the same PR branch, and if the story brought a new or ambiguous domain term, it is flagged so the PM adds it to .context/business/domain-glossary.md. The implementation does not edit the glossary.
11 · Stage 4 · staging deploy

Merged is not deployed: it is verified at the destination

The PR merge happens only with your OK: the skill never merges on its own. After that, CI runs and the staging deploy is watched until the deployment of that commit says READY.

With an integration branch

git_strategy.branches.integration has a name

  • The PR merges into that branch, whichever .agents/project.yaml says; never a literal in a command.
  • CI deploys staging; the skill queries the deployment by SHA until READY.
Without an integration branch

The value is null

  • It happens with solo-main, github-flow and trunk-based.
  • There is no merge to staging: Stage 4 verifies the Preview deployment of the PR's branch.
  • The merge to git_strategy.branches.production is Stage 5.

The ticket moves to QA, verified

The automation should move In Review → Ready For QA; if it does not, the skill fires deployed (bugs: fixed_and_deployed; tech items without QA: complete) and re-reads the status. It never marks Ready For QA without green CI and a passed smoke test.

The notice and the assignee

Moves the assignee to the QA named in qa_assignee (the record of who followed the story from shift-left), because the merge automation usually leaves it on the developer. If the field is empty, it leaves the assignee as it is and says so in the comment. It comments with the PR URL, the branch and a mention of QA, and verifies that the change stuck.

Tokens: optional and cumulative

With the Ready For QA status verified, and again after every fix cycle, it reads the current value of development_token_usage, adds the tokens measured for this cycle (input plus output, no cache) and publishes DTU cycle N: +x K (total y K). With no figure available it stays empty and the verifier says N/A with the reason. It is never estimated.

QA defect: the story goes to blocked

When QA reports a defect, the story stays in blocked. The skill fires fix_defect on the story, fixes it through the bug flow and hands it back to Ready For QA with its token cycle.

Closing the session

With the ticket in Ready For QA and the smoke green, the session is archived in .session/.archive/ and a summary is left in memory. It waits for you to tell it which ticket is next.

QA's verification in staging stays out. A separate QA flow takes the story from Ready For QA. If the staging smoke comes back red, it goes back to Stage 2.
12 · Stage 5 · production

Production is another event, with another approval

It is never chained from Stage 4. It runs only with QA green in staging and explicit business approval, from a person or from a brief that names that ticket and that deploy. If the session was already archived, Phase 0 reopens it and adds the Stage 5 entries.

Release checklist

pre-deploy-checklist.md: tests, types, lint and production build; review approved; production variables and secrets; migrations ready; recent backup; monitoring and alerts; PM and QA with their go.

Deploy + monitoring window

One subagent deploys and another, in the background, watches health. The orchestrator stays online at least through the window in which a rollback is decided, before calling the deploy good.

Rollback if the KPIs go red

rollback-plan.md: go back to the last healthy deployment, validate production, investigate the cause, fix and re-test in staging. No other feature starts until the rollback is finished.

On any subagent failure: the skill stops and reports which stages closed, which artifacts were left and which Jira transitions fired. It offers you retry, skip the step or abort. It never fixes things on its own or rolls back on its own.
13 · who does the heavy lifting

Orchestrated by default, all in one session if you ask

Both modes run the same stages, the same gates and the same verification, in the same order. Only the delegation changes. The mode is resolved once and stays fixed for the whole run.

Orchestrated (default) Solo (opt-in)
Work of each stage A fresh subagent per stage, with the 7-component briefing Inline, in the main conversation; zero subagents
Verification cap=3 Three verifiers in parallel The three checks inline, one after the other
Fixes after the review A fix subagent The fix inline
Review Two reviewers (spec and standards), then adjudication One deliberate pass with fresh eyes, then the same adjudication

How to ask for Solo: an explicit signal in the message, such as solo, no subagents, in a single session or inline. If the signal is ambiguous, the AI asks once and confirms the mode with you before starting.
14 · a whole sprint

A sprint in one session, or one session per story

There are two axes. Scope: one story or a sprint (batch). Executors: one or several. With one executor, the loop walks the tickets in this session. With several, each story has its own session and the conversation that talks to you is the conductor.

Batch · one executor

The sprint report rules

  • Before the loop, it exists or is generated: .context/reports/SPRINT-{N}-DEVELOPMENT.md; if it is more than 24 hours old, it is regenerated keeping its Session Log.
  • The loop runs Stages 1 to 4 per ticket and waits for your OK before the next one.
  • A blocked ticket does not move the next one forward: it is reported and waits.
  • Stage 5 never runs in batch: production is manual, ticket by ticket.
Fleet · several executors

One worker per story, up to an open PR

  • Only in batch, when you ask for it or when orchestration.max_workers in .agents/project.yaml is greater than 1.
  • Each worker runs Stages 1 to 3 on one ticket, in its own worktree, without human checkpoints, and stops at the open PR.
  • A worker is recognized by its prompt: /sprint-development <KEY> fleet worker and the path of its brief. Never by the environment.
PENDING→ IN_PROGRESS→ IN_REVIEW→ MERGED→ STAGING_DEPLOYED→ PROD_DEPLOYED BLOCKED ABORTED

Each row of the report advances with each Jira transition; BLOCKED branches off sideways from any active state. In a fleet, only the conductor writes the report.

Only the conductor Why
Merge + staging deploy + its verification One staging and one correct merge order: by dependencies, one at a time, each deploy in READY before the next.
Migrations to the shared database Irreversible and they hit everyone at once; the worker sends its SQL and waits.
Regenerating from the live instance Supabase types or bun run api:sync: a worker would absorb another worker's unmerged schema.
Sprint report, bulk sync, generated records Files across the whole repo with a single writer.
launch.txt is always written, in .session/sprint-development/sprint-<N>/ of the primary checkout: one self-contained line per ticket of the round. If an orchestration layer is available (/orca-orchestration), it opens and supervises the sessions. If not, you paste each line into a terminal. The rest of the rules does not change, and with a single executor none of this exists.
15 · safety rails

What the skill never does

The full list lives in SKILL.md (Compact Rules and antipatterns). These are the ones you notice first from the outside.

It does not code without a plan, nor declare a story finished without tests, types and lint green.
It does not push to a protected branch without resolving the policy. git_strategy.policy.direct_push_to_protected: allowed pushes, confirm asks, forbidden sends it through a PR (Critical Rule #4, mechanics in /git-flow-master).
It does not merge on its own, does not chain production from staging, and does not skip review on a PR that touches production behavior.
It does not guess transitions. It moves the ticket by slug, re-reads the status afterwards, and on a missing slug it lists the live transitions and asks you one question.
It does not re-decide what is decided. Before a technical decision it searches the ADRs, the decision record and sibling tickets. It escalates only product matters, a new security posture or the irreversible.
It does not hardcode credentials, Jira field IDs (customfield_NNNNN) or configuration values: it reads .env, the slug catalog and .agents/project.yaml, and cites the file.
It does not rewrite an ADR to change course: it replaces it with a new one that links to the old one.
16 · what you tell the AI

Invoking it in each terminal

The skill has no named modes: the entry comes from your phrase. You name the skill, the ticket or the sprint, and what you want to do, in English or Spanish.

Claude Code

/sprint-development PROJ-123 /sprint-development PROJ-123 solo

The slash bar loads the skill; the rest of the phrase picks the entry and the mode.

OpenCode

load the sprint-development skill: implement PROJ-123

No slash bar: you name the skill in the phrase.

Codex

load the sprint-development skill: process sprint 4

Same pattern as OpenCode, in CLI or Desktop.

Pi

/skill:sprint-development PROJ-123

Slash bar with the /skill: prefix. In a new folder, /trust once.

If you say something like… It runs
"implement this story" · "work the ticket PROJ-123" Stages 1 to 4 on one story
"fix this bug and merge" Stage 2 with the bug flow, then 3 and 4
"continue implementation" Phase 0, and resume at Stage 2
"code review for PR" Stage 3 with its fix loop
"process sprint N" · "continue sprint" Batch: sprint report and ticket loop
"parallelize the sprint" · "one session per story" Batch in a fleet
"production deployment" · "rollback" Stage 5 or its rollback runbook
17 · who it works with

Who it hands off to, and who hands off to it

Before, if the backlog is missing

/product-management

If there is no story or the criteria are unclear, it is refined there first and you come back. See the deck.

Branches, PRs, conflicts, chains

/git-flow-master

Opens the PR, resolves conflicts, decides the PR chain with its trace and resolves the push policy for protected branches.

TDD midway through Stage 2

/unit-testing

Red, green, refactor on one function, and back to Stage 2. See the deck.

A screen that does not exist

/design-system

Its screens phase produces the just-in-time mockup (route a). See the deck.

Missing foundation or infrastructure

/project-foundation · /project-bootstrap

If there is no PRD and SRS and no business maps, the skill stops and points to /project-foundation or to /project-context data; in an existing app the path is /project-adoption and it never writes a PRD or an SRS to pass the check. If a new project is missing infrastructure, it points to /project-bootstrap. See the bootstrap deck.

Generates and re-orders .context/dev-roadmap.md; this skill only makes targeted changes when a ticket finishes.

Reviewing a teammate's PR

/pr-review-lead

Uses the same checklist and the same severity scale as Stage 3, with its own level of rigor and a published comment.

After Stage 4

QA

A separate QA flow takes the story from Ready For QA. It is outside this skill.

To read more: .agents/skills/sprint-development/SKILL.md and its references/ folder, one reference per stage. How the Jira cache that every stage reads works: the PBI cache deck.

The idea behind it. Each stage leaves something the next one can read, and each gate opens with evidence, not with a label. The AI plans, builds, reviews and verifies at the destination; you choose the design route, give the OK for the merge and decide when something reaches production.
