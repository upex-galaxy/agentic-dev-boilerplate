00 · multi-session orchestration

One conductor, a fleet of sessions.

/orca-orchestration coordinates work that does not fit in one session: a conductor session talks to the owner and hands out the work; each worker is a persistent session that keeps one scope from start to finish (a story, a module, a cluster of bugs), reports through a mailbox, and can be interrupted, asked and resumed. The skill owns the HOW. The WHAT stays with the workflow skill that calls it.

for whoever leads and whoever develops optional by design no runtime: the same lines, pasted by hand

01 · two executors

The subagent is still the default

AGENTS.md §3 is always on: the main conversation is the command center and the single-use subagent is the default executor. This skill adds a SECOND executor and states the exception in writing, because a supervised worker breaks three assumptions of the single-use contract: a new agent per dispatch, no channel until it finishes, and the orchestrator as the only one that asks the user.

Single-use subagent (default) Supervised worker (this skill)
Lives Inside the turn Until you close it
Context Lost when it reports Persists; you keep talking to it
Channel None until it finishes; it cannot be paused Messages, blocking questions and replies at any moment
The owner sees it No Yes: board, terminal, phone
Git The orchestrator's Its own worktree, or the shared checkout with explicit file owners
Good for Reading, verifying, mapping Writing and integrating on its own: a whole story, long work
The practical rule: the subagent explores and returns a map; the worker executes a full scope. The conductor keeps using subagents for ITS own reads, which is what keeps its context light.
Dispatch a subagent

The 7-component briefing

  • Goal, context documents, project standards (from REGISTRY.md), skills to load, exact instructions, report format and rules. Mandatory on every dispatch (briefing-template.md).
Launch a worker

The same briefing, extended for the fleet

  • COMMON.md plus one W-<label>.md per worker: file owners, channel, sibling roster, claims, report path, session label (references/brief-template.md).
02 · before starting

Is this orchestration at all?

Most work is not. The skill's decision tree cuts early.

Does it fit in this turn and is it a read, a verification or a map?

Single-use subagent. Done. This is most of the work.

Do you want to hand the work over and walk away?

That is a handoff, a change of owner: no Task, no Dispatch, no mailbox. A single loose task goes through the binary's orca-cli guide; the whole session, because the window is filling up, goes through /session-handoff.

Do you need to supervise, wait for results, answer questions or run a dependency graph?

Orchestration. Keep going.

Does the work write code?

One Orca worktree per worker. If it does not write code, a fleet in the same checkout (references/topologies.md).

Do you want the workers SUPERVISED?

Native launch, and nothing else: the runtime only recognizes agents it started itself. If the machine lacks the agent's default arguments or the credentials do not reach the worker, the fleet runs anyway, unsupervised, and the owner is told before launching.

Is nobody at the wheel?

references/automations.md. For unattended delivery, /autonomous-delivery decides what runs and this skill launches it.

Situation Use instead
One story, one session, its stages run by subagents /sprint-development in single-ticket mode. A fleet is its batch-sprint mode with more than one executor
Deciding WHAT an unattended run may work on /autonomous-delivery: audit, selection, caps
Branch, commit, push, PR, or a git worktree without a fleet /git-flow-master
One long task, one session, no siblings Just do the task
03 · the gate

Three states, and silence as the rule

The gate looks at the binary plus a reachable runtime. It never checks whether the provider's skill is installed: a machine with the binary and without those guides is just as capable, because this skill knows how to ask the binary for the grammar. 

# the gate in SKILL.md: the scope flag is NESTED
command -v orca >/dev/null 2>&1 \
  && [ "$(orca status --json </dev/null 2>/dev/null | jq -r '.result.runtime.reachable' 2>/dev/null)" = "true" ]
State In a workflow skill In this skill
A · no binary Total silence. It is not named, not recommended, not a prerequisite, and it does not appear in a PR or a plan. The flow writes its launch.txt and the human pastes the lines One line, and only because the user ASKED for orchestration; then, the fallback
B · binary, runtime unreachable Silence (the same fallback) orca open --json once, check again once; if it still does not answer, treat it as A
C · ready The reinforcement switches on without announcing itself: the runtime launches the workers with the identical prompt, and they report to the mailbox IN ADDITION to the file tokens Full mode: conductor, worker, automation
The one-line recommendation (states A or B, only here): level 1 orchestration is already in the session, with the AGENTS.md §3 subagents. The professional kind (persistent sessions you talk to, a mailbox, a board, the phone) needs Orca installed. Without Orca, a launch.txt is still written with one ready-to-paste line per worker.
The test that decides any future edit: would this line make sense, unchanged, to a developer who never heard of Orca? If not, it goes in this skill and not in the workflow one. The real prohibition was always that the orchestrator's absence must not cost anything and must never be reported; a silent gate meets it, and that is why a workflow skill can carry a few lines behind the gate.

05 · modes

Who loads what

The modes are roles, not subcommands: each session loads just enough for its own.

Mode Who Loads
CONDUCTOR The session that talks to the owner SKILL.md + references/coordinator-playbook.md + the provider guides. Its reads go through subagents
WORKER Each launched session The provider guides + worker-contract.md + channel-discipline.md + its domain skill (/sprint-development, /product-management)
AUTOMATION A scheduled routine, unattended references/automations.md + this skill in conductor mode. The dispatcher never produces: its workers do
OWNER The owner, by chat or from the phone The phrases below; the conductor translates
The conductor cycle (native path)
1Run and briefsOne Run per run; the briefs are written BEFORE the Tasks, because the Task spec cites them by path. 2Native launchThe runtime starts the agent (task, worktree, agent, model, effort). A terminal with our command line can never be supervised. 3Read the screenWorker ready and credentials loaded, before sending it work. 4Send the promptThe same text as the fallback, pointing to its brief.
Wait and close
5One waiter per RunWindows of 540 s at most (the harness kills a command at 600 s), each one re-armed with the ack verified in the same command. No homemade monitors. 6Verify the integrationCommits landed, PR open, tracker artifacts in their state. 7Read the cost, releaseThe token footer only exists on the worker's screen and dies with the terminal. Then release by dispatch. 8Orphan auditOnly then is the worktree deleted.
The worker sends

Three things, nothing else: worker_done (once, with an explicit --outcome), ask (blocking) and escalation.

No heartbeats, even if the injected preamble asks for them: each one wakes the conductor just to read "alive".

It never asks the human: no question tool, no mkd deck, no sweep. Errors, blockers and decisions that are not its own go to the session that launched it, which passes them to the human. Exception: the human wrote to it in its own terminal, or the brief authorizes it in writing.

You decide

The scope: the conductor decides scope, the worker decides execution.

What changes the brief: a new file, another ticket, another branch or a shared schema stops the worker and gets escalated.

Output

One PR per worker, which stops there, and a long report written BEFORE worker_done, by absolute path to the primary checkout.

The report is a COUNT, not a narrative.

Gate a stage is not a checkpoint: the worker runs all of them without returning to the prompt until it sends worker_done. And if its measurement contradicts the conductor, it stops and asks with both readings; it never obeys or silently deviates.
06 · the fallback, in full

launch.txt is the contract; the runtime is the shortcut

Without binary and without runtime the work does not change. What changes is who launches and how state is read.

Step Without runtime
Plan Identical: same topology, same collision check, same rounds
Brief Identical: COMMON.md + W-<label>.md, cited by absolute path
Launch The conductor prints launch.txt; the human opens the terminals and pastes one line into each
Identity In Claude Code the line carries no name flag: the hook names the session from the prompt token, and in Pi the adapter does it. In Codex and OpenCode v2.2 the human types /rename <label>--<handle> (only <label> outside Orca)
State The workflow's blocking tokens, plus the tracker and git
Questions In the report, with options and a recommendation; the worker carries on with what does not depend on the answer
Close The human closes the terminals
Claims The degraded ledger, append-only, with smaller rounds 
# one line of launch.txt (Claude Code). The prompt in single quotes is the PAYLOAD:
# identical, byte for byte, to the one the supervised path sends to the native worker.
# It is the bare binary: its MCPs read .env through the .env loader.
claude --model <full-model-id> --effort high --dangerously-skip-permissions \
  '/<workflow-skill> <label> fleet worker. Read <ABS>/.../COMMON.md then <ABS>/.../W-<label>.md
  and execute your brief. Run every stage without returning to the prompt until worker_done is sent;
  stage boundaries are not checkpoints. Channel: orca orchestration. No heartbeats.'
It is always writtenWith or without a runtime, in the scope of the workflow skill that hands out the work. It is regenerated whole on every planning pass: what is closed drops off, nothing is edited in place.
The opening token carries weight/<workflow-skill> <label> fleet worker names the session <label>--<handle> (in Claude Code the hook builds it; on the supervised path there is no name flag), tells the hook it is a launched session that does not ask the human, and tells the skill to run as a fleet worker.
The continuation phrase is not decoration eitherMeasured workers stopped at a stage boundary even with briefs that already forbade checkpoints. The instruction works as a prompt and fails as a pointer to a file.
Every line is self-sufficient and gets validatedThe prompt goes whole inside single quotes, with no apostrophes inside, and the file passes sh -n before anything launches. A quoting error killed a whole fleet whose terminals looked perfect.
Never detect the fleet by an environment variableAn environment prefix does not reach a native worker and was measured empty even on the pasted path. The fleet is detected by the prompt token and the brief.
07 · topology and provisioning

A freshly created worktree lacks what the session needs

Topology comes from what the work writes. And a provisioning gap never announces itself: it disguises itself as another failure, and the worker debugs the wrong thing for an hour.

Activity Topology
Batch-sprint of /sprint-development One Orca worktree per worker, one worker per story. Two sessions in one checkout collide in the git index even if they never touch the same file
Independent bugs One worktree per CLUSTER: three bugs with one root cause are one worker
Refinement with /product-management Fleet in the SAME checkout: it writes to Jira, not to code
Maps, audits, research Not a fleet: single-use subagents
No exceptions: never two workers in the same module, and never two migrations in the same round.
Missing in the worktree How it fails without it
.env Silently on every host: the MCP server starts and dies on its first authenticated call (Critical Rule #9)
node_modules/ and the husky shims Cannot find module, which reads like a broken import; without hooks, a commit skips every gate
.context/PBI/ Silently: the worker does not see the synced story and works from the ticket title
.session/ Not copied: the prompt cites ABSOLUTE paths to the primary checkout (<<PRIMARY_ROOT>>). What is written inside a worktree dies with it

Provision

bun run worktree:provision [<path>] closes the repairable gaps in one go: it copies the gitignored files from the primary (the list is PROVISION_COPIES in cli/lib/worktree.ts), installs dependencies, runs bun run agents:compat and does not copy .session/. Hydrating the tracker cache is left to a human decision.

As an Orca hook

The repo commits orca.yaml: scripts.setup provisions every worktree Orca creates and scripts.archive runs bun run worktree:audit --rescue before deleting it. Trust and hook policy are decided per machine, and the CLI skips the archive hook by default: the conductor passes --run-hooks when deleting, and without hooks it runs the audit by hand.

Credentials on the native path

No launch loads .env into the agent process, with or without a launch line. The MCP servers do not need it: in every harness each one reads the worktree's .env with the .env loader; the CLIs (acli, supabase, vercel) use their own login and nothing is exported to the shell. The conductor confirms on screen before sending work.

Before deleting

Uncommitted changes, unintegrated commits, bun run worktree:audit <wt> (STATE, CACHE, DISPOSABLE, UNKNOWN; exit 0 is the gate) and whether anyone is going to resume that session. Only then is it deleted.

08 · claims and conductor operations

One writer for what is shared

A claim is a MESSAGE with a reserved prefix in the subject, and the conductor keeps the ledger. There is no claim command and no lock daemon. Files are not claimed: their collisions are avoided by assigning owners.

What gets claimed

Mutable resources two workers would touch at once

  • identity (one identity = one live browser), seed, record, schema, env-resource y tracker-artifact, each at the smallest defensible id.
Three intents

read · write · enumerate

  • write is exclusive; the other two stack. enumerate is listing a collection that shows entities from the siblings: nobody asserts on its size, content or order.
What is in the brief is already grantedThe conductor decided it at triage and notes it as pre-granted at launch. The worker announces it and works. It only waits on a claim discovered mid-run.
The first message winsThe order is the order of arrival in the mailbox. A denial without an alternative is a bug in the protocol. worker_done releases everything the worker held.
Without runtime, conventionThe same claims.md, append-only, with a grep before touching. It has a real race window: better than nothing and worse than an arbiter. 
# .session/orchestration/<slug>/claims.md: the conductor's, append-only
[09:30] W1 record:orders@staging enumerate pre-granted   -> no assertion on the collection
[09:41] W2 seed:checkout-cart write granted
[09:44] W3 seed:checkout-cart write denied      -> seeds own cart
Migrations on the shared database. The number comes from the live ledger; a worker that needs one sends BLOCKED: migration.
Output generated from a live instance: Supabase types, api/schemas/.
Merge to the integration branch and deploy to staging, one story at a time, in dependency order, verified at the destination.
Fleet-level tracker writes and generated registries such as REGISTRY.md; a conflict in a generated file is regenerated, never merged by hand.
09 · the orchestration: block

Defaults, not policy

It lives in .agents/project.yaml and .agents/README.md documents it. The values are read there; this page does not repeat them. 

orchestration:
  max_workers:          # concurrent workers per round             {{MAX_WORKERS}}
  default_agent:        # claude | codex | opencode | pi       {{DEFAULT_AGENT}}
  default_model:        # worker model, full id                {{DEFAULT_MODEL}}
  default_effort:       # worker effort                        {{DEFAULT_EFFORT}}
  conductor_model:      # conductor model, full id             {{CONDUCTOR_MODEL}}
  conductor_effort:     # conductor effort                     {{CONDUCTOR_EFFORT}}
  subagent_model:       # sonnet | opus | haiku | fable        {{SUBAGENT_MODEL}}
  permission_modes:     # conductor auto · worker bypass · subagent inherit
  model_overrides:      # model and effort per brief topic
  orchestrator_name:    # the app, as the operator names it
  orchestrator_cli:     # the binary; empty = no orchestrator on this machine
  message_verb:         # messages BETWEEN sessions, intact
  terminal_verb:        # commands and keys, NEVER conversation
  orchestrator_skills:  # provider guides, loaded NEXT TO this skill
The user wins

An explicit instruction overrides the default

  • "Run six", "use the small model", "codex for this one": it holds for that run. The user is not asked to confirm a default they never mentioned.
No block

It degrades, it does not break

  • Cap 1, the harness defaults, no orchestrator named. /sprint-development in single-ticket mode never reads the block.
The two verbs are not interchangeable. If a PERSON is going to READ it, it does not go through terminal_verb: it truncates without warning, keeps the TAIL and reports success anyway. If a shell or a TUI is going to EXECUTE it, that is what it is for. The only exception is the first prompt of a supervised worker, short and pointing to a file, because native launch has no argv. And a round is concurrency ("Sprint 42, round 2"); an execution sprint of .context/dev-roadmap.md is an order, and may need several rounds.
10 · unattended routines

The dispatcher never produces

An automation runs a versioned prompt on a cron-style trigger, with no human. It produces no artifact, not a draft and not a plan: it creates the worker that produces and closes its own session. When something is ambiguous, it reports it instead of guessing.

Delivery routine

Es /autonomous-delivery <mode>

  • Its lock, audit, selection, caps and hazards belong to that skill; they are not repeated or duplicated here. This skill only launches and closes its workers, and orchestration.max_workers can only lower the mode's cap, never raise it.
Any other routine

Takes its own lock first

  • <<PRIMARY_ROOT>>/.session/orchestration/automations/<routine>/lock.json, created without overwriting and read back. A live lock means exit with one line; an expired one is claimed and reported; with no declared window, it fails closed.
Three brakes, and one fix does not start anotherThe output passes automatic checks and a cold review by a reader who did not write it; a person's review arrives later and never stops the run. One automatic trigger is added at a time, with a retry cap. A fix run does not chain another.
Decision logA long or unattended worker writes one row per decision with its evidence as a pointer (/show-me-your-work, or its six columns by hand if it is not installed). A note that fails is reported and the run continues.
One round, with a capAt most orchestration.max_workers workers in total; the rest go to the report as deferred, in the order in which the next trigger should take them.
An empty run is correctPicking a marginal item so the report is not empty spends a worker on work nobody asked for.
The report is written at every step boundaryIf the run dies midway, it is the only place where the workers still running were noted.
Git is the truth, the tracker is a hintSomething shipped when its merge commit is an ancestor of the integration branch after a fetch, and it is live when the deploy of that SHA reads READY.
11 · what the owner says

Natural language, translated by the conductor

The Run's roster.md is what turns "the one on BK-123" into a task, a dispatch, a terminal and a worktree.

The owner says The conductor does
"how is it going?" A table: KEY · stage · status · last message
"tell the one on BK-123 that…" The MESSAGE goes to the mailbox; to the terminal, at most, a one-line nudge so it checks its mail
"pause X" An interrupt in its terminal, verified on screen: there is no native pause
"close X" Release by dispatch; with no dispatch, count the worktree's terminals first, because the stop verb has a whole-worktree radius
"resume last night's run" Tie this session to the Run id in run.md and list tasks
"merge W2's story" PR checks and review, merge in dependency order, staging deploy verified for that SHA. Only the conductor
12 · guardrails

The ones that cost the most when forgotten

The full list is in the skill's "Hard rules"; the compact ones travel to the subagents through .agents/skills/REGISTRY.md.

A success code describes the call, never the outcome. A launch that died in the shell, a terminal send that delivered the tail, a message accepted and unread: all returned success. Verify at the destination.
A message that starts mid-sentence is a truncation. It is not answered or reconstructed: the pointer is requested.
A name is not an address. Sign with the terminal handle plus the Run id, and whoever receives a message with no identifiable author asks.
ok: false on a terminal send means a human is typing there. It is never retried.
Every level in the mode from permission_modes, never edits-only: commands would sit waiting for a human who is not watching. The worker runs in bypass because auto pauses and asks after several blocks (ADR-0020); the conductor verifies the mode on the worker's screen.
Critical Rule #13 counts double in a fleet in the same checkout, and a worker's commits carry the trailers Worktree: and Session:, which are forensic and not attribution (Critical Rule #3).
13 · what you tell the AI

Invoking it in each terminal

It has no invocation modes: the role comes from context. It is enough to name it or to ask in your own words, for example "orchestrate", "launch workers", "one session per story", "fleet status" or "resume the run". In WORKER mode it loads itself when a brief names it.

Claude Code

/orca-orchestration

The skill's slash command, no arguments.

OpenCode

load the orca-orchestration skill

No slash command: you name the skill in the sentence.

Codex

load the orca-orchestration skill

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:orca-orchestration

Slash command with the /skill: prefix. In a new folder, /trust once.

A worker can be from any of the harnesses. The harness comes from orchestration.default_agent or from what the owner says. In Codex and OpenCode v2.2 the conductor types /rename <label>--<handle> in the worker's terminal, because a session cannot rename itself; in Claude Code the hook does it and in Pi the adapter. The worker does rename its own tab, as its first action.
