00 · tooling

Before the binary, the skill that knows how to use it.

/acli and /vercel-cli are skills of type utility: they don't run a workflow, they teach the AI to use a binary the workflow needs. This deck puts those two together with the bun run jira:* scripts that live around acli, and the .env loader and the startup and credentials commands (setup:doctor, harness:env) that decide whether an MCP server starts with its key or without it.

01 · when they apply

When the work touches Jira or Vercel from the terminal

Neither one decides what to do: that belongs to the workflow skill that calls them. They answer how to do it without breaking anything.

They apply when

A binary is involved

  • /acli: create, transition, comment, link or bulk-operate on Jira issues; authenticate against an Atlassian site from the shell or CI.
  • /vercel-cli: "is my deploy live yet?", sync env vars with Vercel, read build or runtime logs, roll back, detect whether the directory is linked.
  • Both load on their own when a command names their binary (§02), even if nobody says their name.
They don't apply to

What belongs to another skill

  • Reading a ticket's content (ACs, plan, bug fields): that is bun run jira:sync-issues get <KEY>, not acli.
  • Choosing how to deploy or link for the first time: the community skill /deploy-to-vercel.
  • Running a story's deploy stage: /sprint-development, stages 4 and 5. /vercel-cli lends it the verbs.
  • The Atlassian MCP server: it is opt-in and documented in docs/mcp/.
02 · the rule that orders everything

Binary named, skill loaded. Before, not after

.agents/instructions/agent-tool-resolution.md §6.5 calls it a hard gate, not a suggestion: before any Bash call that names a binary from that table, the AI checks that its skill is loaded in the session and loads it if not. Skipping the step means flying blind on syntax, flags, auth and error semantics.

If the command names Loads What the skill brings
acli · jq /acli Slug syntax, custom field IDs, and parsing of the --json output
vercel /vercel-cli (+ /deploy-to-vercel, /sprint-development) Verification, env, debug and rollback; the deploy method; the deploy stages
any other one in the table the skill that .agents/instructions/agent-tool-resolution.md §6.5 names The table is the only list; this deck doesn't copy it

CLI first, MCP as fallback

.agents/instructions/agent-tool-resolution.md §6 resolves tool labels with the CLI as the primary option because it spends fewer tokens. [ISSUE_TRACKER_TOOL] is /acli; the Atlassian MCP stays as an opt-in fallback.

Workflow skills don't call the binary

They write the label ([ISSUE_TRACKER_TOOL]) and the AI resolves it. That indirection is what lets you swap the tool without rewriting the methodology.

When in doubt, --help

It is the authoritative source and is tied to the installed binary. Watch out with acli: a subcommand that doesn't exist falls back to the parent's help with exit 0. Read the body of the help, not the exit code.

03 · /acli

Authenticate, read the right way, write with slugs

acli is Atlassian's official CLI. What is specific to this repo lives in agentic-dev-core/references/acli-integration.md.

before mutating

Fresh auth. acli jira auth status before any bulk mutation and before every bun run jira:sync-*.

An expired session cuts a batch in half with a 401 and no clean rollback; in a sync, it silently poisons the catalogs.

your call

Production Jira from your machine. Transitions, deletions and bulk edits can't be undone.

--yes is fine in CI against an agreed scope; --yes by hand against production is not: every operation asks for your confirmation.

the site

Comes from the yaml. --site "$(bun run --silent jira:url --slug)", with email and token from .env.

Auth is per product: jira auth doesn't authenticate confluence or admin.

Operation Tool Why
Detail read (ACs, scope, plan, bug fields, comments) bun run jira:sync-issues get <KEY> --include-comments acli view returns null in custom fields; the sync resolves slugs and writes one .md per field
Write (create, transition, comment, link, assign) /acli The sync is read-only; every mutation goes through acli
Trivial search (key, summary, status) acli ... search --paginate --json Without --paginate it returns the first page and doesn't warn you

Slugs, never IDs

A custom field is {{jira.<slug>}}, resolved against .agents/jira-fields.json; a status or a transition, against .agents/jira-workflows.json. IDs change per workspace, slugs travel. If a slug doesn't resolve: stop, report and run the matching sync. Never a placeholder literal.

Links: the flags are inverted

link create --out X --in Y leaves "Y depends on X", the opposite of what the names suggest. --out carries the prerequisite, --in the dependent. After every link, link list --key <dependent> --json has to show the prerequisite as outwardIssueKey; if not, delete it and recreate it.

Errors: keep the trace id

unexpected error, trace id: … is the only debugging signal the backend gives, and the only one Atlassian support accepts. Always capture it and report it.

04 · /acli · rich text

Markdown in, ADF out, and the size measured first

Jira stores descriptions, comments and rich text fields as ADF, a JSON tree. acli never converts Markdown: a # Title passed as is gets stored as that literal text. 

# 1. write in Markdown · 2. convert (validates by default)
bun .agents/skills/acli/scripts/md-to-adf.ts body.md body.adf.json

# 3. measure the FULL value as it will be stored
jq -c . body.adf.json | wc -m # must stay at 30000 or less

# ADF built outside the converter (create payload, PUT body): validate it anyway
bun .agents/skills/acli/scripts/md-to-adf.ts --check field.adf.json
the AI does it

Never hand-written ADF. The converter is deterministic, diffable, respects snake_case and stops the combined-marks bug (inline code next to bold or italic gives HTTP 400).

your call

If it goes over budget. Jira cuts at 32,767 characters of the serialized ADF, not of the Markdown. Past the limit the AI stops and proposes which sections to move and where.

It never truncates or splits a value across two fields.

where it goes

Depends on the surface. --from-json on workitem create; --description-file on edit; comment create -F; comment update --body-adf.

workitem edit rejects custom fields. Any form (additionalAttributes, fields, customfield_X flat) ends in exit 1. To fix a rich text field on an issue that already exists, the only way is REST: PUT "$(bun run --silent jira:url)/rest/api/3/issue/<KEY>" con {"fields": {...}} and ATLASSIAN_EMAIL / ATLASSIAN_API_TOKEN from the session. Success is HTTP 204, and you still re-read the field: Jira silently drops some invalid nodes.
05 · the scripts around acli

bun run jira:*: the host, the catalogs and the check

The exact names come from package.json, the only source. These scripts talk to Jira's REST API using the same credentials from .env.

Script Does Watch out
jira:url Prints the active host from .agents/project.yaml → issue_tracker.atlassian_url. With --slug, no scheme, for acli --site Use it with --silent inside $(...). Never trim the https:// by hand
jira:sync-fields Writes .agents/jira-fields.json: slug → custom field ID and its options If the catalog is already populated, it asks for --force
jira:sync-workflows Writes .agents/jira-workflows.json: statuses and transitions per work type Reads the project key from .agents/project.yaml
jira:sync-link-types Writes .agents/jira-link-types.json: link types between issues By hand only: neither setup nor CI runs it
jira:check Compares .agents/jira-required.yaml against the catalog: a missing required field = exit 1 --live also compares the workflows cache against live Jira (warnings only)
The host anchor

ATLASSIAN_URL is not a .env variable

  • The host lives in the yaml and nowhere else: a second copy is the one that goes stale and points the scripts at a dead site while reporting success.
  • If an inherited variable disagrees, the yaml wins and the resolver warns with both values. setup:doctor flags it for deletion.
They live in another deck

Two families with their own owner

  • jira:sync-issues and context:hydrate, the cache of .context/PBI/: PBI as a Jira cache.
  • jira:components and regenerating catalogs after moving instances: jira-administration.
06 · /vercel-cli · verify

Is my deploy live? By SHA, and really waiting

An accepted push or a queued build doesn't say the deploy finished (Critical Rule #16). The question has only one correct form: find this commit's deploy and block until a final state. 

# the SHA of the commit you expect to see deployed
SHA=$(git rev-parse HEAD)

# 1. find ITS deploy: metadata filter + JSON, never grep (retry for a few seconds until it shows up)
vercel ls -m githubCommitSha="$SHA" --format json | jq -r '.deployments[0].url // empty'

# 2. block until READY / ERROR / CANCELED · exit 0 only on READY
vercel inspect "https://$URL" --wait --timeout=10m

--no-wait on deploy, --wait on inspect

This is the asymmetry that confuses most: vercel deploy blocks by default and vercel inspect doesn't. Get it backwards and you either wait ten minutes for a URL you needed already, or run the smoke test against an unfinished build.

Uppercase states

--status READY works; --status ready returns empty and gives no error. And always --format json: the human table carries ANSI colors that break any regex.

Which commit to look at

Stage 4: the commit on the integration branch, git_strategy.branches.integration in .agents/project.yaml. If it is null, as in solo-main, the staging surface is the PR branch's Preview. Stage 5: the production deploy.

If the URL never shows up, it isn't a script problem: the Vercel webhook didn't fire, the production branch is misconfigured in the Vercel project, or the directory isn't linked (.vercel/project.json or .vercel/repo.json). To link for the first time: /deploy-to-vercel.
07 · /vercel-cli · operate

Env vars by scope, logs and rollback

The operations around the deploy. The only safe probe in an unlinked directory is vercel whoami; ls or link ask questions, or with --yes they link as a side effect.

Scope (CLI) Used in Rule
production The production branch Every runtime key that .env.example declares has to exist in both before the deploy
preview Any other branch
development vercel dev and vercel env pull The pull writes .env.local, gitignored: it is never committed
env vars

Diff before pushing. Local keys against vercel env ls preview --format json; a blind push overwrites values that were different on purpose.

Never ATLASSIAN_*, N8N_* or SUPABASE_ACCESS_TOKEN in Vercel: they are the agent's credentials, not the runtime's.

your call

Rollback or forward-fix. If the fix is clear, commit and push; if the bug only shows in production, roll back and debug calmly.

A rollback doesn't undo database migrations, sent emails or changed flags.

logs

Build: vercel inspect <url> --logs.

Runtime: vercel logs <url> --follow.

An env change doesn't redeploy by itself: a new deploy is needed.

# rollback: the previous production deploy, promoted; then verify the alias
vercel ls --prod --status READY --format json
vercel rollback <healthy-deploy-url>
vercel inspect <production-alias> --wait --timeout=2m
Accounts with several teams: --scope <team-slug> on every command that modifies. With the directory linked, the orgId in .vercel/project.json resolves the team and the flag is not needed. The full rollback procedure (Jira transitions, incident note) belongs to /sprint-development, stage 5; this skill provides the execution.
08 · startup and credentials

A missing credential doesn't announce itself: you have to go looking for it

The harness reads its config and launches the MCP servers before any hook runs. Every server that needs a key starts with the .env loader (varlock run --filter), which reads it from .env at that moment, however the harness was launched. If the key is missing, the server starts anyway and only fails on its first authenticated call (Critical Rule #9).

Command What it solves When
claude · opencode · codex The bare binary, with no wrapper script: nothing loads .env into the agent's process, so no secret reaches the AI's shell. Each MCP server reads .env with the .env loader Every time you open the agent from the terminal (or its desktop app)
bun run vars:env:check Names the variable the shell exports with a value different from the one in .env (under varlock the inherited one wins). Names and lengths only When an MCP behaves as if .env didn't exist
bun run harness:env Removes the plain-text copies an old install used to write (the env block of .claude/settings.local.json, .auth/opencode/<VAR>): if it matches .env it deletes it, if not it moves it to .auth/harness-env-backup/ and names it. Never prints a value Once, on a machine that ran the old version. After a change in .env, restarting the session is enough
bun run harness:env:check Exits with 1 while one of those copies is left To confirm none is left
bun run setup:doctor Read-only check: env vars, the Atlassian host, dependencies, the contract between harnesses, the plain-text copies left over, where the secrets come from (.env or the secret manager), the harness-level MCPs this machine declares. With --json, a list of pending actions When setting up, and on any odd tool failure
The signal

A 401, a 403 or a mysterious failure

  • Don't wait for a parse error: it isn't coming.
  • The loader hands the server the variable empty or undefined, and nobody says anything. The check is /mcp inside the session; bunx varlock load --agent shows, redacted, which value fails the schema.
What the AI does

Stop, no shortcuts

  • It tells you the exact variable and sends you to .env / .env.example.
  • It asks you to restart the agent session: the environment was fixed when the MCPs started. In OpenCode, also opencode service restart.

10 · what you tell the AI

Invoking them in each terminal

They are skills without modes. You almost never need to name them: they load on their own when the command names their binary. When you want to force them, like this:

Claude Code

/acli · /vercel-cli

The skill's slash command, through the generated alias .claude/skills.

OpenCode

load the acli skill

No slash command: you name the skill in the sentence. It reads .agents/skills/ natively.

Codex

load the vercel-cli skill

Same pattern as OpenCode, in the CLI or Desktop.

Pi

/skill:acli

Slash command with the /skill: prefix. In a new folder, /trust once.

To read more: .agents/skills/acli/SKILL.md, acli-integration.md y .agents/skills/vercel-cli/SKILL.md, each with its own references/. The loading rule is in .agents/instructions/agent-tool-resolution.md §6.5; the startup per harness, in .agents/instructions/agent-harnesses.md §5.5.

The underlying idea. Each of these tools has a way of failing silently: a page truncated without warning, a dropped field, a deploy that is still building, an MCP server without its key. That is why the skill loads before the binary, and why the result is verified at the destination.
