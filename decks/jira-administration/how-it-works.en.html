00 · Jira administration

Two admin operations that cannot be undone with an undo.

/jira-administration covers two Jira project administration jobs: reconciling its Components with the app's real modules, or repointing the repo to another instance of Atlassian after a site migration. Both write outside the repo (in Jira, or in the machine-wide acli session), so both follow the same sequence: read first, show the plan and wait for your approval before touching anything.

01 · when to use it

Administering the project, not operating tickets

It is a rarely used skill with big consequences. Day-to-day work with Jira (creating, transitioning, commenting) goes through another door.

Use it when

The project or the instance changes shape

  • "Sincroniza los Components de Jira" (sync the Jira Components) · "jira-components": the project's Components module drifted from what the app really has.
  • "Cambió la URL de Jira" (the Jira URL changed) · "repoint jira" · "jira-instance-migration": the company moved the Atlassian site and the repo still points to the old one.
Do not use it for

What belongs to another tool

  • Putting a component on a ticket or any other operation on issues: that is /acli.
  • Refreshing the catalogs without an instance change: you run bun run jira:sync-* directly.
  • Setting up Jira for the first time: it is in docs/setup/README.md, section "Jira (lado dev)" (dev side).

03 · the sealed contract

The rules that hold in either mode

They live in the ## Compact Rules block of the skill, which is what travels to subagents through .agents/skills/REGISTRY.md.

Reads before every mutation. The plan is written after looking at the live state, never from memory.
Approval inside the same run. Nothing is created, applied, deleted or repointed without your explicit yes. Silence or ambiguity means stop and ask. With nobody at the keyboard, the brief that delegates counts as approval only if it names the exact change (mode, key and, in a migration, both instances); otherwise the routine does the read and stops before writing to Jira.
Missing credentials = hard stop. It names the exact variable, sends you to .env / .env.example and asks you to restart the agent session. No shortcuts, no partial run.
Loads /acli before any Jira operation, in both modes. Other tool-owning skills, only if the chosen reference asks for them.
Verifies only with its own mode's steps. It never runs the other mode's verification.
Forwards the rest of the arguments as they are: everything after the mode word reaches the reference intact.
04 · components mode

A component is a module of the running app

Not an epic. An epic is a unit of work; a component is a unit of the running system, finer on purpose, because a filter is only as useful as it discriminates. It is a native Jira field (set it directly, never through {{jira.*}}) and it is the grouping axis for JQL filters, metrics and dashboards.

Phase 1 · derive the module map

Two inputs. What exists: the app's route tree (app/**/page.tsx and app/api/**/route.ts in the Next.js App Router), grouped with the product's vocabulary. What is coming: epics and stories in the backlog that have no route yet.

A component can be declared before the code: a feature in refinement already has stories that need somewhere to hang. The AI proposes, it does not decide.

Phase 2 · read the live Components

It lists each component with its issue count. That number is the point: deleting and recreating one under a new name would orphan all of its issues.

Each proposed module is classified: it already exists (skip), exists under another name (rename) or is missing (create).

Phase 3 · plan and approval

It writes the plan to .context/reports/jira-components-plan.json, shows it to you as a table (renames apart, each with its issue count) and runs the dry run. If you want to change names or grouping, it regenerates and shows it again.

Phase 4 · apply and verify

Only after your yes: --apply, and right after another --list. The live list has to match the approved plan. 

# phase 2 · current state, with issue counts
bun scripts/sync-jira-components.ts --list --project {{PROJECT_KEY}}

# phase 3 · dry run (it is the default: writes nothing)
bun scripts/sync-jira-components.ts .context/reports/jira-components-plan.json

# phase 4 · only with explicit approval
bun scripts/sync-jira-components.ts .context/reports/jira-components-plan.json --apply
bun scripts/sync-jira-components.ts --list --project {{PROJECT_KEY}}
The AI does

Reads the code and the backlog, groups routes into modules and builds the plan.

Warns if the product vocabulary clashes with generic names (Tests, Runs, Bugs) and proposes prefixing each component with the product name.

You decide

The grouping and the names of each module.

Whether the prefix is applied: it never goes in silently, it is part of the plan.

The yes that enables --apply.

Output

The plan in .context/reports/.

The project's Components module reconciled, and a report of what was renamed, created and skipped.

Gate the live list of Components matches the approved plan.
Rename is not createA rename keeps all existing assignments. That is how a component migrates to a new convention without editing issues in bulk.
Re-running is normalA rename whose source is gone, or whose target already exists, degrades to a documented skip. A half-applied plan can be run again.
Why a REST scriptacli cannot create, rename or delete Components. It is a documented limit of the tool, not a shortcut.
05 · instance-migration mode

Why it is not a find and replace

A site migration reassigns custom field IDs. The old ID often still exists in the new instance, pointing to another field. The failure is not a 404: it is a 200 OK that writes your data to the wrong field, silently.

Easy half

Repoint the host

  • One line in .agents/project.yaml.
  • acli re-login. The REST credentials and the acli session are independent: if you change only one, REST hits the new instance and acli keeps reading the old one, with no error.
Half that prevents corruption

Regenerate the catalogs

  • The catalogs in .agents/ describe an instance that no longer exists. See catalogs.

Phase 0 · resolve the two instances

Source: it detects it by reading .agents/project.yaml, the acli session and what bun run jira:url resolves. If they disagree, the repo is already half migrated: it treats it as a repair and asks you which one is the real "before". Target: it never guesses it, it asks you.

It confirms both hosts in one line, and before going on checks that the target answers 200 on /rest/api/3/myself. Migrating to an empty instance publishes empty catalogs.

Phase 1 · audit before editing

It sweeps the repo for the old host and sorts each finding into "changes" or "does not change". It shows you the table before touching anything. What fits neither list (a CI workflow, a README, .mcp.json) it asks about.

Phase 2 · apply

First atlassian_url in .agents/project.yaml, which is what everything else reads. Then it deletes any stray ATLASSIAN_URL. Last, the acli re-login with the host read back from the yaml.

Phase 3 · verify

Five checks in a table: the yaml, what jira:url resolves and the acli session all name the target; the presence probe [ -n "${ATLASSIAN_URL+x}" ] says unset; the REST call returns 200. Anything less than that is a failed migration.

Changes Does not change
.agents/project.yaml → atlassian_url: the only place the host is written An organization alias domain: it usually redirects to the active instance. But it is not visible from the repo, so you confirm it by hand
An old ATLASSIAN_URL in .env or in the process: it is deleted, not updated Historical records: sprint reports, retros, changelogs. Rewriting them falsifies the past
The acli session: re-login per machine Code that already matches a general regex, and the regenerable cache in .context/PBI/
The acli session is machine-wide. It lives in ~/.config/acli, not in the repo: the re-login repoints every project of the team, not just this one. If you still need the old instance for another repo, the AI stops and tells you; you will switch using the session-switch operation of /acli.
06 · phases 4 and 5

Regenerate the catalogs and prove the IDs moved

The agents' variables never store Jira IDs: they resolve slugs against three catalogs owned by each workspace. It is the part people skip, and the one that corrupts data.

Catalog Regenerated with Stores Watch out
.agents/jira-fields.json bun run jira:sync-fields --force IDs of custom fields and their options without --force it halts: the catalog is already populated
.agents/jira-workflows.json bun run jira:sync-workflows statuses and transitions per work type idempotent; --force adds nothing
.agents/jira-link-types.json bun run jira:sync-link-types link types between issues has no --force, and swallows it without warning

Before: the manifest sets the ceiling

.agents/jira-required.yaml stores no IDs, but it is the input of the regeneration: jira:sync-workflows catalogs only the work types it declares. An old manifest produces an amputated catalog that exits with code 0.

It is compared against upstream's and, if there is a difference, the AI stops and lets you choose type by type: the file is co-owned by upstream and the project.

After: a changed ID is not a correct ID

A diff with no ID changes means the sync never reached the new instance. But two slugs can swap IDs and survive that check. So it asks the live instance what each cataloged ID is and compares it with the registered name.

It also checks fields left with empty options, literal IDs outside the catalogs and any variable that pins an ID above the catalog.

Commit: separate responsibilities

One commit for the atlassian_url repoint, another for the three catalogs. If the manifest changed, it goes first, in a third one. All through /git-flow-master, and the push follows the git policy (Critical Rule #4).

--upex almost neverPulls a reference catalog generated against the boilerplate authors' workspace. If you migrate your own instance, its IDs are not yours. It only works as scaffolding without Administer permission, and it is flagged as incorrect data.
No backup of the .env in the repoA .env.bak is left unignored, with a live token inside, one git add away. The edit is one line and reverts itself.
Never open the .env, not even filtered by keyNot cat, not grep, not cut: the variables are used by name inside bunx varlock run, and if you need to know whether they exist, run bunx varlock load --agent, which redacts them. If a token does get printed, the AI says so and recommends rotating it.
Three things are left for a human in the closing report: confirming the alias domain already resolves to the target, knowing that a manifest that fell behind will fall behind again (the updater does not watch it), and telling the team that everyone must redo the acli login on their machine.
07 · the host anchor

The host lives in one place

.agents/project.yaml → issue_tracker.atlassian_url, and nowhere else in the repo. A second copy is what goes stale: after a migration, a stray host in the environment points the scripts at the old site and reports success.

How it is read

Always through the resolver

  • From code: cli/lib/atlassian-instance.ts, never process.env.ATLASSIAN_URL.
  • From the terminal: bun run --silent jira:url (base URL) or --slug (the bare host that acli --site asks for).
  • If an old environment variable disagrees, the yaml wins and the resolver warns with both values.
Contamination

A stray ATLASSIAN_URL gets deleted

  • It is not a local variable of this repo: a hit in .env or in the process is a leftover from before the split.
  • A value inherited from the process survives every restart. bun run vars:env:check and bun run setup:doctor report it.
  • Updating it instead of deleting it recreates the copy that will go stale in the next migration.
Template repo, values at null. If project.project_name is null, the repo is a template with no onboarding: atlassian_url and project_key stay at null, the report says so, and no empty commit is fabricated to hide it.
08 · what you tell the AI

Invoking it in each terminal

The first word after the skill name picks the mode, and the rest travels as is to the reference: the project key and the app path, or the two instances.

Claude Code

/jira-administration components

The skill slash plus the mode. With no mode, the AI takes it from the phrase or asks.

OpenCode

carga la skill jira-administration, modo instance-migration (load the jira-administration skill, mode instance-migration)

No slash: you name the skill and the mode in the sentence.

Codex

carga la skill jira-administration, modo components (load the jira-administration skill, mode components)

Same pattern as OpenCode, CLI or Desktop.

Pi

/skill:jira-administration components

Slash with the /skill: prefix. In a new folder, /trust once.

# components: explicit key and source, or empty so phase 1 resolves them
/jira-administration components BK ../bunkai

# instance-migration: source and target, in that order, or empty so phase 0 detects and asks
/jira-administration instance-migration oldsite.atlassian.net newsite.atlassian.net
09 · around this skill

Who it works with

On entry it resolves its complementary categories (issue-tracker, meta-skill) from .agents/skills/REGISTRY.md.

Always · both modes

/acli

Owns every Jira read, the authentication state and the site switch. It is loaded before any operation. It is also the door for day-to-day ticket work.

After · migration, phase 5

/git-flow-master

Owns the commit, branch and push contract that publishes the repoint and the catalogs. The push follows the git policy (Critical Rule #4).

Alongside · the Jira cache

.context/PBI/

The local mirror of the backlog, and why an old host corrupts it while reporting success. Deck: PBI as a Jira cache.

To read more: .agents/skills/jira-administration/SKILL.md and its two references in references/, one per mode. The host anchor is in .agents/instructions/agent-project-variables.md §7.

The idea behind it. Both operations write where a mistake goes unseen: a deleted component leaves orphaned issues, an old field ID writes to the wrong field with a 200. That is why each run reads first, shows you the whole plan and verifies by reading the destination.
