# Refresh AI Memory

Regenerate `README.md` and the AI memory file (auto-detected: `CLAUDE.md` / `GEMINI.md` / `CLAUDE.md` / `.cursor/rules` / `.github/copilot-instructions.md` / `.windsurf/rules`) so they reflect the current state of the project, its `.context/` files, and `package.json` scripts.

**Target**: $ARGUMENTS (leave blank to operate on the current repo)

---

## What this produces

Two synchronized documents:

1. **`README.md`** at the project root — human-facing project documentation.
2. **The AI memory file** — operational context loaded at every AI session start. The exact file is detected from disk (see Step 0).

Both are rewritten or refreshed. Existing structure is preserved; only stale facts are updated.

## Step 1 — Detect project state

Inspect what already exists. The set of present files determines mode.

```bash
# Project foundation (Constitution + Architecture + Discovery)
ls .context/idea/business-model.md .context/PRD/executive-summary.md .context/SRS/architecture.md 2>/dev/null

# Discovery outputs
ls .context/business-data-map.md .context/api-architecture.md .context/project-dev-guide.md 2>/dev/null

# Technical scaffolding
ls package.json tsconfig.json 2>/dev/null
ls api/schemas/ 2>/dev/null  # Generated by `bun run api:sync` if OpenAPI spec present

# Project identity
ls .agents/project.yaml 2>/dev/null
```

**Mode selection:**

| What exists                                                  | Mode               | Action                                                                                                                               |
| ------------------------------------------------------------ | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `.context/PRD/` + at least one Discovery output              | **Full Update**    | Rewrite README + refresh memory file with real values                                                                                |
| `package.json` + `.agents/project.yaml` only, no `.context/` | **Minimal Update** | Generate README + memory file with `<<PLACEHOLDER>>` values                                                                          |
| No `package.json` or no `.agents/`                           | **Stop**           | Tell the user to run `/agentic-dev-core` first, then `/project-foundation` to define identity, then `/project-bootstrap` for scaffolding |

Read in priority order. Stop at the first source that answers each question — do not load everything.

**Priority 1 (project identity):**

- `.context/idea/business-model.md`
- `.context/idea/market-context.md`
- `.agents/project.yaml`

**Priority 2 (technical context):**

- `.context/PRD/executive-summary.md` — what we're building, for whom

- `.context/business-data-map.md` — entities, flows, state machines

**Priority 3 (live config):**

- `package.json` (scripts, dependencies)
- `tsconfig.json`
- `.env.example` (variable names — never read `.env` itself)

Extract: project name, target app URLs, tech stack, main entities, critical APIs, top user journeys / core features, available scripts.

If `.context/` is empty, ask the user for the four minimum facts before proceeding:

1. Project name
2. Application URL (staging/dev)
3. Tech stack (frontend / backend / database)
4. Top 3 user journeys / core features

## Step 3 — Generate `README.md`

**This is a refresh, not a regeneration.** If `README.md` already exists at the repo root, read it first and patch only the facts that drifted (project identity, environment URLs, scripts table synced from `package.json`, tech-stack row, status row, references to `.context/` outputs). Keep the existing section order, headings, and any prose the user wrote. Do not reorder, rename, merge, or split sections you believe are redundant. The structure template below applies **only when `README.md` does not yet exist** — use it to bootstrap the file, then subsequent runs patch in place.

### Security rules (non-negotiable)

The README MUST NOT contain:

- Real credentials, API keys, or session tokens
- Production URLs that embed secrets
- Personal user data (emails, names) beyond placeholders

Always reference `.env.example` for variable names and use placeholders (`{your-api-key}`, `{your-staging-url}`).

#### Pre-write redaction (run before `Write`)

Scan the drafted README **and** AI-memory body in-memory before touching disk:

1. **Credential patterns** — strings matching `/(password|secret|token|api[_-]?key|authorization)\s*[:=]\s*\S+/i`.
2. **Production URLs** — hostnames that resolve to the project's production domain (`{{WEBAPP_DOMAIN}}`) **outside** the Environment URLs table. Staging / dev / localhost hosts are fine.
3. **Shaped secrets** — JWTs (`eyJ...`), Atlassian API tokens (`ATATT...`), GitHub PATs (`ghp_...`, `gho_...`), AWS keys (`AKIA...`).

On any match:

1. Replace the literal with `<<REDACTED>>` (or `{your-{field-name}}` placeholder when the field is the point of the paragraph).
2. Keep a redaction log — `{line reference} · {what was redacted} · {why}`.
3. Surface the log back to the user in the Step 6 report so they can source the value from `.env` instead and decide whether it was a false positive.

A redaction never silently succeeds — the user must see what was removed before the file is written.

### Structure (bootstrap template — used only when `README.md` is absent)

```markdown
# {Project Name}

> {1-paragraph description: what this app does, who it's for}
> Built with {tech stack: framework + language + database}

## Overview

{2-3 paragraph description}

### Status

| Aspect                       | Status       |
| ---------------------------- | ------------ |
| Foundation (PRD/SRS)         | ✅ / 🔄 / ❌ |
| Backend scaffolding          | ✅ / 🔄 / ❌ |
| Frontend scaffolding         | ✅ / 🔄 / ❌ |
| First feature in development | ✅ / 🔄 / ❌ |

## Tech stack

{Table: framework version, language version, database, key MCPs, runtime (Bun/Node)}

## Quick start

{Install steps, env setup, first run command}

## Available scripts

{Tables synced from package.json: Development, Quality, Tooling, Utilities}

## Project structure

{Simplified tree showing top-level dirs}

## AI-assisted development

{Reference to the AI memory file from Step 0 + a note about `/agentic-dev-core`, `/project-foundation`, `/sprint-dev`}

## Links

{Project repo, internal docs, deployment dashboards}
```

Sync the **Available scripts** section against `package.json` — do not invent scripts.

## Step 4 — Update the AI memory file

**The file already has structure — match it 1:1.** Refresh facts inside known sections and tables only. Do **not**:

- Reorder, rename, add, or remove top-level sections.
- Rewrite prose the user already wrote (especially Critical Reminders, Fundamental Rules, and narrative passages).
- "Improve" formatting, collapse tables you think are redundant, or merge sections.
- Restructure on the grounds that a different layout would be cleaner.

If the file's structure itself needs to change, that is a separate task the user has to request explicitly — never a side-effect of this refresh. Match section headings byte-for-byte; edit only the cell values.

### Sections to refresh with real values

- **Project Identity** — name, type, stack, target repo
- **Project Variables** table — fill `<<PLACEHOLDER>>` values from `.agents/project.yaml`
- **Environment URLs** — local / staging / production
- **Discovery Progress** — mark phases done by checking outputs under `.context/`:
  - Constitution → look for `.context/idea/`
  - Architecture (PRD + SRS) → look for `.context/PRD/`, `.context/SRS/`
  - Infrastructure → look for `package.json` setup, frameworks installed
  - Discovery → look for `.context/business-data-map.md`, `.context/api-architecture.md`, `.context/project-dev-guide.md`
- **Context System (3-Level Hierarchy)** — update the file lists to match what actually exists
- **Access Configuration** — verify which MCPs are configured, which env vars exist in `.env.example`

### Sections to preserve verbatim

These are stable rules — leave them alone unless the user asks otherwise:

- Critical Reminders (login from `.env`, no AI attribution, etc.)
- Fundamental Rules (TypeScript Patterns, etc.)
- Skills (Claude Code) table
- Tool Resolution table
- Git Workflow
- MCPs Available
- Future Hooks

### If the memory file does not yet exist

Create it from the canonical template at `.claude/skills/agentic-dev-core/templates/CLAUDE.md.template` (which is the source-of-truth mirror of the live `CLAUDE.md`). Copy the full structure, then fill or placeholder each section based on what `.context/` provides.

If no template exists in the project, generate a fresh skeleton based on the structure of `CLAUDE.md` in the boilerplate root.

Do **not** copy from a sibling project's `CLAUDE.md`/`CLAUDE.md` — those are downstream consumers, not templates.

## Step 5 — Validate

Run all three before reporting done.

**Security check** — grep the new README for:

- [ ] No hardcoded passwords / API keys / tokens
- [ ] No production URLs with embedded credentials
- [ ] No personal emails (placeholders only)

**Reference check:**

- [ ] Every script in README exists in `package.json`
- [ ] Every file path mentioned exists on disk
- [ ] Directory tree in README matches actual structure

**Consistency check:**

- [ ] Project name matches between README and the AI memory file
- [ ] Environment URLs match between both files
- [ ] Tech stack matches `package.json` and the relevant framework configs
